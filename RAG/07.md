# 07. RAG Evaluation 

## 1. How do you evaluate a RAG system?

### Answer

A RAG system should be evaluated in **two main stages**:

1. **Retrieval evaluation** → Did the system retrieve the right information?
2. **Generation evaluation** → Did the LLM use that information to produce a good answer?

Both stages are important because a RAG system can fail either during retrieval or during generation.

---

### Overall Evaluation Flow

```text
User Query
    ↓
Retrieval
    ↓
Retrieved Documents
    ↓
Evaluate Retrieval
    ↓
Context Construction
    ↓
LLM
    ↓
Generated Answer
    ↓
Evaluate Generation
```

---

### 1. Evaluate Retrieval

First, check whether the retriever is finding relevant documents.

Important metrics include:

- **Precision@k**
- **Recall@k**
- Retrieval relevance

### Precision@k

Precision@k measures how many of the top-k retrieved documents are actually relevant.

For example:

```text
Top 5 retrieved documents

Relevant documents = 4
Irrelevant documents = 1

Precision@5 = 4 / 5 = 0.8
```

A high precision means the retrieved results contain relatively little irrelevant information.

---

### Recall@k

Recall@k measures how many of the relevant documents that exist in the knowledge base were successfully retrieved in the top-k results.

For example:

```text
Relevant documents in knowledge base = 5
Relevant documents retrieved = 4

Recall@5 = 4 / 5 = 0.8
```

A high recall means the retriever is less likely to miss relevant information.

---

### 2. Evaluate Generation

After checking retrieval, evaluate the answer produced by the LLM.

Important aspects include:

### Faithfulness

**Faithfulness** checks whether the generated answer is supported by the retrieved context.

Example:

```text
Retrieved Context:
"Refunds are available within 30 days."

Answer:
"Customers can request a refund within 30 days."

→ Faithful
```

If the model says:

```text
"Customers can request a refund within 90 days."
```

the answer is not supported by the retrieved context.

---

### Answer Relevance

**Answer relevance** checks whether the generated answer actually addresses the user's question.

For example:

```text
Question:
"What is the refund period?"

Relevant Answer:
"Customers can request a refund within 30 days."

Irrelevant Answer:
"The company has several billing departments."
```

The second answer may contain factual information, but it does not answer the user's question.

---

### 3. Identify Where the Problem Occurs

A useful evaluation process separates retrieval problems from generation problems.

```text
                 RAG System
                     ↓
              Evaluate Retrieval
                     ↓
          Are retrieved documents
               relevant?
             ↙           ↘
           No             Yes
           ↓               ↓
   Retrieval Problem   Evaluate LLM
                           ↓
                    Is answer correct,
                    relevant and faithful?
                       ↙       ↘
                     No         Yes
                     ↓           ↓
              Generation      Good RAG
                Problem
```

### Example

Suppose the user asks:

> "What is the company's refund period?"

The system retrieves:

```text
Document:
"Refunds are available within 30 days."
```

But the LLM answers:

```text
"Refunds are available within 90 days."
```

Here:

- Retrieval → **Good**
- Generation → **Poor**

The problem is likely in the generation stage.

Now suppose the retriever returns:

```text
Document:
"Customers can contact support for billing issues."
```

and the LLM cannot answer the refund question.

Here:

- Retrieval → **Poor**
- Generation → difficult to evaluate fairly because the required information was not retrieved

The problem is primarily in retrieval.

---

### 4. Create an Evaluation Dataset

A RAG system should be tested using a representative set of questions.

An evaluation dataset can contain:

```text
Question
   ↓
Expected / Relevant Documents
   ↓
Expected Answer or Reference
```

For example:

| Question | Relevant Information | Expected Answer |
|---|---|---|
| What is the refund period? | Refund policy document | 30 days |
| How do I reset my password? | Account help document | Password reset steps |
| What is the support email? | Contact document | Support email |

This dataset can then be used repeatedly when changing the RAG pipeline.

---

### 5. Evaluate the Complete System

A complete evaluation should consider:

```text
                 RAG Evaluation
                       ↓
        ┌──────────────┴──────────────┐
        ↓                             ↓
 Retrieval Evaluation          Generation Evaluation
        ↓                             ↓
 Precision@k                   Faithfulness
 Recall@k                      Answer Relevance
 Retrieval Relevance           Answer Quality
        └──────────────┬──────────────┘
                       ↓
                Overall RAG Quality
```

The system can then be tested after changes to:

- Chunking
- Embedding model
- Retrieval strategy
- Query rewriting
- Reranking
- Prompt template
- LLM

This helps determine whether a change actually improves the system.

---

### Key Point

**A RAG system should be evaluated separately at the retrieval and generation stages. Retrieval can be evaluated using metrics such as Precision@k and Recall@k, while generation can be evaluated using faithfulness and answer relevance.**

### Interview Answer

> **I would evaluate a RAG system at both the retrieval and generation levels. For retrieval, I would check whether relevant documents are being retrieved using metrics such as Precision@k, Recall@k, and retrieval relevance. For generation, I would evaluate whether the answer is supported by the retrieved context using faithfulness and whether it actually answers the user's question using answer relevance. I would also create a representative evaluation dataset and use it to identify whether poor results are caused by retrieval or generation.**


## 2. What is Retrieval Evaluation vs Generation Evaluation?

### Answer

RAG evaluation is generally divided into **two stages**:

1. **Retrieval Evaluation** → Checks whether the system retrieved the right information.
2. **Generation Evaluation** → Checks whether the LLM used that information correctly to produce a good answer.

The main difference is:

> **Retrieval evaluation asks: "Did we find the right documents?"**  
> **Generation evaluation asks: "Did the LLM generate the right answer using those documents?"**

---

## 1. Retrieval Evaluation

**Retrieval evaluation** measures the quality of the documents or chunks retrieved by the retriever.

The goal is to determine whether the relevant information was successfully retrieved.

### What Do We Check?

We check:

- Are the retrieved documents relevant?
- Did the retriever find the required information?
- How many relevant documents were retrieved?
- How much irrelevant information was retrieved?

Common metrics include:

- **Precision@k**
- **Recall@k**
- Retrieval relevance

### Example

User asks:

```text
"What is the company's refund period?"
```

Suppose the knowledge base contains:

```text
Document A → Refund policy
Document B → Password reset
Document C → Product information
Document D → Billing policy
```

The retriever returns:

```text
Document A → Relevant
Document D → Relevant
Document C → Irrelevant
```

Retrieval evaluation checks whether the retrieved documents are useful for answering the question.

---

## 2. Generation Evaluation

**Generation evaluation** measures the quality of the answer produced by the LLM after receiving the retrieved context.

The goal is to determine whether the generated answer is:

- Supported by the retrieved context
- Relevant to the user's question
- Correct and useful

Important aspects include:

### Faithfulness

Checks whether the generated answer is supported by the retrieved context.

```text
Context:
"Refunds are available within 30 days."

Answer:
"Customers can request a refund within 30 days."

→ Faithful
```

---

### Answer Relevance

Checks whether the answer actually addresses the user's question.

```text
Question:
"What is the refund period?"

Answer:
"Customers can request a refund within 30 days."

→ Relevant
```

An answer about the company's billing department would not be relevant even if it were factually correct.

---

## Retrieval vs Generation

| Retrieval Evaluation | Generation Evaluation |
|---|---|
| Evaluates the retriever | Evaluates the LLM output |
| Checks retrieved documents | Checks generated answer |
| Happens before generation | Happens after retrieval and generation |
| Focuses on document relevance | Focuses on answer quality |
| Precision@k | Faithfulness |
| Recall@k | Answer relevance |
| Retrieval relevance | Answer correctness / usefulness |

---

## How They Work Together

```text
User Query
    ↓
Retriever
    ↓
Retrieved Documents
    ↓
┌──────────────────────┐
│ Retrieval Evaluation │
│                      │
│ Precision@k          │
│ Recall@k             │
│ Relevance            │
└──────────────────────┘
    ↓
Context
    ↓
LLM
    ↓
Generated Answer
    ↓
┌──────────────────────┐
│ Generation Evaluation│
│                      │
│ Faithfulness         │
│ Answer Relevance     │
│ Answer Quality       │
└──────────────────────┘
```

---

## Why Is This Separation Important?

Separating the two evaluations helps identify **where the RAG system is failing**.

### Case 1: Good Retrieval + Bad Generation

```text
Relevant documents retrieved
          ↓
Correct context
          ↓
LLM produces wrong answer
```

This indicates a likely **generation problem**.

---

### Case 2: Bad Retrieval

```text
Relevant document exists
          ↓
Retriever fails to find it
          ↓
LLM receives incorrect/incomplete context
          ↓
Poor answer
```

This indicates a **retrieval problem**.

---

### Case 3: Both Are Good

```text
Relevant documents
        ↓
Good context
        ↓
Faithful and relevant answer
```

This indicates good performance across both stages.

---

### Key Point

**Retrieval evaluation measures whether the correct and relevant information is retrieved, while generation evaluation measures whether the LLM produces a relevant and faithful answer from that retrieved information.**

### Interview Answer

> **Retrieval evaluation and generation evaluation measure different parts of a RAG system. Retrieval evaluation checks whether relevant documents are retrieved using metrics such as Precision@k, Recall@k, and retrieval relevance. Generation evaluation checks the quality of the final LLM answer, including whether it is supported by the retrieved context through faithfulness and whether it addresses the user's question through answer relevance. Separating these evaluations helps identify whether a poor RAG response is caused by retrieval or generation.**


## 3. What are Precision@k and Recall@k in Retrieval?

### Answer

**Precision@k** and **Recall@k** are retrieval evaluation metrics used to measure how well a RAG retriever finds relevant documents or chunks.

They help us understand whether the **top-k retrieved results are relevant** and whether the retriever **found most of the relevant information available**.

---

### 1. Precision@k

**Precision@k** measures:

> Out of the top `k` documents retrieved, how many are actually relevant?

### Formula

**Precision@k = Relevant documents in top-k / k**

### Example

Suppose the retriever returns the top 5 documents:

~~~text
Top 5 retrieved documents:

D1 → Relevant
D2 → Relevant
D3 → Not relevant
D4 → Relevant
D5 → Not relevant
~~~

There are **3 relevant documents** out of 5.

Therefore:

**Precision@5 = 3 / 5 = 0.6 = 60%**

So, precision tells us about the **quality of the retrieved results**.

---

### 2. Recall@k

**Recall@k** measures:

> Out of all the relevant documents that exist, how many were retrieved in the top-k?

### Formula

**Recall@k = Relevant documents retrieved in top-k / Total relevant documents**

### Example

Suppose there are **4 relevant documents** in the entire knowledge base.

The retriever finds 3 of them in its top 5 results:

~~~text
Total relevant documents = 4

Retrieved relevant documents = 3

Recall@5 = 3 / 4 = 0.75 = 75%
~~~

So, recall tells us how well the retriever **covers the relevant information**.

---

### Precision@k vs Recall@k

| Metric | Measures | Main Question |
|---|---|---|
| **Precision@k** | Relevance of retrieved results | "How many of the retrieved documents are relevant?" |
| **Recall@k** | Coverage of relevant documents | "How many of the relevant documents did we retrieve?" |

---

### Example in RAG

Suppose a user asks:

> "What are the refund conditions?"

There are **5 relevant chunks** in the knowledge base.

The retriever returns 5 chunks:

~~~text
Retrieved:
Chunk 1 → Relevant
Chunk 2 → Relevant
Chunk 3 → Relevant
Chunk 4 → Irrelevant
Chunk 5 → Irrelevant
~~~

Then:

**Precision@5 = 3 / 5 = 60%**

**Recall@5 = 3 / 5 = 60%**

If the retriever had returned:

~~~text
Chunk 1 → Relevant
Chunk 2 → Relevant
Chunk 3 → Relevant
Chunk 4 → Relevant
Chunk 5 → Relevant
~~~

Then:

**Precision@5 = 5 / 5 = 100%**

**Recall@5 = 5 / 5 = 100%**

---

### Why are they important in RAG?

A RAG system needs to retrieve the right information before asking the LLM to generate an answer.

#### Low Precision

The retriever returns many irrelevant chunks.

This can:

- Add noise to the context
- Confuse the LLM
- Increase token usage
- Increase latency and cost
- Reduce answer quality

#### Low Recall

The retriever fails to find important relevant chunks.

This can:

- Cause missing information
- Give the LLM incomplete context
- Result in incomplete or incorrect answers
- Increase the chance of unsupported generation

---

### Precision vs Recall Trade-off

Increasing `k` can often improve recall because more documents are retrieved.

However, retrieving more documents can also introduce irrelevant information and reduce precision.

~~~text
Small k
  ↓
Less context
  ↓
Usually less noise
  ↓
But may miss relevant information


Large k
  ↓
More context
  ↓
May find more relevant information
  ↓
But may introduce more irrelevant information
~~~

Therefore, the value of `k` should be selected by evaluating the RAG system on representative queries.

---

### Key Point

**Precision@k measures how many of the top-k retrieved documents are relevant, while Recall@k measures how many of all relevant documents were successfully retrieved in the top-k results.**

In RAG:

- **Precision → quality of retrieved results**
- **Recall → coverage of relevant information**

---

### Interview Answer

> **Precision@k measures the proportion of relevant documents among the top-k retrieved documents, while Recall@k measures the proportion of all relevant documents that were retrieved within the top-k results. Precision helps identify whether retrieval results contain too much irrelevant information, while recall helps identify whether the retriever is missing important information. Both are useful for evaluating and tuning the retrieval stage of a RAG system.**


## 4. What are Faithfulness and Answer Relevance?

### Answer

**Faithfulness** and **Answer Relevance** are evaluation metrics used to measure the quality of the **generated answer** in a RAG system.

They answer two different questions:

- **Faithfulness:** Is the answer supported by the retrieved context?
- **Answer Relevance:** Does the answer actually address the user's question?

---

### 1. Faithfulness

**Faithfulness** measures whether the information in the generated answer is **supported by the retrieved documents/context**.

In other words:

> "Did the LLM generate the answer using information that is actually present in the retrieved context?"

A highly faithful answer should not introduce unsupported facts.

### Example

User asks:

> "What is the company's refund period?"

Retrieved context:

~~~text
Customers can request a refund within 30 days of purchase.
~~~

Generated answer:

~~~text
Customers can request a refund within 30 days of purchase.
~~~

This answer is **faithful** because it is directly supported by the retrieved context.

Now consider:

~~~text
Customers can request a refund within 60 days of purchase.
~~~

This answer is **not faithful** because the retrieved context says **30 days**, not 60 days.

---

### Why is Faithfulness Important?

A RAG system can retrieve documents correctly but the LLM may still:

- Add information that is not present
- Misinterpret the retrieved context
- Make unsupported claims
- Hallucinate facts

Therefore, faithfulness helps identify **grounding problems in the generated answer**.

---

### 2. Answer Relevance

**Answer relevance** measures whether the generated answer is **relevant to the user's question**.

In other words:

> "Does the generated answer actually answer what the user asked?"

### Example

User asks:

> "What is the refund period?"

Answer:

~~~text
The refund period is 30 days from the date of purchase.
~~~

This answer is **relevant** because it directly answers the question.

But if the answer is:

~~~text
The company provides several payment methods, including credit cards
and UPI.
~~~

The answer may contain factual information, but it is **not relevant** to the user's question.

---

### Faithfulness vs Answer Relevance

| Metric | Measures | Main Question |
|---|---|---|
| **Faithfulness** | Support from retrieved context | "Is the answer supported by the context?" |
| **Answer Relevance** | Relevance to user query | "Does the answer answer the user's question?" |

---

### Example Showing the Difference

Suppose the user asks:

> "What is the refund period?"

Retrieved context:

~~~text
Customers can request a refund within 30 days of purchase.
~~~

#### Case 1 — Faithful and Relevant

~~~text
The refund period is 30 days from the date of purchase.
~~~

- Faithful → Yes
- Relevant → Yes

#### Case 2 — Relevant but Not Faithful

~~~text
The refund period is 60 days from the date of purchase.
~~~

- Faithful → No
- Relevant → Yes, because it attempts to answer the question.

#### Case 3 — Faithful but Not Relevant

~~~text
The company allows refunds within 30 days and accepts
credit card payments.
~~~

The first part is supported by the context, but if the answer mainly discusses payment methods instead of the refund question, its **answer relevance is lower**.

---

### Where Do They Fit in RAG Evaluation?

~~~text
User Query
    ↓
Retrieval
    ↓
Retrieved Context
    ↓
LLM
    ↓
Generated Answer
    ↓
┌──────────────────────────────┐
│      Generation Evaluation   │
│                              │
│  Faithfulness                │
│  Answer Relevance            │
└──────────────────────────────┘
~~~

**Faithfulness** checks the relationship between:

**Generated Answer ↔ Retrieved Context**

**Answer Relevance** checks the relationship between:

**Generated Answer ↔ User Question**

---

### Key Point

**Faithfulness checks whether the generated answer is grounded in the retrieved context, while answer relevance checks whether the answer actually addresses the user's question.**

A good RAG answer should ideally be:

- **Faithful** → supported by retrieved information
- **Relevant** → directly answers the user's question

---

### Interview Answer

> **Faithfulness measures whether a generated answer is supported by the retrieved context and does not contain unsupported claims. Answer relevance measures whether the generated answer actually addresses the user's question. In RAG evaluation, faithfulness helps detect hallucinations or unsupported generation, while answer relevance helps determine whether the system provided a useful answer to the user's query.**


## 5. How would you identify whether a poor answer is caused by retrieval or generation?

### Answer

In a RAG system, a poor answer can be caused by either:

1. **Retrieval failure** → the correct information was not retrieved.
2. **Generation failure** → the correct information was retrieved, but the LLM produced a poor answer.

The easiest way to identify the problem is to **inspect the retrieved documents before evaluating the generated answer**.

---

### Step 1: Check the Retrieved Documents

First, look at the documents/chunks retrieved for the user's query.

Ask:

> "Does the retrieved context contain the information needed to answer the question?"

### Case 1 — Relevant information is missing

Suppose the user asks:

> "What is the company's refund period?"

But the retriever returns:

~~~text
Chunk 1 → Payment methods
Chunk 2 → Shipping policy
Chunk 3 → Account security
~~~

The correct refund policy was not retrieved.

This indicates a **retrieval problem**.

Possible causes:

- Poor chunking
- Poor embeddings
- Incorrect query formulation
- Wrong top-k
- Poor search strategy
- Missing metadata filtering
- Lack of reranking

---

### Case 2 — Correct information is retrieved

Suppose the retrieved context contains:

~~~text
Customers can request a refund within 30 days of purchase.
~~~

But the LLM generates:

~~~text
Customers can request a refund within 60 days of purchase.
~~~

The required information was retrieved correctly, but the LLM generated an incorrect answer.

This indicates a **generation problem**.

Possible causes:

- LLM misunderstood the context
- Prompt is poorly designed
- Model generated unsupported information
- Too much irrelevant context confused the model
- Context was not presented clearly

---

### Step 2: Compare Retrieval and Generation Separately

A useful debugging approach is:

~~~text
User Query
    ↓
Retriever
    ↓
Retrieved Documents
    ↓
[Check Retrieval Quality]
    ↓
Context Construction
    ↓
LLM
    ↓
Generated Answer
    ↓
[Check Generation Quality]
~~~

This separates the two possible failure points.

---

### Retrieval Failure vs Generation Failure

| Situation | Likely Problem |
|---|---|
| Correct document is not retrieved | Retrieval |
| Retrieved documents are irrelevant | Retrieval |
| Retrieved context is incomplete | Retrieval |
| Correct information is present but ignored | Generation |
| LLM contradicts the retrieved context | Generation |
| LLM adds unsupported information | Generation |
| Answer does not address the question despite good context | Generation |

---

### Example

User asks:

> "What is the refund period?"

#### Scenario A — Retrieval Problem

Retrieved context:

~~~text
Shipping usually takes 5–7 business days.
~~~

Generated answer:

~~~text
The refund period is 7 days.
~~~

The retriever failed to provide the refund policy.

**Problem → Retrieval**

---

#### Scenario B — Generation Problem

Retrieved context:

~~~text
Customers can request a refund within 30 days of purchase.
~~~

Generated answer:

~~~text
Customers can request a refund within 60 days.
~~~

The correct information was available to the LLM, but it generated an unsupported answer.

**Problem → Generation**

---

### Metrics Can Help

Retrieval metrics can be used to identify retrieval problems:

- **Precision@k** → Are the retrieved documents relevant?
- **Recall@k** → Did we retrieve the important relevant documents?
- **Retrieval relevance** → How useful are the retrieved chunks?

Generation metrics can then be used to identify generation problems:

- **Faithfulness** → Is the answer supported by the retrieved context?
- **Answer relevance** → Does the answer address the user's question?
- **Answer quality/correctness** → Is the final answer accurate and useful?

---

### Practical Debugging Process

When a RAG answer is poor:

~~~text
1. Check the user query
        ↓
2. Inspect retrieved documents
        ↓
3. Are the required facts present?
        ↓
   ┌───────────────┴───────────────┐
   │                               │
  NO                              YES
   │                               │
Retrieval problem          Check generated answer
                                   ↓
                         Is answer supported?
                                   ↓
                          ┌────────┴────────┐
                          │                 │
                         NO                YES
                          │                 │
                  Generation problem   Check answer
                                      relevance/quality
~~~

If the required information is **not present in the retrieved context**, investigate the **retrieval pipeline**.

If the required information **is present but the LLM produces an incorrect or unsupported answer**, investigate the **generation stage**.

---

### Key Point

**To distinguish retrieval failure from generation failure, inspect the retrieved context first.**

- **Correct information missing → Retrieval problem**
- **Correct information present but answer is wrong → Generation problem**

This separation is important because improving the LLM will not fix a retriever that fails to find the required information, and improving retrieval will not necessarily fix an LLM that misuses correct context.

---

### Interview Answer

> **I would first inspect the retrieved documents before looking at the final answer. If the required information is missing or the retrieved chunks are irrelevant, the problem is likely in retrieval. I would then investigate chunking, embeddings, query formulation, top-k, filtering, and reranking. If the correct information is present in the retrieved context but the LLM produces an incorrect, unsupported, or irrelevant answer, the problem is likely in generation. I would then investigate the prompt, context construction, and model behavior.**


## 6. How would you create a test/evaluation dataset for a RAG application?

### Answer

A **RAG evaluation dataset** is a collection of representative questions and expected information used to measure whether the RAG system retrieves the right documents and generates good answers.

A good evaluation dataset should test both:

1. **Retrieval quality**
2. **Generation quality**

---

### 1. Collect Representative Documents

First, collect the documents that the RAG system will actually use.

For example, for a company knowledge-base RAG system:

~~~text
Company Policies
├── Refund Policy
├── Leave Policy
├── Security Policy
├── HR Guidelines
└── Product Documentation
~~~

The evaluation dataset should be created from the same type of information that the system will retrieve in production.

---

### 2. Create Representative Questions

Create questions that users are likely to ask.

For example:

~~~text
Question:
"What is the company's refund period?"

Question:
"How many days of paid leave are employees allowed?"

Question:
"What should I do if I forget my password?"
~~~

The questions should cover different types of queries, including:

- Simple questions
- Specific questions
- Multi-part questions
- Ambiguous questions
- Questions requiring information from multiple documents
- Questions for which the answer is not present in the knowledge base

---

### 3. Add Expected / Ground-Truth Information

For each question, identify the correct information or expected answer.

A simple dataset could look like:

| Question | Expected Answer | Relevant Document |
|---|---|---|
| What is the refund period? | 30 days | Refund Policy |
| How many paid leaves are allowed? | 20 days | Leave Policy |
| How do I reset my password? | Follow the password reset procedure | Security Policy |

The **relevant document/chunk** is particularly useful for evaluating retrieval.

---

### 4. Include Relevant Documents or Chunks

For retrieval evaluation, record which documents or chunks should be retrieved for each question.

Example:

~~~text
Question:
"What is the refund period?"

Relevant chunks:
- refund_policy_chunk_12
- refund_policy_chunk_13
~~~

Then compare the actual retrieved chunks against the expected relevant chunks.

This allows metrics such as:

- **Precision@k**
- **Recall@k**
- Retrieval relevance

to be calculated.

---

### 5. Include Expected Answers

For generation evaluation, store an expected answer or reference information.

Example:

~~~text
Question:
"What is the refund period?"

Reference Answer:
"Customers can request a refund within 30 days
of purchase."
~~~

The generated answer can then be evaluated for:

- **Faithfulness**
- **Answer relevance**
- Correctness
- Overall answer quality

---

### 6. Include Different Difficulty Levels

The dataset should not contain only easy questions.

For example:

~~~text
Easy
→ "What is the refund period?"

Medium
→ "Can I request a refund after receiving a replacement?"

Hard
→ "What happens if I request a refund after a replacement
has already been issued?"
~~~

This helps determine how the RAG system performs on different types of queries.

---

### 7. Include Negative / Unanswerable Questions

It is also useful to include questions whose answers are **not present in the knowledge base**.

Example:

~~~text
Question:
"Who is the CEO of the company?"

Knowledge base:
No information about the CEO.
~~~

The expected behavior should be something like:

> "The available information does not contain the answer."

This tests whether the RAG system avoids generating unsupported information.

---

### Example Evaluation Dataset

A simple structure could be:

~~~text
{
    "question": "What is the refund period?",
    "relevant_documents": [
        "refund_policy_chunk_12",
        "refund_policy_chunk_13"
    ],
    "reference_answer":
        "Customers can request a refund within 30 days of purchase."
}
~~~

Multiple such examples form the evaluation dataset.

---

### Complete Process

~~~text
Production Documents
        ↓
Create Representative Questions
        ↓
Identify Relevant Documents / Chunks
        ↓
Create Reference Answers
        ↓
Add Difficult & Unanswerable Questions
        ↓
Evaluation Dataset
        ↓
Run RAG System
        ↓
Compare Results
        ↓
Retrieval + Generation Metrics
~~~

---

### What Makes a Good Evaluation Dataset?

A good dataset should be:

- **Representative** → reflects real user queries
- **Diverse** → contains different types of questions
- **Balanced** → includes easy, difficult, and unanswerable questions
- **Grounded** → based on the actual knowledge base
- **Large enough** → contains enough examples to identify patterns
- **Maintained** → updated when documents or application behavior changes

---

### Key Point

A RAG evaluation dataset should contain **representative user questions, relevant documents/chunks, and reference answers or expected information**.

It should allow us to separately evaluate:

**Retrieval → Did we retrieve the right information?**

**Generation → Did the LLM use that information to produce a correct and relevant answer?**

---

### Interview Answer
