# 02 — Document Ingestion & Preprocessing

## 1. What is document ingestion in a RAG pipeline?

### Answer

**Document ingestion** is the process of **collecting documents from different sources, extracting their content, and preparing them to be used by the RAG system**.

It is the first major step in preparing a knowledge base for retrieval.

### Basic Document Ingestion Flow

```text
Documents / Data Sources
          ↓
    Document Loading
          ↓
     Text Extraction
          ↓
    Data Cleaning
          ↓
       Chunking
          ↓
      Embeddings
          ↓
Vector Database / Index
```

### What happens during document ingestion?

A RAG system may receive information from different sources, such as:

- PDF files
- Text files
- Word documents
- Web pages
- Databases
- Company documents

The ingestion process prepares this information so that it can later be retrieved when a user asks a question.

### Example

Suppose a company wants to build a RAG system using its internal documents.

```text
Company Documents
       ↓
   Load Documents
       ↓
   Extract Text
       ↓
   Clean Text
       ↓
   Split into Chunks
       ↓
   Create Embeddings
       ↓
   Store in Vector Database
```

Later, when a user asks a question, the RAG system can search these stored chunks and retrieve the relevant information.

### Why is Document Ingestion Important?

Good document ingestion is important because the quality of the information prepared during this stage affects the later **retrieval process**.

Poorly extracted or poorly prepared documents can lead to:

```text
Poor Document Processing
          ↓
Poor Chunks
          ↓
Poor Retrieval
          ↓
Poor Context
          ↓
Poor Answer
```

### Key Point

> **Document ingestion is the process of collecting, loading, extracting, and preparing documents so that their information can be processed and made available for retrieval in a RAG system.**

### Interview Answer

> **Document ingestion in a RAG pipeline is the process of collecting documents from different sources and preparing their content for retrieval. It generally involves loading documents, extracting and cleaning their text, splitting the content into chunks, creating embeddings, and storing the resulting representations in a searchable index or vector database.**


## 2. How would you extract text from PDFs, webpages, and other documents?

### Answer

Text extraction is the process of converting documents from different sources into **machine-readable text** that can be processed by a RAG system.

The method used for extraction depends on the type of document.

### 1. PDFs

For text-based PDFs, libraries such as **PyMuPDF** can be used to extract text from each page.

```python
import pymupdf

doc = pymupdf.open("document.pdf")

text = ""

for page in doc:
    text += page.get_text()

print(text)
```

If the PDF is **scanned or contains images instead of selectable text**, normal text extraction may not work. In that case, **OCR (Optical Character Recognition)** can be used.

```text
PDF
 ↓
Check whether text is available
 ↓
 ┌───────────────┐
 │               │
Yes             No
 │               │
 ↓               ↓
Extract Text    OCR
 │               │
 └───────┬───────┘
         ↓
     Extracted Text
```

---

### 2. Webpages

For webpages, we can first fetch the HTML content and then extract the meaningful text using an HTML parser such as **BeautifulSoup**.

```python
import requests
from bs4 import BeautifulSoup

url = "https://example.com"

response = requests.get(url)

soup = BeautifulSoup(response.text, "html.parser")

text = soup.get_text(separator=" ", strip=True)

print(text)
```

Unnecessary content such as navigation menus, advertisements, scripts, and HTML tags may need to be removed during preprocessing.

---

### 3. Word Documents

For `.docx` files, libraries such as `python-docx` can be used to extract text.

```python
from docx import Document

doc = Document("document.docx")

text = "\n".join(
    paragraph.text
    for paragraph in doc.paragraphs
)

print(text)
```

---

### 4. Text Files

For plain `.txt` files, Python's built-in file handling can be used.

```python
with open("document.txt", "r", encoding="utf-8") as file:
    text = file.read()

print(text)
```

---

### 5. Other Document Types

Different document formats can require different extraction methods.

Common sources include:

- PDF
- DOCX
- TXT
- HTML
- Markdown
- CSV
- JSON
- Databases

The goal is to convert these different sources into a **consistent text/document format** that can be processed by the RAG pipeline.

---

### After Text Extraction

Text extraction is only the first step.

The extracted content usually goes through:

```text
Document
    ↓
Text Extraction
    ↓
Cleaning
    ↓
Normalization
    ↓
Chunking
    ↓
Embedding
    ↓
Vector Database
```

---

### Important Consideration

Not every document can be processed in the same way.

For example:

- A text-based PDF can be directly parsed.
- A scanned PDF may require OCR.
- A webpage may contain unnecessary HTML content.
- A document containing tables may require special handling.

Therefore, the extraction method should depend on the **document type and structure**.

### Key Point

> **The extraction method depends on the document type. PDFs can be processed using PDF parsers, scanned PDFs may require OCR, webpages can be parsed from HTML, and DOCX or TXT files can be processed using their respective libraries. The extracted text is then cleaned and prepared for chunking and embedding.**

### Interview Answer

> **I would use a document-specific extraction method. For text-based PDFs, I can use a PDF parser such as PyMuPDF, while scanned PDFs may require OCR. For webpages, I would fetch the HTML and extract the meaningful content using an HTML parser such as BeautifulSoup. For DOCX and other formats, I would use appropriate libraries or document loaders. After extraction, I would clean and normalize the text before passing it to the chunking and embedding stages of the RAG pipeline.**


## 3. Why is document cleaning important before indexing?

### Answer

**Document cleaning** is the process of removing unwanted, irrelevant, or incorrectly extracted content from documents before they are converted into embeddings and stored in the index.

It is important because the quality of the indexed data directly affects the **retrieval quality** of a RAG system.

### Why is Document Cleaning Important?

#### 1. Removes Unnecessary Content

Documents may contain content that is not useful for retrieval, such as:

- Extra whitespace
- Repeated headers and footers
- Page numbers
- Navigation menus
- Advertisements
- HTML tags
- Duplicate content

Removing this information makes the stored content cleaner and more useful.

---

#### 2. Improves Retrieval Quality

If unnecessary content is indexed, it can interfere with similarity search.

```text
Unclean Document
      ↓
Noisy Chunks
      ↓
Poor Retrieval
      ↓
Irrelevant Context
      ↓
Poor Answer
```

Cleaning helps the retriever find more relevant information.

---

#### 3. Prevents Duplicate Information

The same content may appear multiple times in a document or across different documents.

Removing duplicates prevents the index from containing unnecessary repeated information.

```text
Before Cleaning:

Document A → Information X
Document A → Information X
Document B → Information X

After Cleaning:

Document A → Information X
```

---

#### 4. Improves Embeddings

Text is usually converted into embeddings before being indexed.

If the text contains unnecessary or noisy content, the resulting embeddings may not represent the important information as effectively.

```text
Clean Text
    ↓
Embedding
    ↓
Better Representation
    ↓
Better Retrieval
```

---

#### 5. Reduces Storage and Processing

Removing unnecessary content can reduce the amount of data that needs to be:

- Processed
- Chunked
- Embedded
- Stored
- Retrieved

This can make the RAG pipeline more efficient.

---

### Example

Suppose a PDF contains:

```text
Company Leave Policy

Page 1

Employees are entitled to 20 days of annual leave.

Page 2

Company Leave Policy

Employees can carry forward 5 unused days.

Page 3

Company Leave Policy
```

The repeated title and page information may not be useful for retrieval.

After cleaning:

```text
Employees are entitled to 20 days of annual leave.

Employees can carry forward 5 unused days.
```

The cleaned text can then be chunked and indexed.

---

### Cleaning Pipeline

```text
Raw Document
     ↓
Remove Noise
     ↓
Remove Duplicates
     ↓
Normalize Text
     ↓
Clean Document
     ↓
Chunking
     ↓
Embeddings
     ↓
Index / Vector Database
```

### Key Point

> **Document cleaning is important because it removes noise, duplicates, and irrelevant content before indexing. This improves the quality of chunks and embeddings, which can lead to better retrieval and more relevant context for the LLM.**

### Interview Answer

> **Document cleaning is important because raw documents often contain unnecessary content, duplicates, formatting issues, headers, footers, or other noise. If this information is indexed, it can negatively affect chunking, embeddings, and retrieval quality. Cleaning the documents before indexing helps create cleaner chunks, better representations, and more relevant retrieved context.**


## 4. What is chunking?

### Answer

**Chunking** is the process of dividing a large document into smaller, manageable pieces called **chunks**.

In a RAG pipeline, documents are usually too large to retrieve and process as a single unit. Therefore, they are split into smaller chunks before creating embeddings and indexing them.

### Example

Suppose we have a large document:

```text
Large Document
      ↓
 ┌────┬────┬────┬────┐
 │ C1 │ C2 │ C3 │ C4 │
 └────┴────┴────┴────┘
```

Each `C` represents a chunk of the original document.

For example:

```text
Original Document:

"RAG is a technique that combines retrieval with
generation. It retrieves relevant information from
an external knowledge source and provides it to an LLM.
The LLM then uses this information to generate an answer."
```

After chunking:

```text
Chunk 1:
"RAG is a technique that combines retrieval with generation."

Chunk 2:
"It retrieves relevant information from an external knowledge source."

Chunk 3:
"The LLM then uses this information to generate an answer."
```

These chunks can then be converted into embeddings and stored in a vector database.

### Where Does Chunking Fit in RAG?

```text
Document
    ↓
Text Extraction
    ↓
Cleaning
    ↓
Chunking
    ↓
Embeddings
    ↓
Vector Database
    ↓
Retrieval
```

### Why is Chunking Needed?

Chunking helps the RAG system:

- Retrieve only the relevant part of a document.
- Avoid sending an entire large document to the LLM.
- Create manageable units for embedding and retrieval.
- Improve the relevance of retrieved information.

### Chunking and Retrieval

Suppose a document contains information about:

```text
Company History
Employee Benefits
Leave Policy
Salary Policy
Contact Information
```

If the user asks:

> "How many annual leaves are employees allowed?"

The retriever should ideally return the chunk containing the **Leave Policy**, rather than the entire document.

```text
User Query
    ↓
Retriever
    ↓
Relevant Chunk
    ↓
LLM
    ↓
Answer
```

### Key Point

> **Chunking is the process of dividing large documents into smaller pieces so that they can be independently embedded, indexed, and retrieved when needed.**

### Interview Answer

> **Chunking is the process of dividing a large document into smaller pieces called chunks. These chunks are used as individual units for embedding and indexing in a RAG system. When a user asks a question, the retriever can then retrieve the most relevant chunks instead of retrieving the entire document.**


## 5. Why can't we simply put an entire document into the vector database?

### Answer

We usually don't store an entire large document as a **single vector** because it contains a lot of information, and a single embedding may not represent all the different topics and details accurately.

Instead, we divide the document into smaller **chunks** and create an embedding for each chunk.

### Example

Suppose a document contains information about:

```text
Company History
Employee Benefits
Leave Policy
Salary Policy
Contact Information
```

If we create only one embedding for the entire document:

```text
Entire Document
      ↓
One Embedding
      ↓
Vector Database
```

A single vector represents many different topics together.

Instead, we can divide the document into chunks:

```text
Entire Document
      ↓
 ┌──────────────┬──────────────┬──────────────┐
 │ Company      │ Leave Policy │ Salary       │
 │ History      │              │ Policy       │
 └──────────────┴──────────────┴──────────────┘
        ↓              ↓              ↓
    Embedding 1    Embedding 2    Embedding 3
        ↓              ↓              ↓
              Vector Database
```

Now, if the user asks:

> "How many annual leaves are employees allowed?"

The retriever can find the **Leave Policy chunk** instead of retrieving the entire document.

### Problems with Storing the Entire Document as One Vector

#### 1. Poor Retrieval Granularity

A single vector represents the entire document.

The retriever cannot easily distinguish between different topics inside that document.

```text
One Large Document
       ↓
One Vector
       ↓
Less Precise Retrieval
```

---

#### 2. Less Relevant Context

If a document contains many unrelated topics, retrieving the entire document may provide a lot of unnecessary information to the LLM.

```text
User Query
    ↓
Retrieve Entire Document
    ↓
Relevant Information + Irrelevant Information
    ↓
LLM
```

With chunking:

```text
User Query
    ↓
Retrieve Relevant Chunk
    ↓
LLM
```

---

#### 3. Large Context Size

Large documents can contain a lot of text.

Passing an entire document to the LLM can consume more context and increase processing requirements.

Chunking allows the system to retrieve only the required portions.

---

#### 4. Lower Retrieval Precision

When different topics are combined into one vector, the vector represents the overall meaning of the document rather than a specific piece of information.

Smaller chunks allow embeddings to represent more focused pieces of information.

---

### Why Do We Use Chunks?

```text
Large Document
      ↓
   Chunking
      ↓
Small Chunks
      ↓
 Embeddings
      ↓
Vector Database
      ↓
Retrieve Relevant Chunks
      ↓
LLM
```

This makes retrieval more **focused and relevant**.

### Key Point

> **We generally don't store a large document as a single vector because one embedding may represent many different topics and provide poor retrieval granularity. By splitting the document into smaller chunks, each chunk can have its own embedding and can be retrieved independently.**

### Interview Answer

> **We don't usually store an entire large document as a single vector because one embedding represents the document as a whole and may not capture the specific information needed for a query. Instead, we split the document into smaller chunks and create embeddings for each chunk. This allows the retriever to find the specific relevant portions of the document and provide more focused context to the LLM.**


## 6. What are fixed-size, recursive, semantic, and document-structure-based chunking?

### Answer

**Chunking strategies** define how a large document is divided into smaller chunks before creating embeddings and storing them for retrieval.

The four common approaches are:

1. Fixed-size chunking
2. Recursive chunking
3. Semantic chunking
4. Document-structure-based chunking

---

### 1. Fixed-Size Chunking

In **fixed-size chunking**, the document is divided into chunks of a predefined size.

The size can be measured using characters, words, or tokens.

```text
Document
    ↓
Fixed Size
    ↓
┌────────┬────────┬────────┬────────┐
│ Chunk 1│ Chunk 2│ Chunk 3│ Chunk 4│
└────────┴────────┴────────┴────────┘
```

For example, if the chunk size is 500 tokens:

```text
Document
   ↓
500 tokens → Chunk 1
500 tokens → Chunk 2
500 tokens → Chunk 3
500 tokens → Chunk 4
```

**Advantages:**
- Simple to implement
- Predictable chunk sizes
- Easy to control

**Limitation:**
- A chunk may split a sentence, paragraph, or idea in the middle.

---

### 2. Recursive Chunking

**Recursive chunking** attempts to split the document using a hierarchy of separators.

For example:

```text
Document
   ↓
Paragraphs
   ↓
Sentences
   ↓
Words
```

The system first tries to split using larger structural boundaries. If the resulting piece is still too large, it recursively splits it using smaller boundaries.

```text
Large Document
      ↓
   Paragraph
      ↓
   Sentence
      ↓
 Smaller Chunk
```

**Advantages:**
- Usually preserves more natural text boundaries.
- More flexible than simply cutting text at a fixed size.

**Limitation:**
- The final chunks may still not perfectly represent individual concepts.

---

### 3. Semantic Chunking

**Semantic chunking** divides a document based on the **meaning or topic of the content** rather than using only a fixed number of tokens or characters.

The goal is to keep related information together.

```text
Document
   ↓
Analyze Meaning
   ↓
Identify Topic Boundaries
   ↓
Semantic Chunks
```

For example:

```text
Chunk 1 → Introduction to RAG
Chunk 2 → Document Retrieval
Chunk 3 → Embeddings
Chunk 4 → Vector Databases
```

Each chunk focuses on a particular concept.

**Advantages:**
- Keeps related information together.
- Can improve the relevance of retrieved chunks.

**Limitation:**
- More computationally expensive and more complex than simple chunking methods.

---

### 4. Document-Structure-Based Chunking

In **document-structure-based chunking**, the existing structure of the document is used to determine the chunks.

The structure may include:

- Headings
- Sections
- Subsections
- Paragraphs
- Tables
- Lists
- Chapters

For example:

```text
Document
   │
   ├── Introduction
   │
   ├── Chapter 1
   │      ├── Section 1.1
   │      └── Section 1.2
   │
   └── Chapter 2
          ├── Section 2.1
          └── Section 2.2
```

The system can use these sections as natural chunks.

**Advantages:**
- Preserves the original document organization.
- Useful for structured documents such as manuals, reports, and books.

**Limitation:**
- Depends on the quality and consistency of the document structure.

---

### Comparison

| Chunking Strategy | Main Idea | Advantage | Limitation |
|---|---|---|---|
| Fixed-size | Split into fixed-sized pieces | Simple and predictable | May split ideas or sentences |
| Recursive | Split using a hierarchy of separators | Preserves natural boundaries better | More complex than fixed-size |
| Semantic | Split based on meaning/topics | Keeps related information together | More computationally expensive |
| Document-structure-based | Split using headings, sections, etc. | Preserves document structure | Depends on document structure |

### Example

Suppose we have a technical document:

```text
# RAG

## Introduction
...

## Embeddings
...

## Vector Databases
...

## Retrieval
...
```

Different strategies would handle it differently:

```text
Fixed-size
→ Split after a fixed number of tokens

Recursive
→ Split using paragraphs/sentences when needed

Semantic
→ Group text according to related meaning

Document-structure-based
→ Use Introduction, Embeddings, Vector Databases,
  and Retrieval as natural boundaries
```

### Key Point

> **Fixed-size chunking splits text using a predefined size, recursive chunking uses a hierarchy of separators, semantic chunking uses meaning or topic boundaries, and document-structure-based chunking uses the existing structure of the document such as headings and sections.**

### Interview Answer

> **The main chunking strategies are fixed-size, recursive, semantic, and document-structure-based chunking. Fixed-size chunking divides text into predefined-sized pieces. Recursive chunking progressively splits text using separators such as paragraphs and sentences. Semantic chunking divides text according to meaning or topic boundaries. Document-structure-based chunking uses elements such as headings, sections, paragraphs, and chapters to create chunks. The appropriate strategy depends on the structure and nature of the dataset.**


## 7. How do chunk size and chunk overlap affect retrieval?

### Answer

**Chunk size** determines how much information is stored in each chunk, while **chunk overlap** determines how much content is shared between consecutive chunks.

Both have a direct effect on the quality of retrieval.

### 1. Chunk Size

Chunk size controls the amount of text contained in each chunk.

```text
Small Chunk
→ Less information
→ More focused

Large Chunk
→ More information
→ More context
```

#### If the chunks are too small:

- Important context may be separated across multiple chunks.
- A chunk may not contain enough information to answer the query.
- More chunks may need to be retrieved.

```text
Too Small
   ↓
Incomplete Context
   ↓
Poor Retrieval
```

#### If the chunks are too large:

- A chunk may contain unrelated information.
- Retrieved context can become noisy.
- More unnecessary information may be passed to the LLM.

```text
Too Large
   ↓
More Irrelevant Information
   ↓
Noisy Context
```

Therefore, the chunk size should be large enough to preserve useful context but small enough to remain focused.

---

### 2. Chunk Overlap

**Chunk overlap** means that some content from one chunk is repeated in the next chunk.

For example, with an overlap:

```text
Chunk 1:
A B C D E F

Chunk 2:
        E F G H I J

Chunk 3:
                I J K L M N
```

Here, `E F` and `I J` are shared between consecutive chunks.

### Why is Chunk Overlap Used?

Overlap helps preserve context when an important piece of information lies near a chunk boundary.

Without overlap:

```text
Chunk 1:
"RAG retrieves relevant information from an external"

Chunk 2:
"knowledge source and provides it to the LLM."
```

The meaning of the complete sentence is split between two chunks.

With overlap:

```text
Chunk 1:
"RAG retrieves relevant information from an external"

Chunk 2:
"from an external knowledge source and provides it to the LLM."
```

The second chunk retains some context from the previous chunk.

---

### Effect of Increasing Overlap

#### Too Little Overlap

- Important context may be lost at chunk boundaries.
- Related information may be split between chunks.

```text
Low Overlap
    ↓
Less Shared Context
    ↓
Possible Context Loss
```

#### Too Much Overlap

- The same information is stored repeatedly.
- More embeddings need to be created.
- Storage requirements increase.
- Retrieval may return highly similar duplicate chunks.

```text
High Overlap
    ↓
More Duplicate Content
    ↓
More Storage + Processing
```

---

### Chunk Size vs Chunk Overlap

| Parameter | Too Low | Too High |
|---|---|---|
| Chunk Size | May lose context | May contain irrelevant information |
| Chunk Overlap | Context may be split | Creates unnecessary duplication |

### Example

Suppose a document contains:

```text
Employee Leave Policy
Employees receive 20 days of annual leave.
Unused leave can be carried forward for one year.
Carry-forward leave must be used before March.
```

If the chunk size is too small, the rule about **carry-forward leave** may be split across different chunks.

Using a suitable chunk size and some overlap can help keep related information together.

### Key Point

> **Chunk size controls how much information each chunk contains, while chunk overlap preserves some context between neighboring chunks. Very small chunks may lose context, very large chunks may contain unnecessary information, too little overlap may break context at boundaries, and too much overlap can create redundant data.**

### Interview Answer

> **Chunk size and overlap directly affect retrieval quality. If chunks are too small, they may not contain enough context to answer a query. If they are too large, they may contain irrelevant information and create noisy context. Chunk overlap helps preserve information across chunk boundaries, but excessive overlap creates duplicate content and increases storage and processing requirements. Therefore, both should be chosen according to the document structure and retrieval requirements.**


## 8. How would you choose an appropriate chunking strategy for a particular dataset?

### Answer

There is **no single chunking strategy that works best for every dataset**. The appropriate strategy depends on the **type, structure, and nature of the documents**, as well as the retrieval requirements of the RAG system.

The main factors to consider are:

1. Document structure
2. Nature of the content
3. Semantic relationships
4. Retrieval requirements
5. Chunk size and overlap
6. Retrieval performance

---

### 1. Consider the Document Structure

First, examine how the documents are organized.

If the documents have a clear structure such as:

- Headings
- Sections
- Subsections
- Chapters
- Paragraphs
- Tables

then **document-structure-based chunking** can be appropriate.

For example:

~~~text
Technical Manual
       ↓
Chapter 1 → Introduction
Chapter 2 → Installation
Chapter 3 → Configuration
Chapter 4 → Troubleshooting
~~~

Each section can act as a natural chunk.

---

### 2. Consider the Nature of the Content

Different datasets contain different types of information.

| Dataset | Suitable Strategy |
|---|---|
| Simple text | Fixed-size chunking |
| Long unstructured text | Recursive chunking |
| Topic-heavy documents | Semantic chunking |
| Books / manuals / reports | Document-structure-based chunking |

The goal is to choose a strategy that keeps useful and related information together.

---

### 3. Consider Semantic Relationships

If information is strongly connected by meaning, **semantic chunking** can be useful.

For example:

~~~text
Document
   ↓
Different Topics
   ↓
Topic 1 → RAG Introduction
Topic 2 → Embeddings
Topic 3 → Vector Databases
Topic 4 → Retrieval
~~~

The objective is to keep information belonging to the same concept together.

---

### 4. Consider Retrieval Requirements

The type of questions users will ask also affects the chunking strategy.

If users usually ask about very specific facts, smaller and more focused chunks may be useful.

~~~text
Specific Query
      ↓
Focused Chunks
      ↓
Precise Retrieval
~~~

If users need broader explanations that depend on more context, larger chunks may be more appropriate.

~~~text
Broad Query
      ↓
Larger Chunks
      ↓
More Complete Context
~~~

Therefore, the chunking strategy should match the expected retrieval requirements.

---

### 5. Choose Chunk Size and Overlap

After selecting a chunking strategy, choose an appropriate **chunk size and overlap**.

~~~text
Too Small
   ↓
Insufficient Context

Too Large
   ↓
Irrelevant Information

Too Little Overlap
   ↓
Context Can Be Lost

Too Much Overlap
   ↓
Duplicate Information
~~~

The goal is to balance **context preservation** and **retrieval precision**.

---

### 6. Evaluate Retrieval Performance

The selected strategy should be tested using the actual dataset and retrieval queries.

~~~text
Dataset
   ↓
Apply Chunking Strategy
   ↓
Create Embeddings
   ↓
Retrieve Chunks
   ↓
Evaluate Retrieval Quality
   ↓
Adjust Chunking
~~~

If retrieval frequently returns incomplete or irrelevant information, the chunking strategy, chunk size, or overlap may need to be changed.

---

### Example

Suppose we have three different datasets:

~~~text
Dataset 1 → Simple text documents
Dataset 2 → Technical documentation
Dataset 3 → Books with chapters and sections
~~~

A possible approach would be:

~~~text
Simple Text
    ↓
Fixed-size / Recursive

Technical Documentation
    ↓
Recursive / Semantic

Books
    ↓
Document-Structure-Based
~~~

The choice should be based on the actual structure and retrieval requirements of the dataset rather than using the same strategy everywhere.

---

### Decision Process

~~~text
Understand Dataset
       ↓
Check Document Structure
       ↓
Understand Content and Topics
       ↓
Determine Retrieval Requirements
       ↓
Choose Chunking Strategy
       ↓
Tune Chunk Size + Overlap
       ↓
Test Retrieval Quality
       ↓
Refine if Necessary
~~~

### Key Point

> **The appropriate chunking strategy depends on the dataset's structure, content, semantic relationships, and retrieval requirements. Structured documents may benefit from document-structure-based chunking, while unstructured or topic-heavy data may use recursive or semantic chunking. The strategy should be tested and adjusted based on retrieval quality.**

### Interview Answer

> **I would choose a chunking strategy based on the structure and nature of the dataset and the type of queries the RAG system needs to answer. For structured documents such as manuals or reports, I would consider document-structure-based chunking. For general text, fixed-size or recursive chunking can be used, while semantic chunking can be useful when maintaining topic-level meaning is important. I would then tune the chunk size and overlap and evaluate retrieval quality to determine whether the strategy needs adjustment.**
