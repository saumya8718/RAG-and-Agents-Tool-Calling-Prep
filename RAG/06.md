# 06. Generation & Context Construction

## 1. How are retrieved documents passed to the LLM?

### Answer

In a RAG system, the documents retrieved from the knowledge base are **not usually sent directly to the LLM as separate database records**.

Instead, the retrieved documents are:

1. Retrieved by the retriever
2. Selected and optionally reranked
3. Combined into a **context**
4. Inserted into a prompt
5. Sent to the LLM along with the user's query

The LLM then uses this retrieved context to generate the final answer.

---

### Basic Flow

~~~text
User Query
    ↓
Retriever
    ↓
Retrieved Documents / Chunks
    ↓
Reranking / Filtering (Optional)
    ↓
Context Construction
    ↓
Prompt + Retrieved Context
    ↓
LLM
    ↓
Generated Answer
~~~

---

### Example

Suppose the user asks:

> **"What is the refund policy?"**

The retriever finds three relevant chunks:

```text
Document 1:
"Customers can request a refund within 30 days..."

Document 2:
"Refund requests must include the original order ID..."

Document 3:
"Refunds are processed within 5-7 business days..."
```

These chunks are combined into a context:

```text
Context:
Customers can request a refund within 30 days.

Refund requests must include the original order ID.

Refunds are processed within 5-7 business days.
```

The application then constructs a prompt:

```text
Use the following context to answer the user's question.

Context:
Customers can request a refund within 30 days.

Refund requests must include the original order ID.

Refunds are processed within 5-7 business days.

Question:
What is the refund policy?
```

This complete prompt is sent to the LLM.

---

### Context Construction

**Context construction** is the process of preparing retrieved information before giving it to the LLM.

It may involve:

- Selecting the most relevant chunks
- Reranking documents
- Removing duplicate information
- Ordering the retrieved chunks
- Combining chunks into a coherent context
- Adding document metadata when useful
- Limiting the context to fit the LLM's context window

The goal is to provide the LLM with **relevant and useful information rather than unnecessary documents**.

---

### Why Not Send All Retrieved Documents?

Sending too much retrieved information can:

- Increase token usage
- Increase cost
- Increase latency
- Consume the context window
- Introduce irrelevant information
- Make it harder for the LLM to identify the important information

Therefore, RAG systems usually select the most relevant retrieved chunks before constructing the final prompt.

---

### Typical RAG Architecture

~~~text
                    User Query
                        ↓
                    Retriever
                        ↓
               Retrieved Chunks
                        ↓
                   Reranker
                        ↓
                Top Relevant Chunks
                        ↓
              Context Construction
                        ↓
          ┌─────────────────────────┐
          │ System Instructions     │
          │ Retrieved Context       │
          │ User Question           │
          └─────────────────────────┘
                        ↓
                       LLM
                        ↓
                  Final Answer
~~~

---

### Grounding the LLM

The retrieved documents provide **external context** that helps ground the LLM's response.

For example:

```text
Question:
"What is the company's refund period?"

Retrieved Context:
"Customers can request a refund within 30 days."

LLM:
"Customers can request a refund within 30 days."
```

The LLM uses the retrieved information instead of relying only on its internal knowledge.

However, retrieval alone does not guarantee that the LLM will always produce a correct answer. Prompt design, context quality, and generation behavior also matter.

---

### Key Point

**Retrieved documents are usually converted into a context and inserted into the LLM prompt along with the user's query. The LLM then uses this context to generate a grounded response.**

### Interview Answer

> **In a RAG system, retrieved documents are first selected, optionally reranked and filtered, and then combined into a context. This context is inserted into a prompt along with the user's query and instructions. The complete prompt is sent to the LLM, which uses the retrieved information to generate the final answer.**


## 2. What is Context Construction?

### Answer

**Context construction** is the process of taking the relevant documents or chunks retrieved from the knowledge base and **organizing them into useful context that is provided to the LLM**.

The retrieved information is prepared and combined with the user's query and instructions to create the final prompt sent to the LLM.

---

### Basic Flow

~~~text
User Query
    ↓
Retriever
    ↓
Retrieved Documents
    ↓
Filtering / Reranking
    ↓
Context Construction
    ↓
Final Prompt
    ↓
LLM
    ↓
Answer
~~~

---

### What Happens During Context Construction?

Context construction may involve:

- Selecting the most relevant chunks
- Removing irrelevant documents
- Removing duplicate information
- Ordering the retrieved chunks
- Combining multiple chunks
- Adding useful metadata or document information
- Formatting the information clearly
- Keeping the context within the LLM's context-window limit

The goal is to create a **high-quality, relevant context** that helps the LLM answer the user's question.

---

### Example

Suppose the user asks:

> **"What are the benefits of RAG?"**

The retriever returns:

```text
Chunk 1:
RAG allows LLMs to access external knowledge.

Chunk 2:
RAG can use frequently updated information.

Chunk 3:
This document discusses the history of neural networks.

Chunk 4:
RAG can reduce dependence on the LLM's internal knowledge.
```

Not every retrieved chunk is useful.

During context construction:

```text
Relevant Chunks
      ↓
Remove irrelevant information
      ↓
Combine useful chunks
      ↓
Create final context
```

The resulting context could be:

```text
RAG allows LLMs to access external knowledge.

RAG can use frequently updated information.

RAG can reduce dependence on the LLM's internal knowledge.
```

This context is then included in the prompt:

```text
Use the following context to answer the question.

Context:
RAG allows LLMs to access external knowledge.
RAG can use frequently updated information.
RAG can reduce dependence on the LLM's internal knowledge.

Question:
What are the benefits of RAG?
```

---

### Why Is Context Construction Important?

Good retrieval alone is not enough.

Even if the retriever finds relevant documents, poorly organized context can make it difficult for the LLM to use the information effectively.

Good context construction helps:

- Improve answer relevance
- Reduce irrelevant information
- Reduce unnecessary token usage
- Reduce latency and cost
- Keep important information within the context window
- Provide clearer evidence to the LLM

---

### Context Construction vs Retrieval

| Retrieval | Context Construction |
|---|---|
| Finds relevant documents | Prepares retrieved documents for the LLM |
| Happens before context construction | Happens after retrieval |
| Focuses on finding information | Focuses on organizing information |
| Uses vector, keyword, or hybrid search | Uses filtering, ordering, combining, formatting, etc. |

For example:

```text
Retrieval:
"Find the relevant documents."

Context Construction:
"Decide what retrieved information should actually be given to the LLM and how it should be presented."
```

---

### Context Construction and Context Window

An LLM has a limited **context window**, so a RAG system cannot always send every retrieved document to the model.

For example:

```text
100 Retrieved Chunks
        ↓
Filter / Rerank
        ↓
10 Relevant Chunks
        ↓
Context Construction
        ↓
LLM
```

This keeps the prompt manageable and focuses the LLM on the most useful information.

---

### Key Point

**Context construction is the process of selecting, organizing, filtering, and formatting retrieved information into a useful context that is passed to the LLM along with the user's query.**

### Interview Answer

> **Context construction is the process of preparing retrieved documents before sending them to the LLM. It involves selecting relevant chunks, removing unnecessary or duplicate information, ordering and combining the chunks, and formatting them into a useful context. This context is then included in the final prompt along with the user's query so that the LLM can generate a relevant and grounded answer.**


## 3. How would you prevent irrelevant retrieved information from confusing the LLM?

### Answer

Irrelevant retrieved information can confuse the LLM and may cause it to generate an incorrect or poorly grounded answer.

To prevent this, the RAG pipeline should ensure that **only relevant and useful information is passed to the LLM**.

Several techniques can be used.

---

### 1. Improve Retrieval Quality

First, improve the retriever so that it returns more relevant documents.

This can be done by:

- Improving document chunking
- Using a better embedding model
- Using hybrid search
- Improving the query
- Using metadata filtering

```text
Better Retrieval
       ↓
More Relevant Documents
       ↓
Better Context
       ↓
Better LLM Answer
```

---

### 2. Use Reranking

A retriever may return documents that are semantically similar but not actually useful for answering the query.

A **reranker** can evaluate the retrieved candidates again and reorder them based on their relevance.

```text
User Query
    ↓
Initial Retrieval
    ↓
Candidate Documents
    ↓
Reranker
    ↓
Most Relevant Documents
    ↓
LLM
```

This helps remove or push less relevant documents away from the final context.

---

### 3. Apply a Relevance Threshold

Instead of sending every retrieved document to the LLM, only include documents whose relevance score is above a certain threshold.

For example:

```text
Document A → 0.92 → Include
Document B → 0.87 → Include
Document C → 0.43 → Exclude
Document D → 0.31 → Exclude
```

The threshold should be chosen through evaluation rather than arbitrarily.

---

### 4. Tune Top-k

The number of retrieved documents also affects context quality.

If `k` is too large:

```text
Too many documents
       ↓
More irrelevant information
       ↓
More noise in context
```

If `k` is too small:

```text
Too few documents
       ↓
Important information may be missed
```

Therefore, the value of `k` should be tested and tuned based on retrieval performance.

---

### 5. Use Metadata Filtering

Metadata filtering can restrict retrieval to documents that satisfy known conditions.

For example:

```text
Query:
"What is the refund policy?"

Filter:
category = "Billing"
language = "English"
```

This prevents documents from unrelated categories from entering the retrieval results.

---

### 6. Remove Duplicate Information

Multiple retrieved chunks may contain the same or very similar information.

Passing all of them to the LLM can waste context space and increase noise.

```text
Retrieved Chunks
       ↓
Remove duplicates / redundant chunks
       ↓
Relevant Context
       ↓
LLM
```

This is particularly useful when multiple chunks come from the same document.

---

### 7. Construct the Context Carefully

After retrieval, the system should build a clean context instead of blindly concatenating every result.

For example:

```text
Retrieved Documents
        ↓
Filter
        ↓
Rerank
        ↓
Remove Duplicates
        ↓
Select Top-k
        ↓
Construct Context
        ↓
LLM
```

The context should contain information that directly helps answer the user's question.

---

### 8. Instruct the LLM to Use the Retrieved Context

The prompt can clearly tell the LLM how to use the supplied context.

For example:

```text
Answer the question using the provided context.
If the answer cannot be found in the context, say that
the information is not available.
Do not rely on irrelevant context.
```

This helps encourage grounded responses, although prompt instructions alone cannot guarantee correct behavior.

---

### 9. Evaluate Retrieval Separately

If the LLM produces a poor answer, check whether the problem is actually retrieval.

For example:

```text
User Query
    ↓
Retrieved Documents
    ↓
Are they relevant?
   ↙       ↘
 Yes       No
 ↓          ↓
Check      Improve
LLM        Retrieval
```

Useful retrieval metrics include:

- Precision@k
- Recall@k
- Relevance of retrieved documents

This helps determine whether irrelevant context is entering the generation stage.

---

### Example

Suppose the user asks:

> **"What is the company's refund period?"**

The retriever returns:

```text
Chunk 1 → Refunds are available within 30 days.
Chunk 2 → Refund requests require an order ID.
Chunk 3 → The company launched a new product in 2025.
Chunk 4 → Contact support for billing issues.
```

Instead of sending all four chunks, the system can filter and rerank them:

```text
Relevant:
Chunk 1
Chunk 2
Chunk 4

Irrelevant:
Chunk 3
```

Then construct:

```text
Context:
Refunds are available within 30 days.
Refund requests require an order ID.
Contact support for billing issues.
```

This gives the LLM a cleaner context.

---

### Recommended Pipeline

```text
User Query
    ↓
Query Rewriting / Expansion
    ↓
Retrieval
    ↓
Metadata Filtering
    ↓
Reranking
    ↓
Relevance Threshold
    ↓
Remove Duplicates
    ↓
Tune Top-k
    ↓
Context Construction
    ↓
LLM
```

### Key Point

**The main goal is to prevent noisy information from reaching the LLM. This can be achieved through better retrieval, metadata filtering, reranking, relevance thresholds, top-k tuning, deduplication, and careful context construction.**

### Interview Answer

> **To prevent irrelevant retrieved information from confusing the LLM, I would first improve retrieval quality using better chunking, embeddings, query rewriting, or hybrid search. I would then use metadata filtering, reranking, relevance thresholds, deduplication, and an appropriate top-k value to select only useful documents. Finally, I would construct a clean context and instruct the LLM to answer using that context. I would evaluate retrieval separately using metrics such as Precision@k and Recall@k to verify that irrelevant information is actually being reduced.**


## 4. What is the role of the prompt template in RAG?

### Answer

A **prompt template** defines the structure of the prompt that is sent to the LLM in a RAG system.

It specifies **how the retrieved context, user question, and instructions should be combined** before being passed to the LLM.

Instead of creating a prompt manually for every query, a template provides a consistent structure.

---

### Basic RAG Prompt Structure

A typical prompt template may look like:

```text
Use the following context to answer the question.

Context:
{context}

Question:
{question}

Answer:
```

Here:

- `{context}` → Retrieved documents or chunks
- `{question}` → User's original query
- Instructions → Tell the LLM how to use the retrieved information
- `{answer}` → Where the generated response is expected

---

### How It Works in RAG

```text
User Query
    ↓
Retriever
    ↓
Retrieved Documents
    ↓
Context Construction
    ↓
Prompt Template
    ↓
Final Prompt
    ↓
LLM
    ↓
Answer
```

For example:

**User query:**

```text
What is RAG?
```

**Retrieved context:**

```text
RAG combines information retrieval with a language model.
It retrieves relevant information from an external knowledge source
and provides it to the LLM as context.
```

The prompt template combines them:

```text
Use the following context to answer the question.

Context:
RAG combines information retrieval with a language model.
It retrieves relevant information from an external knowledge source
and provides it to the LLM as context.

Question:
What is RAG?

Answer:
```

The completed prompt is then sent to the LLM.

---

### Why Is a Prompt Template Important?

#### 1. Provides Consistency

Every query follows the same structure.

```text
Context + Question + Instructions
```

This makes the RAG pipeline more predictable.

---

#### 2. Clearly Separates Context and Question

The template makes it clear to the LLM which information comes from the retrieved documents and which part is the user's question.

```text
Context:
{context}

Question:
{question}
```

---

#### 3. Controls LLM Behavior

Instructions can tell the LLM how to generate the answer.

For example:

```text
Answer the question using only the provided context.
If the answer is not present in the context, say that
the information is not available.
```

This encourages the model to stay grounded in the retrieved information.

---

#### 4. Makes the Pipeline Reusable

The same template can be used for thousands of different queries.

```text
Prompt Template
      ↓
Query 1 → Context 1 → LLM
Query 2 → Context 2 → LLM
Query 3 → Context 3 → LLM
```

Only the values of `{context}` and `{question}` change.

---

#### 5. Helps Control the Context

A prompt template can define how retrieved information should be presented.

For example:

```text
Context:
{context}

Instructions:
- Use the context to answer.
- Do not invent unsupported information.
- Keep the answer concise.

Question:
{question}
```

This provides the LLM with both the information and the instructions for using it.

---

### Example with Multiple Retrieved Documents

Suppose retrieval returns:

```text
Document 1:
RAG retrieves relevant information from an external knowledge source.

Document 2:
The retrieved information is provided to the LLM as context.
```

The template can combine them:

```text
You are an AI assistant.

Use the following retrieved context to answer the question.

Context:
{document_1}
{document_2}

Question:
{question}

Answer:
```

The placeholders are replaced at runtime.

---

### Prompt Template vs Context Construction

These two concepts are related but different.

| Context Construction | Prompt Template |
|---|---|
| Prepares retrieved information | Defines the structure of the final prompt |
| Selects, filters, orders, and combines chunks | Specifies where context and query are placed |
| Focuses on **what information** to provide | Focuses on **how to present it** |
| Happens before final prompt creation | Used to construct the final prompt |

```text
Retrieved Documents
       ↓
Context Construction
       ↓
Prepared Context
       ↓
Prompt Template
       ↓
Final Prompt
       ↓
LLM
```

### Key Point

**A prompt template provides a consistent structure for combining retrieved context, the user's question, and instructions before sending them to the LLM.**

### Interview Answer

> **The role of a prompt template in RAG is to define how the retrieved context, user query, and instructions are combined into the final prompt sent to the LLM. It provides consistency, clearly separates the retrieved context from the question, controls the model's behavior, and makes the RAG pipeline reusable across different queries.**


## 5. How can RAG reduce hallucination, and why does it not eliminate it completely?

### Answer

**RAG can reduce hallucination by providing the LLM with relevant external information as context.**

Instead of relying only on the knowledge stored in its parameters, the LLM can use the retrieved documents as a source of information when generating the answer.

However, RAG **does not completely eliminate hallucination** because the retrieval process and the generation process can both introduce errors.

---

### How RAG Reduces Hallucination

A standalone LLM mainly relies on the knowledge learned during training:

```text
User Query
    ↓
LLM
    ↓
Answer
```

If the required information is missing or uncertain, the model may generate an unsupported answer.

RAG adds an external knowledge source:

```text
User Query
    ↓
Retriever
    ↓
Relevant Documents
    ↓
Context
    ↓
LLM
    ↓
Grounded Answer
```

The retrieved documents provide information that the LLM can use to support its response.

---

### Example

Suppose a company has this policy:

```text
Customers can request a refund within 30 days of purchase.
```

The user asks:

> "How many days do I have to request a refund?"

A RAG system retrieves the relevant policy:

```text
Retrieved Context:
Customers can request a refund within 30 days of purchase.
```

The LLM can then generate:

```text
You can request a refund within 30 days of purchase.
```

The answer is grounded in the retrieved information rather than relying only on the model's internal knowledge.

---

### Why RAG Does Not Eliminate Hallucination

#### 1. Retrieval Can Return Irrelevant Documents

If the retriever finds incorrect or irrelevant information, the LLM may use it.

```text
User Query
    ↓
Poor Retrieval
    ↓
Irrelevant Context
    ↓
LLM
    ↓
Incorrect Answer
```

Therefore:

**Bad retrieval → Bad context → Potentially bad answer**

---

#### 2. Relevant Information May Not Be Retrieved

The correct document may exist in the knowledge base but fail to appear in the top-k results.

For example:

```text
Knowledge Base
    ↓
Correct Document exists
    ↓
Retriever misses it
    ↓
LLM does not receive it
    ↓
Potentially incorrect answer
```

This is a retrieval problem.

---

#### 3. The Retrieved Context May Be Incomplete

A retrieved chunk may contain only part of the required information.

For example:

```text
Chunk:
"Refunds are available within 30 days..."
```

But another part of the policy may contain important exceptions.

If the exception is not retrieved, the LLM may produce an incomplete answer.

---

#### 4. The LLM Can Still Misinterpret the Context

Even when the correct information is retrieved, the LLM may misunderstand or incorrectly combine the information.

```text
Correct Context
      ↓
LLM Interpretation
      ↓
Incorrect Answer
```

Therefore, retrieval does not guarantee correct generation.

---

#### 5. Poor Context Construction Can Add Noise

If too many irrelevant documents are passed to the LLM, the model may have difficulty identifying the useful information.

```text
Too Much Context
      ↓
Irrelevant Information
      ↓
More Noise
      ↓
Potentially Poor Answer
```

This is why filtering, reranking, deduplication, and appropriate top-k selection are important.

---

#### 6. The LLM May Still Generate Unsupported Information

Even when relevant context is provided, the LLM is still a generative model.

It may produce information that is not explicitly supported by the retrieved documents.

Therefore, RAG **reduces the likelihood of hallucination but cannot guarantee its absence**.

---

### RAG vs Hallucination

```text
                 RAG
                  ↓
       Retrieve External Knowledge
                  ↓
          Relevant Context
                  ↓
        Ground the LLM Response
                  ↓
       ↓ Hallucination Risk
                  
        BUT NOT ZERO
                  ↓
   Retrieval Errors + Missing Context
   + Context Noise + Generation Errors
                  ↓
          Possible Hallucination
```

### How to Further Reduce Hallucination

A RAG system can combine several techniques:

- Improve document chunking
- Use a suitable embedding model
- Improve retrieval quality
- Use hybrid search
- Use metadata filtering
- Apply reranking
- Remove irrelevant or duplicate context
- Use an appropriate top-k value
- Use clear prompt instructions
- Evaluate retrieval separately from generation
- Instruct the model to indicate when the answer is not available in the retrieved context

---

### Key Point

**RAG reduces hallucination by grounding the LLM with relevant external context, but it cannot eliminate hallucination because retrieval can fail, context can be incomplete or noisy, and the LLM can still misinterpret or generate unsupported information.**

### Interview Answer

> **RAG can reduce hallucination by retrieving relevant information from an external knowledge base and providing it to the LLM as context. This gives the model factual information to ground its response instead of relying only on its internal knowledge. However, RAG does not eliminate hallucination because the retriever may return irrelevant or incomplete documents, important information may be missed, the context may contain noise, or the LLM may still misinterpret the retrieved information or generate unsupported content.**
