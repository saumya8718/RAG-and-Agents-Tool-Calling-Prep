# 08. Production RAG & Troubleshooting

## 1. How would you design a production RAG architecture?

### Answer

A production RAG system should be designed as a complete pipeline that handles:

- Document ingestion and processing
- Embedding generation
- Vector/search storage
- Query processing
- Retrieval
- Reranking
- Context construction
- LLM generation
- Monitoring and evaluation

The architecture should also consider **scalability, latency, cost, reliability, and security**.

---

### 1. High-Level Architecture

A typical production RAG architecture can look like:

~~~text
                    ┌──────────────────┐
                    │   Data Sources   │
                    │ PDFs / Web / DB  │
                    └────────┬─────────┘
                             ↓
                  ┌─────────────────────┐
                  │ Document Ingestion  │
                  │ Cleaning + Chunking │
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │ Embedding Model     │
                  └──────────┬──────────┘
                             ↓
                  ┌─────────────────────┐
                  │ Vector DB / Search  │
                  │ + Metadata          │
                  └──────────┬──────────┘
                             │
                             │
User Query ──────→ Query Processing
                             ↓
                  ┌─────────────────────┐
                  │ Retrieval           │
                  │ Vector / Keyword /  │
                  │ Hybrid Search       │
                  └──────────┬──────────┘
                             ↓
                       Reranking
                             ↓
                  Context Construction
                             ↓
                  ┌─────────────────────┐
                  │        LLM          │
                  └──────────┬──────────┘
                             ↓
                         Response
                             ↓
                  Monitoring + Evaluation
~~~

---

### 2. Document Ingestion Pipeline

Documents first need to be prepared before they can be searched.

~~~text
Documents
    ↓
Text Extraction
    ↓
Cleaning
    ↓
Chunking
    ↓
Metadata
    ↓
Embeddings
    ↓
Vector Database
~~~

The ingestion pipeline should preserve useful metadata such as:

- Document ID
- Source
- Title
- Date
- Category
- Author
- Access permissions

This metadata can later be used for filtering during retrieval.

---

### 3. Query and Retrieval Pipeline

When a user sends a query:

~~~text
User Query
    ↓
Query Processing / Rewriting
    ↓
Metadata Filtering
    ↓
Vector / Keyword / Hybrid Search
    ↓
Top-k Documents
    ↓
Reranking
    ↓
Relevant Context
~~~

Using **hybrid search** can be useful when both semantic meaning and exact keyword matching are important.

Reranking can further improve the relevance of the retrieved chunks before they are sent to the LLM.

---

### 4. Context Construction and Generation

After retrieval:

~~~text
Retrieved Chunks
      ↓
Remove Irrelevant / Duplicate Chunks
      ↓
Order Relevant Information
      ↓
Build Context
      ↓
Prompt Template
      ↓
LLM
      ↓
Final Answer
~~~

The context should contain only useful information so that the LLM does not receive unnecessary noise.

The prompt should also instruct the LLM to use the retrieved context and avoid unsupported claims.

---

### 5. Scalability

For a production system with many users, individual components should be independently scalable.

For example:

~~~text
Users
  ↓
Load Balancer
  ↓
API Servers
  ↓
Retrieval Service
  ↓
Vector Database
  ↓
LLM Service
~~~

Multiple API/retrieval instances can be used to handle increased traffic.

Caching can also be used for:

- Frequently asked questions
- Frequently used embeddings
- Repeated retrieval results

---

### 6. Latency Optimization

A production RAG system should minimize unnecessary work.

Possible techniques include:

- Efficient vector indexes
- Appropriate top-k
- Metadata filtering
- Reranking only a limited candidate set
- Query/result caching
- Efficient embedding models
- Streaming LLM responses
- Parallel processing where appropriate

The goal is to maintain a balance between:

**Accuracy ↔ Latency ↔ Cost**

---

### 7. Monitoring and Evaluation

A production RAG system should continuously monitor both system performance and answer quality.

Useful metrics include:

#### System Metrics

- Request latency
- Retrieval latency
- LLM latency
- Error rate
- Throughput
- Token usage
- API cost

#### RAG Quality Metrics

- Precision@k
- Recall@k
- Retrieval relevance
- Faithfulness
- Answer relevance
- User feedback

This helps identify whether problems are occurring in retrieval, generation, or infrastructure.

---

### 8. Reliability and Security

A production architecture should also handle:

- API failures
- Timeouts
- Retries
- Rate limits
- Authentication
- Authorization
- Access-controlled documents
- Sensitive data
- Logging and auditing

For example, a user should only retrieve documents that they are authorized to access.

---

### Complete Production Flow

~~~text
                OFFLINE / INGESTION
                        
Documents
   ↓
Extract
   ↓
Clean
   ↓
Chunk
   ↓
Embed
   ↓
Vector DB + Metadata


                ONLINE / QUERY

User Query
   ↓
API Layer
   ↓
Query Processing
   ↓
Metadata Filtering
   ↓
Hybrid / Vector Retrieval
   ↓
Reranking
   ↓
Context Construction
   ↓
LLM
   ↓
Response
   ↓
Monitoring + Evaluation
~~~

---

### Key Point

A production RAG architecture should not be treated as just:

**Vector Database + LLM**

It should be a complete system covering:

**Ingestion → Indexing → Retrieval → Reranking → Context Construction → Generation → Monitoring**

while also addressing **scalability, latency, cost, reliability, and security**.

---

### Interview Answer

> **I would design a production RAG system with separate ingestion and query pipelines. The ingestion pipeline would extract, clean, and chunk documents, generate embeddings, and store them with metadata in a vector database or search system. The query pipeline would process the user query, apply metadata filtering and vector or hybrid retrieval, rerank the retrieved documents, construct the context, and pass it to the LLM. Around this pipeline, I would add caching, scalable API services, authentication and authorization, error handling, monitoring, and evaluation. I would monitor retrieval quality, faithfulness, answer relevance, latency, token usage, cost, and error rates to maintain the system in production.**


## 2. How would you handle document updates and re-indexing?

### Answer

In a production RAG system, documents can be **added, modified, or deleted** over time.

The vector database must be kept synchronized with the latest version of the source documents. This is done through an **update and re-indexing pipeline**.

---

### 1. Basic Update Flow

When a document changes:

~~~text
Updated Document
      ↓
Detect Change
      ↓
Extract & Clean Text
      ↓
Chunk Document
      ↓
Generate Embeddings
      ↓
Update Vector Database
      ↓
Updated Index
~~~

The important idea is that we should not blindly rebuild the entire vector database whenever one document changes.

---

### 2. Detect Which Documents Changed

First, identify whether a document has:

- Been newly added
- Been modified
- Been deleted

A document can be tracked using metadata such as:

~~~text
document_id
version
last_updated
content_hash
source
~~~

A **content hash** can be useful for detecting whether the actual document content has changed.

For example:

~~~text
Document A
Version: 3
Hash: abc123
        ↓
Document updated
        ↓
New Hash: xyz789
        ↓
Re-index required
~~~

---

### 3. Re-process the Changed Document

If the document has changed, process it again:

~~~text
Updated Document
      ↓
Text Extraction
      ↓
Cleaning
      ↓
Chunking
      ↓
Embedding Generation
~~~

The new chunks receive updated embeddings because their content may have changed.

---

### 4. Update the Vector Database

The old chunks associated with the document should be replaced or updated.

For example:

~~~text
Before:

Document A
 ├── Chunk A1
 ├── Chunk A2
 └── Chunk A3


Document A updated

After:

Document A
 ├── Chunk A1-new
 ├── Chunk A2-new
 └── Chunk A3-new
~~~

A stable `document_id` can be stored in the metadata of every chunk so that all chunks belonging to a document can be identified.

---

### 5. Handling New Documents

For a newly added document:

~~~text
New Document
    ↓
Extract Text
    ↓
Chunk
    ↓
Generate Embeddings
    ↓
Insert into Vector DB
~~~

There is no need to modify existing documents.

---

### 6. Handling Deleted Documents

If a source document is deleted, its corresponding chunks should also be removed from the vector database.

~~~text
Document Deleted
      ↓
Find chunks using document_id
      ↓
Delete corresponding vectors
      ↓
Update index
~~~

Otherwise, the RAG system could retrieve information from a document that no longer exists.

---

### 7. Incremental Re-indexing

For large production systems, **incremental re-indexing** is usually preferable to rebuilding everything.

Instead of:

~~~text
10,000 documents
      ↓
Re-process all 10,000
      ↓
Rebuild entire index
~~~

we can do:

~~~text
10,000 documents
      ↓
Detect changed documents
      ↓
Only 25 documents changed
      ↓
Re-process 25 documents
      ↓
Update their vectors
~~~

This reduces:

- Processing time
- Embedding computation
- Infrastructure cost
- Downtime

---

### 8. Full Re-indexing

Sometimes a full re-index is necessary.

For example, if:

- The embedding model changes
- Chunking strategy changes
- Major preprocessing changes
- Vector/index configuration changes

Then existing embeddings may no longer be compatible with the new pipeline.

A full re-index can then be performed:

~~~text
All Documents
      ↓
New Processing Pipeline
      ↓
New Chunks
      ↓
New Embeddings
      ↓
New Index
~~~

---

### 9. Versioning

Production systems should maintain versions of documents and indexes.

For example:

~~~text
Document Version 1
        ↓
Index Version 1

Document Version 2
        ↓
Index Version 2
~~~

This helps with:

- Tracking changes
- Debugging
- Reproducibility
- Rollbacks

A new index can be built separately and switched into production after validation.

---

### 10. Validate Before Switching

For important production systems, it is safer to build the updated index separately.

~~~text
Source Documents
      ↓
Build New Index
      ↓
Validate
      ↓
Quality Checks
      ↓
Switch Production Traffic
~~~

If something goes wrong, the previous index can remain available.

This avoids exposing users to a partially updated or incorrect index.

---

### Example

Suppose a company's refund policy changes:

~~~text
Old:
"Refunds are allowed within 30 days."

        ↓

Policy Updated

        ↓

New:
"Refunds are allowed within 60 days."
~~~

The system should:

1. Detect that the document changed.
2. Re-extract the document.
3. Re-chunk it.
4. Generate new embeddings.
5. Remove or replace the old chunks.
6. Insert the new chunks.
7. Validate retrieval.
8. Make the updated index available to users.

The RAG system can then retrieve the **60-day policy** instead of the outdated 30-day information.

---

### Recommended Production Strategy

~~~text
Document Store
      ↓
Change Detection
      ↓
┌───────────────┐
│ Added?        │ → Process + Index
│ Modified?     │ → Re-process + Update
│ Deleted?      │ → Remove from Index
└───────────────┘
      ↓
Validation
      ↓
Production Index
~~~

For large systems, use **incremental updates by default**, while using **full re-indexing when the underlying embedding or chunking pipeline changes significantly**.

---

### Key Point

Document updates should be handled through an automated ingestion pipeline that detects changes and **incrementally updates the affected chunks and embeddings**.

Full re-indexing should be reserved for cases where a major change, such as a new embedding model or chunking strategy, affects the entire index.

---

### Interview Answer

> **I would keep the source documents and vector index synchronized using an automated ingestion pipeline. I would detect added, modified, and deleted documents using document IDs, versions, timestamps, or content hashes. For modified documents, I would re-extract, clean, chunk, and embed them, then replace their old vectors in the vector database. Deleted documents would have their associated chunks removed. I would prefer incremental re-indexing because it is faster and cheaper, while using a full re-index when the embedding model or chunking strategy changes. For production, I would also version and validate new indexes before switching them into production.**


## 3. How would you reduce RAG latency?

### Answer

RAG latency is the total time taken from receiving the user's query to returning the final answer.

A RAG request typically has several stages:

~~~text
User Query
    ↓
Query Processing
    ↓
Embedding
    ↓
Retrieval
    ↓
Reranking
    ↓
Context Construction
    ↓
LLM Generation
    ↓
Response
~~~

To reduce latency, we should identify which stage is taking the most time and optimize that stage.

---

### 1. Optimize Retrieval

Use efficient vector indexes and approximate nearest-neighbor search instead of comparing the query with every vector.

For example:

- HNSW
- IVF

This reduces the amount of search required.

~~~text
Query
  ↓
Efficient Vector Index
  ↓
Fast Candidate Retrieval
~~~

---

### 2. Reduce the Number of Retrieved Documents

Do not retrieve an unnecessarily large number of chunks.

For example:

~~~text
Instead of:

Retrieve 50 chunks
       ↓
Rerank 50
       ↓
Send many chunks to LLM

Use:

Retrieve a smaller candidate set
       ↓
Rerank
       ↓
Select only relevant chunks
       ↓
LLM
~~~

A smaller context reduces both retrieval/reranking work and LLM processing.

However, `k` should be chosen based on evaluation because making it too small can reduce recall.

---

### 3. Use Metadata Filtering

If the query contains known constraints, apply metadata filters before or during retrieval.

For example:

~~~text
Query:
"What was the 2025 sales policy?"

Metadata Filter:
year = 2025
department = sales
        ↓
Search smaller set of documents
        ↓
Relevant chunks
~~~

This can reduce the search space and improve retrieval efficiency.

---

### 4. Optimize Reranking

Reranking can improve retrieval quality but adds additional latency.

Therefore:

- Retrieve a reasonable candidate set.
- Rerank only the most useful candidates.
- Avoid unnecessarily large reranking sets.
- Use a faster reranker when appropriate.

The goal is to balance:

**Retrieval Quality ↔ Reranking Latency**

---

### 5. Use Efficient Embedding Models

Query embedding is performed before vector retrieval.

Using an efficient embedding model can reduce embedding latency.

For frequently repeated queries, embeddings can also be cached.

~~~text
Query
  ↓
Check Cache
  ↓
If available → Reuse embedding
  ↓
Otherwise → Generate embedding
~~~

---

### 6. Use Caching

Caching is useful when the same or similar requests occur repeatedly.

Possible things to cache include:

- Query embeddings
- Retrieval results
- Frequently requested answers
- Other expensive intermediate results

Example:

~~~text
User Query
    ↓
Cache?
 ┌──┴──┐
Yes   No
 ↓     ↓
Use   Retrieve
Cache  + Generate
Result
~~~

Caching can significantly reduce repeated computation.

---

### 7. Reduce LLM Context Size

The LLM is given retrieved context along with the user's query.

A large amount of unnecessary context can increase processing time.

Therefore:

- Remove irrelevant chunks.
- Remove duplicate chunks.
- Use reranking.
- Select only useful information.
- Keep prompts concise.

~~~text
Many Retrieved Chunks
        ↓
Filter + Rerank + Deduplicate
        ↓
Small Relevant Context
        ↓
LLM
~~~

This can reduce both latency and token usage.

---

### 8. Use a Faster / Appropriate LLM

LLM generation can be one of the largest sources of latency.

Depending on the application, use a model that provides the required quality without unnecessary computational cost.

For simple queries, a smaller/faster model may be sufficient.

For complex queries, a more capable model may be required.

The choice should be based on:

- Answer quality
- Latency
- Cost
- Task complexity

---

### 9. Stream the Response

Instead of waiting for the complete answer before displaying anything, stream generated tokens to the user.

~~~text
LLM
 ↓
Token 1 → User
Token 2 → User
Token 3 → User
Token 4 → User
...
~~~

This may not reduce total generation time, but it **reduces perceived latency** because the user starts seeing the response earlier.

---

### 10. Parallelize Independent Operations

If multiple operations do not depend on each other, they can sometimes be executed in parallel.

For example:

~~~text
          ┌── Search A ──┐
Query ────┤              ├── Combine Results
          └── Search B ──┘
~~~

This can reduce overall waiting time compared with performing independent operations sequentially.

---

### 11. Measure Each Stage

Before optimizing, measure where the latency is coming from.

For example:

| Stage | Latency |
|---|---:|
| Query processing | 20 ms |
| Embedding | 30 ms |
| Retrieval | 50 ms |
| Reranking | 100 ms |
| Context construction | 20 ms |
| LLM generation | 800 ms |
| **Total** | **1020 ms** |

In this example, LLM generation is the largest contributor, so optimizing only the vector database may have little effect on total latency.

---

### Latency Optimization Flow

~~~text
Measure End-to-End Latency
          ↓
Identify Bottleneck
          ↓
┌─────────┼─────────┬─────────┐
↓         ↓         ↓         ↓
Retrieval Reranking Context    LLM
↓         ↓         ↓         ↓
Indexing  Smaller   Reduce    Faster/
Caching   Candidate  Context   appropriate
          Set        Size      Model
          ↓
        Re-measure
          ↓
      Evaluate Quality
~~~

Optimization should not reduce latency at the cost of unacceptable retrieval or answer quality.

---

### Key Point

To reduce RAG latency:

- Use efficient vector indexes.
- Reduce unnecessary retrieval and reranking.
- Apply metadata filtering.
- Use caching.
- Reduce context size.
- Use an appropriate LLM.
- Stream responses.
- Parallelize independent operations.
- Measure each stage and optimize the actual bottleneck.

The main goal is to balance:

**Accuracy ↔ Latency ↔ Cost**

---

### Interview Answer

> **I would first measure latency across each stage of the RAG pipeline to identify the bottleneck. For retrieval, I would use efficient ANN indexes, metadata filtering, appropriate top-k values, and caching. I would limit reranking to a reasonable candidate set and remove irrelevant or duplicate context before sending it to the LLM. On the generation side, I would use an appropriate model, keep the context and prompt concise, and use streaming to reduce perceived latency. I would also parallelize independent operations where possible and continuously evaluate the effect of these optimizations on both latency and answer quality.**


# 4. How would you reduce the cost of a RAG application?

### Answer

The cost of a RAG application mainly comes from:

- LLM API calls
- Input and output tokens
- Embedding generation
- Vector database/storage
- Retrieval and reranking
- Infrastructure and network usage

The goal is to reduce unnecessary computation while maintaining answer quality.

### 1. Reduce the Number of LLM Tokens

One of the biggest costs is sending large amounts of context to the LLM.

Instead of sending many retrieved chunks:

~~~text
Many Retrieved Chunks
        ↓
Filter + Rerank + Deduplicate
        ↓
Small Relevant Context
        ↓
LLM
~~~

Use only the most relevant information.

This reduces:

- Input tokens
- LLM cost
- Latency
- Noise in the context

### 2. Optimize Top-k Retrieval

If we retrieve too many documents, unnecessary information is sent to the LLM.

For example:

```text
Top-k = 20 → many chunks → high token usage
Top-k = 5  → fewer relevant chunks → lower cost
```

However, `k` should not simply be made as small as possible. It should be chosen based on retrieval quality and evaluation.

### 3. Use Smaller / Cheaper Models Where Appropriate

Not every task requires the most expensive LLM.

A smaller model can be used for:

- Query rewriting
- Query classification
- Simple summarization
- Metadata extraction
- Other lightweight tasks

A more capable model can be reserved for complex generation tasks.

### 4. Cache Results

Frequently repeated queries can be cached.

```text
User Query
    ↓
Check Cache
   / \
 Hit  Miss
 ↓      ↓
Answer  RAG Pipeline
          ↓
        Answer
          ↓
       Store in Cache
```

Caching can reduce repeated:

- Embedding generation
- Retrieval operations
- LLM calls

### 5. Cache Query Embeddings

If the same query is repeated, its embedding does not need to be generated again.

```text
Query
  ↓
Check Embedding Cache
  ↓
Existing embedding?
  ├── Yes → Reuse
  └── No  → Generate → Store
```

### 6. Reduce Unnecessary Reranking

Rerankers improve retrieval quality but add computation and cost.

Instead of reranking hundreds of documents:

```text
Retriever
   ↓
Top 20 candidates
   ↓
Reranker
   ↓
Top 5 documents
```

Retrieve a reasonable candidate set first and rerank only those candidates.

### 7. Optimize Document Processing

During ingestion, avoid repeatedly processing unchanged documents.

Use:

- Document IDs
- Versions
- Timestamps
- Content hashes

Only changed documents should normally be reprocessed and re-embedded.

### 8. Use Efficient Vector Search

Efficient indexes such as HNSW or IVF can reduce retrieval computation compared with exhaustive search.

Metadata filtering can also reduce the search space.

### 9. Monitor Token Usage and Cost

Track:

- Input tokens
- Output tokens
- Embedding usage
- Number of LLM calls
- Number of retrieval calls
- Cost per request
- Cost per user/query

This helps identify expensive parts of the pipeline.

### Cost Optimization Flow

~~~text
Measure Cost
     ↓
Find Expensive Components
     ↓
Reduce Context Size
     ↓
Optimize Top-k
     ↓
Cache Repeated Work
     ↓
Use Appropriate Models
     ↓
Optimize Retrieval/Reranking
     ↓
Monitor Cost Again
~~~

### Key Point

The main idea is **not to blindly use cheaper models**. Reduce unnecessary computation while preserving retrieval and answer quality.

### Interview Answer

> **I would reduce RAG cost by minimizing unnecessary LLM tokens, optimizing top-k retrieval, using smaller models for simple tasks, caching repeated queries and embeddings, limiting expensive reranking, and incrementally processing only changed documents. I would also optimize vector search and continuously monitor token usage, LLM calls, latency, and cost per request. The goal is to reduce cost without significantly affecting retrieval and answer quality.**

## 5. How would you monitor a RAG system in production?

### Answer

A production RAG system should be monitored at both the **system level** and the **RAG quality level**.

There are two major categories:

```text
Production Monitoring
       /       \
      /         \
System Metrics   RAG Quality Metrics
```

### 1. Monitor System Metrics

### Latency

Measure the latency of individual stages:

- Query processing latency
- Embedding latency
- Retrieval latency
- Reranking latency
- LLM generation latency
- End-to-end response latency

Example:

```text
Query Processing → 20 ms
Retrieval        → 80 ms
Reranking        → 100 ms
LLM              → 900 ms
-------------------------
Total            → 1100 ms
```

This helps identify bottlenecks.

### Error Rate

Monitor:

- API failures
- Vector database failures
- LLM failures
- Timeout errors
- Embedding errors
- Invalid requests

### Throughput

Track:

- Requests per second
- Number of queries
- Concurrent users
- Requests over time

### Token Usage

Track:

- Input tokens
- Output tokens
- Total tokens

This is useful for both cost monitoring and detecting unexpectedly large contexts.

### Cost

Monitor:

- Cost per request
- Cost per user
- LLM cost
- Embedding cost
- Infrastructure cost

---

### 2. Monitor Retrieval Quality

The retrieval stage should be monitored separately from generation.

Useful metrics include:

- Precision@k
- Recall@k
- Retrieval relevance
- Number of retrieved documents
- Similarity scores

For example:

```text
Query
  ↓
Retrieved Documents
  ↓
Are they relevant?
  ↓
Precision@k / Recall@k
```

If retrieval quality decreases, the problem may be related to:

- Chunking
- Embeddings
- Query formulation
- Vector index
- Metadata filtering
- Retrieval strategy

---

### 3. Monitor Generation Quality

Monitor whether the generated answer is:

### Faithful

Does the answer stay supported by the retrieved context?

### Relevant

Does the answer actually address the user's question?

### Correct / Useful

Does the answer provide the required information correctly?

User feedback can also help identify poor answers.

---

### 4. Monitor the RAG Pipeline End-to-End

A production monitoring system should make it possible to trace a request through the entire pipeline.

```text
User Query
    ↓
Query Processing
    ↓
Embedding
    ↓
Retrieval
    ↓
Reranking
    ↓
Context Construction
    ↓
LLM
    ↓
Final Answer
```

For each request, useful information to log or trace includes:

- Query
- Retrieved document IDs
- Retrieval scores
- Number of retrieved chunks
- Reranking results
- Final context size
- Model used
- Token usage
- Latency
- Errors
- Final response
- User feedback

Sensitive information should be handled according to the application's security and privacy requirements.

---

### 5. Set Alerts

Monitoring becomes useful when abnormal behavior generates alerts.

Examples:

```text
Retrieval latency > threshold
        ↓
       Alert

LLM error rate > threshold
        ↓
       Alert

Recall@k decreases
        ↓
       Alert

Cost per request increases
        ↓
       Alert
```

### Example Monitoring Dashboard

| Category | Metrics |
|---|---|
| Latency | Retrieval, reranking, LLM, total latency |
| Reliability | Error rate, timeout rate |
| Retrieval | Precision@k, Recall@k, relevance |
| Generation | Faithfulness, answer relevance |
| Usage | Requests, tokens |
| Cost | Cost per request, total cost |
| User feedback | Ratings, corrections, complaints |

### Key Point

Production monitoring should cover **both infrastructure performance and RAG quality**.

### Interview Answer

> **I would monitor a production RAG system at two levels: system metrics and RAG quality metrics. System metrics include latency, throughput, errors, token usage, and cost. RAG-specific metrics include Precision@k, Recall@k, retrieval relevance, faithfulness, and answer relevance. I would also trace individual requests through retrieval, reranking, context construction, and generation so that retrieval and generation problems can be diagnosed separately.**

## 6. Your RAG application retrieves the correct document but produces the wrong answer. How would you debug it?

### Answer

If the correct document is retrieved but the final answer is wrong, the problem is likely **after the retrieval stage**.

However, we should systematically check each stage rather than immediately assuming the LLM is the problem.

## Step 1: Verify the Retrieved Document

First check whether the retrieved document actually contains the information required to answer the question.

```text
User Query
    ↓
Retrieved Document
    ↓
Does it contain the required information?
```

If **No**, retrieval is still a problem.

If **Yes**, continue debugging the generation pipeline.

---

### Step 2: Check the Retrieved Chunk

The correct document may have been retrieved, but the relevant information might not be present in the selected chunk.

For example:

```text
Document
 ├── Chunk 1
 ├── Chunk 2  ← contains answer
 ├── Chunk 3
 └── Chunk 4
```

If the document is correct but Chunk 2 was not included in the final context, the LLM may not have enough information.

Check:

- Chunk boundaries
- Chunk size
- Chunk overlap
- Whether the relevant section was retrieved
- Whether the chunk was truncated

---

### Step 3: Inspect the Final Context

Do not only inspect the vector database result.

Check exactly what was passed to the LLM.

```text
Retrieved Chunks
      ↓
Filtering
      ↓
Reranking
      ↓
Deduplication
      ↓
Context Construction
      ↓
Final LLM Context
```

The relevant information may have been removed during context construction.

---

### Step 4: Check for Irrelevant or Conflicting Context

The LLM may receive the correct information along with:

- Irrelevant chunks
- Duplicate chunks
- Outdated information
- Conflicting information

For example:

```text
Correct information
        +
Old information
        +
Irrelevant information
        ↓
      LLM
        ↓
Wrong answer
```

Check document versions, metadata, reranking, and context ordering.

---

### Step 5: Check the Prompt Template

Inspect the prompt sent to the LLM.

A simple RAG prompt could be:

~~~text
Use the following context to answer the question.

Context:
{context}

Question:
{question}

Answer:
~~~

Check whether:

- The context is clearly separated
- The question is clearly stated
- Instructions are clear
- The model is told to use the provided context
- The model is instructed not to invent unsupported information

---

### Step 6: Check Context Length

If too much context is provided, important information may become harder for the model to use.

Reduce unnecessary context using:

- Better top-k
- Reranking
- Deduplication
- Relevance thresholds
- Better chunk selection

---

### Step 7: Check the LLM Output

If the correct information is clearly present in the final context and the prompt is correct, but the model still produces an incorrect answer, the problem is more likely related to the **generation stage**.

Possible causes include:

- Model misunderstanding
- Poor prompt
- Conflicting context
- Unsupported inference
- Model limitations

---

## Debugging Flow

~~~text
Correct Document Retrieved
          ↓
Does the required information exist?
       /       \
     No         Yes
     ↓           ↓
Retrieval    Check Chunk
Problem          ↓
             Check Final Context
                    ↓
          Relevant information present?
               /           \
             No             Yes
             ↓               ↓
      Context/Retrieval   Check Prompt
          Problem             ↓
                          Check Context
                             Size
                              ↓
                         Check LLM Output
                              ↓
                       Generation Problem
~~~

### Key Point

Do not assume that retrieving the correct **document** means the correct **context** was given to the LLM. Check the complete path from retrieved document → selected chunks → final context → prompt → LLM output.

### Interview Answer

> **I would first verify whether the retrieved document actually contains the information required to answer the query. Then I would inspect the selected chunks and the exact context passed to the LLM. I would check for missing information, truncation, irrelevant or conflicting chunks, duplicate content, and context ordering. Next, I would inspect the prompt template and context size. If the required information is clearly present in the final context and the prompt is correct but the answer is still wrong, I would investigate the generation stage and model behavior.**

## 7. Your RAG application retrieves irrelevant documents. How would you systematically diagnose and fix it?

### Answer

If irrelevant documents are being retrieved, the problem is mainly in the **retrieval pipeline**.

The best approach is to diagnose each stage systematically rather than changing everything at once.

## Step 1: Inspect the User Query

First check whether the query itself is clear.

For example:

```text
"How can I make RAG faster?"
```

This may be rewritten as:

```text
"What techniques can reduce the latency of a RAG application?"
```

If queries are ambiguous or conversational, consider:

- Query rewriting
- Query expansion
- Multi-query retrieval

---

## Step 2: Check Document Quality

Poor-quality documents can lead to poor retrieval.

Check for:

- Duplicate documents
- Outdated documents
- Incorrect text extraction
- Missing content
- Unnecessary boilerplate
- Poorly structured documents

Clean the data before indexing.

---

## Step 3: Check Chunking

Bad chunking can cause irrelevant retrieval.

Check:

- Chunk size
- Chunk overlap
- Chunk boundaries
- Whether chunks preserve enough context

For example:

```text
Bad Chunk
────────────
A topic is split in the middle
        ↓
Embedding loses useful context
        ↓
Poor retrieval
```

Use an appropriate chunking strategy for the dataset.

---

## Step 4: Check the Embedding Model

The embedding model determines how semantic similarity is represented.

Check whether:

- The model is suitable for the domain
- The query and documents use the same embedding space
- The embedding model handles the language/domain properly
- The model captures the required semantic relationships

If necessary, evaluate another embedding model.

---

## Step 5: Check Retrieval Strategy

Determine whether semantic search alone is sufficient.

For example, a technical query containing an exact error code may benefit from keyword search.

```text
Semantic Search
       +
Keyword Search
       ↓
Hybrid Search
       ↓
Better Candidate Set
```

Hybrid search can help when both exact terms and semantic meaning are important.

---

## Step 6: Check Metadata Filtering

If documents contain useful metadata, use filters to reduce irrelevant results.

For example:

```text
Query: "What is the refund policy?"

Metadata:
Department = Customer Support
Document Type = Policy
Language = English
```

Filtering can reduce the search space and improve relevance.

---

## Step 7: Check Top-k

If `k` is too large, many irrelevant documents may be returned.

```text
Top-k = 20
→ relevant + many irrelevant chunks

Top-k = 5
→ smaller candidate set
```

But reducing `k` too much can reduce recall.

Therefore, choose `k` using evaluation rather than guessing.

---

## Step 8: Add Reranking

A common architecture is:

```text
Query
  ↓
Initial Retriever
  ↓
Top 20 Candidates
  ↓
Reranker
  ↓
Top 5 Relevant Documents
  ↓
LLM
```

The initial retriever provides candidates quickly, while the reranker performs a more detailed relevance check.

---

## Step 9: Remove Duplicates and Low-Quality Results

Even relevant documents can contain:

- Duplicate chunks
- Nearly identical chunks
- Very short/incomplete chunks
- Low-quality content

Use deduplication and relevance thresholds before constructing the final context.

---

## Step 10: Evaluate the Retrieval System

Use a test dataset containing:

```text
Question
   ↓
Expected Relevant Documents
   ↓
Retrieved Documents
   ↓
Compare
```

Useful metrics include:

- Precision@k
- Recall@k
- Retrieval relevance

### Systematic Debugging Flow

~~~text
Irrelevant Documents Retrieved
            ↓
       Check Query
            ↓
      Check Document Quality
            ↓
        Check Chunking
            ↓
     Check Embeddings
            ↓
    Check Retrieval Strategy
            ↓
     Check Metadata Filters
            ↓
        Tune Top-k
            ↓
        Add Reranking
            ↓
 Deduplicate / Relevance Threshold
            ↓
        Evaluate Again
~~~

### Example

Suppose a user asks:

```text
"What is the refund period for a product?"
```

But the system retrieves:

```text
1. Shipping policy
2. Payment policy
3. Refund policy
4. Product catalog
```

Possible fixes:

```text
Query
 ↓
Metadata filter → Policy documents
 ↓
Hybrid retrieval
 ↓
Reranking
 ↓
Refund policy chunks
 ↓
LLM
```

This reduces irrelevant context before generation.

### Key Point

Do not immediately change the LLM when retrieval is poor. First diagnose:

**query → documents → chunking → embeddings → retrieval → filtering → top-k → reranking**

Then evaluate whether the retrieved results actually became more relevant.

### Interview Answer

> **I would systematically diagnose irrelevant retrieval by checking the query, document quality, chunking strategy, embedding model, retrieval method, metadata filters, and top-k value. I would consider query rewriting, query expansion, hybrid search, and reranking where appropriate. I would also remove duplicate or low-quality chunks and evaluate the retriever using Precision@k, Recall@k, and retrieval relevance. The key is to isolate the retrieval stage and improve one component at a time rather than changing the entire RAG pipeline blindly.**
