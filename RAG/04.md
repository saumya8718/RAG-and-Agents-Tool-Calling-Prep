# 04. Vector Databases & Retrieval 

## 1. What is a vector database?

### Answer

A **vector database** is a database designed to store and efficiently search **vector embeddings**.

In RAG, documents are converted into embeddings and stored in a vector database. When a user asks a question, the query is also converted into an embedding. The vector database then searches for the most similar vectors and returns the corresponding document chunks.

---

### 1. Why Do We Need a Vector Database?

Traditional databases are mainly designed for structured data and exact queries.

For example:

~~~text
SQL Database

"Find users where age = 25"
        ↓
Exact / structured matching
~~~

RAG needs a different type of search:

~~~text
User Query
"What is the purpose of RAG?"
        ↓
Query Embedding
        ↓
Find semantically similar documents
        ↓
Relevant Chunks
~~~

A vector database is designed to perform this type of **similarity search** efficiently.

---

### 2. How Does a Vector Database Work in RAG?

During document ingestion:

~~~text
Documents
    ↓
Chunking
    ↓
Embedding Model
    ↓
Vector Embeddings
    ↓
Vector Database
~~~

The vector database stores the embeddings along with the associated information, such as:

~~~text
Vector
   +
Original Text / Chunk
   +
Metadata
~~~

When a user asks a question:

~~~text
User Query
    ↓
Embedding Model
    ↓
Query Vector
    ↓
Vector Database
    ↓
Similarity Search
    ↓
Top-k Relevant Chunks
    ↓
LLM
    ↓
Answer
~~~

---

### 3. Example

Suppose we have three document chunks:

~~~text
Chunk 1 → Information about RAG
Chunk 2 → Information about Python
Chunk 3 → Information about databases
~~~

Their embeddings are stored in the vector database.

The user asks:

~~~text
"What is Retrieval-Augmented Generation?"
~~~

The query is converted into a vector.

The vector database compares the query vector with the stored vectors.

~~~text
Query Vector
      ↓
Vector Database
      ↓
┌──────────────────────┐
│ Chunk 1 → High       │
│ Chunk 2 → Low        │
│ Chunk 3 → Low        │
└──────────────────────┘
      ↓
Relevant Chunk
~~~

The relevant chunk is then passed to the LLM as context.

---

### 4. What Does a Vector Database Store?

A vector database can store:

- **Embedding vectors**
- Original document chunks or references to them
- **Metadata**
- IDs or other information needed to retrieve the source

For example:

~~~text
ID: 101

Vector:
[0.21, -0.43, 0.78, ...]

Text:
"RAG combines retrieval with generation."

Metadata:
{
    "source": "rag_notes.pdf",
    "page": 5
}
~~~

The metadata can also be used to filter search results.

---

### 5. Similarity Search

The main operation performed by a vector database is **similarity search**.

It compares the query vector with stored vectors using a similarity or distance measure.

Common measures include:

- Cosine similarity
- Euclidean distance
- Other vector distance metrics

~~~text
Query Vector
      ↓
Similarity Search
      ↓
Compare with stored vectors
      ↓
Rank results
      ↓
Top-k results
~~~

---

### 6. Vector Database in the RAG Architecture

A simplified RAG architecture looks like:

~~~text
             DOCUMENTS
                 ↓
              Chunking
                 ↓
          Embedding Model
                 ↓
          Vector Database
                 ↑
                 │
           Similarity Search
                 ↑
                 │
             User Query
                 ↓
          Query Embedding
                 ↓
          Relevant Chunks
                 ↓
                LLM
                 ↓
              Answer
~~~

The vector database therefore acts as the **retrieval layer** between the user's query and the LLM.

---

### Key Point

> **A vector database is a database optimized for storing, indexing, and searching vector embeddings. In RAG, it stores document embeddings and retrieves the most semantically relevant document chunks by comparing them with the embedding of the user's query.**

### Interview Answer

> **A vector database is a database designed to store and efficiently search high-dimensional vector embeddings. In a RAG system, document chunks are converted into embeddings and stored in the vector database. When a user asks a question, the query is converted into an embedding, and the vector database performs a similarity search to retrieve the most relevant chunks. These chunks are then provided to the LLM as context for generating the answer.**


## 2. How is a vector database different from a traditional relational database?

### Answer

A **vector database** is designed to store and search **vector embeddings**, while a **traditional relational database** is designed to store structured data in **tables, rows, and columns** and query it using conditions and relationships.

The main difference is the **type of data and type of search** they are optimized for.

---

### 1. Traditional Relational Database

A relational database stores structured data in tables.

For example:

~~~text
Users Table

+----+--------+-----+
| ID | Name   | Age |
+----+--------+-----+
| 1  | Rahul  | 22  |
| 2  | Priya  | 25  |
+----+--------+-----+
~~~

We can query it using SQL:

~~~sql
SELECT * FROM Users
WHERE Age = 25;
~~~

This performs **exact or condition-based matching**.

---

### 2. Vector Database

A vector database stores **high-dimensional vectors**, usually generated by an embedding model.

For example:

~~~text
Document:
"RAG combines retrieval with generation."

        ↓
Embedding Model

Vector:
[0.21, -0.43, 0.78, 0.12, ...]
~~~

The vector database can then search for vectors that are **similar** to a query vector.

~~~text
User Query
"What is Retrieval-Augmented Generation?"
        ↓
Query Embedding
        ↓
Vector Database
        ↓
Similarity Search
        ↓
Most Similar Document Vectors
~~~

This is called **semantic similarity search**.

---

### 3. Key Differences

| Feature | Relational Database | Vector Database |
|---|---|---|
| Main data | Structured data | Vector embeddings |
| Storage | Tables, rows, columns | Vectors + metadata/documents |
| Query style | Exact/condition-based | Similarity-based |
| Common query | `WHERE age = 25` | Find vectors closest to query vector |
| Main purpose | Structured data management | Semantic/vector search |
| Typical use | Banking, users, transactions | RAG, semantic search, recommendations |
| Search method | SQL and database indexes | Vector similarity / nearest-neighbor search |

---

### 4. Example in RAG

Suppose we have thousands of documents.

A relational database could store:

~~~text
Document ID
Document Name
Author
Date
Category
```

For example:

~~~text
ID: 101
Name: RAG_Notes.pdf
Category: AI
Date: 2026
~~~

But storing metadata alone does not allow us to efficiently find a document that is **semantically similar** to a user's question.

A vector database stores the embedding of the document:

~~~text
Document
   ↓
Chunking
   ↓
Embedding Model
   ↓
Vector
   ↓
Vector Database
~~~

When the user asks:

~~~text
"How does RAG retrieve information?"
~~~

the query is converted into a vector and compared with stored vectors.

~~~text
Query Vector
      ↓
Similarity Search
      ↓
Similar Document Vectors
      ↓
Relevant Chunks
      ↓
LLM
~~~

This makes vector databases particularly useful for the **retrieval stage of RAG**.

---

### 5. Can a Relational Database Store Vectors?

Yes.

Some relational databases can store vectors and support vector similarity search through extensions or built-in capabilities.

However, the important distinction is:

> A traditional relational database is primarily designed around structured relational data, while a vector database is specifically optimized for vector storage, indexing, and similarity search.

Therefore, the choice depends on the application and its requirements.

---

### 6. Simple Analogy

Think of a relational database as a system where you ask:

~~~text
"Give me all products where price < 1000."
~~~

A vector database allows you to ask:

~~~text
"Find products that are similar to this product."
~~~

The first is based mainly on **structured conditions**.

The second is based on **similarity between vectors**.

---

### Key Point

> **A relational database is mainly optimized for structured data and exact or condition-based queries, whereas a vector database is optimized for storing embeddings and performing similarity searches. In RAG, vector databases are used to retrieve document chunks that are semantically similar to the user's query.**

### Interview Answer

> **A traditional relational database stores structured data in tables and is mainly queried using SQL conditions and relationships. A vector database stores high-dimensional vector embeddings and is optimized for similarity search. In RAG, documents are converted into embeddings and stored in a vector database. When a user asks a question, the query is also converted into an embedding, and the vector database retrieves the most similar document chunks.**


## 3. What is an index in a vector database?

### Answer

An **index** in a vector database is a data structure that helps the database **search and retrieve similar vectors efficiently**.

Without an index, the database may need to compare the query vector with **every stored vector**, which becomes very slow when millions of vectors are stored.

---

### 1. Why Do We Need an Index?

Suppose a vector database contains:

~~~text
10 vectors
    ↓
Compare query with 10 vectors
    ↓
Easy and fast
~~~

But a real RAG application may contain:

~~~text
10 million vectors
    ↓
Compare query with every vector
    ↓
Very expensive and slow
~~~

An index organizes the vectors in a way that allows the database to **quickly find likely nearest vectors** instead of checking every vector.

---

### 2. How Does a Vector Index Work?

During indexing:

~~~text
Document Chunks
      ↓
Embedding Model
      ↓
Vector Embeddings
      ↓
Build Vector Index
      ↓
Vector Database
~~~

When a user sends a query:

~~~text
User Query
     ↓
Query Embedding
     ↓
Vector Index
     ↓
Find Similar Vectors
     ↓
Top-k Results
~~~

The index therefore makes **similarity search faster and more scalable**.

---

### 3. Without an Index vs With an Index

#### Without an Index

The database may perform a brute-force comparison:

~~~text
Query Vector
     ↓
Compare with Vector 1
Compare with Vector 2
Compare with Vector 3
Compare with Vector 4
...
Compare with Vector N
     ↓
Find closest vectors
~~~

This can become expensive for a very large dataset.

#### With an Index

The index helps narrow down the search:

~~~text
Query Vector
     ↓
Vector Index
     ↓
Likely Similar Vectors
     ↓
Similarity Calculation
     ↓
Top-k Results
~~~

This significantly reduces the amount of search required.

---

### 4. Common Types of Vector Indexes

Different vector databases provide different indexing methods.

Two important approaches are:

#### HNSW

**HNSW (Hierarchical Navigable Small World)** builds a graph structure connecting vectors that are close to each other.

~~~text
Query
  ↓
Navigate through graph
  ↓
Nearby vectors
  ↓
Top-k results
~~~

It is commonly used for fast approximate nearest-neighbor search.

#### IVF

**IVF (Inverted File Index)** divides vectors into groups or clusters.

~~~text
All Vectors
     ↓
┌─────────┬─────────┬─────────┐
│ Cluster │ Cluster │ Cluster │
│    1    │    2    │    3    │
└─────────┴─────────┴─────────┘
             ↓
       Query searches
       relevant clusters
             ↓
          Top-k results
~~~

Instead of searching every vector, the system first identifies relevant clusters and searches within them.

---

### 5. Index and Approximate Nearest-Neighbor Search

Vector indexes are commonly used for **Approximate Nearest-Neighbor (ANN) search**.

The goal is:

~~~text
Find vectors that are very close
to the query vector
```

without necessarily checking every vector in the database.

This creates a trade-off:

~~~text
More exhaustive search
        ↓
Higher search accuracy
        ↓
Higher computation cost

More approximate search
        ↓
Faster retrieval
        ↓
Potentially slightly less accurate
~~~

The appropriate choice depends on the application's requirements.

---

### 6. Example in RAG

Suppose a RAG system contains **1 million document chunks**.

Each chunk is converted into an embedding:

~~~text
1,000,000 document chunks
          ↓
Embedding Model
          ↓
1,000,000 vectors
          ↓
Vector Index
~~~

When the user asks:

~~~text
"What are the benefits of RAG?"
~~~

the query is converted into a vector.

The index helps find the most relevant vectors efficiently:

~~~text
User Query
    ↓
Query Embedding
    ↓
Vector Index
    ↓
Similar Vectors
    ↓
Top-k Document Chunks
    ↓
LLM
    ↓
Answer
~~~

Without an efficient index, searching through a very large collection of vectors can become slow.

---

### 7. Important Trade-off

A vector index is mainly about balancing:

- **Search speed**
- **Retrieval accuracy**
- **Memory usage**
- **Indexing/building cost**

For example, an index configuration that gives very fast searches may sometimes sacrifice some retrieval accuracy compared with exhaustive search.

Therefore, index selection is an important part of designing a production RAG system.

---

### Key Point

> **A vector index is a data structure used to organize vectors so that similarity searches can be performed efficiently. It avoids the need to compare a query against every stored vector and is especially important for large-scale RAG systems. HNSW and IVF are examples of approaches used for efficient approximate nearest-neighbor search.**

### Interview Answer

> **An index in a vector database is a data structure that makes similarity search over embeddings faster and more scalable. Without an index, the system may need to compare a query vector with every stored vector. Vector indexes such as HNSW and IVF organize the vectors so that the database can search a smaller set of likely candidates and retrieve the top-k similar vectors efficiently.**


## 4. What are approximate nearest-neighbor search methods?

### Answer

**Approximate Nearest-Neighbor (ANN) search methods** are techniques used to find vectors that are **very similar to a query vector without comparing the query with every vector in the database**.

They are important in RAG because vector databases may contain **millions or billions of embeddings**. Searching every vector would be expensive and slow.

ANN methods trade a small amount of search accuracy for a **large improvement in speed and scalability**.

---

### 1. What is Nearest-Neighbor Search?

Suppose we have a query vector:

~~~text
Query Vector
[0.21, 0.43, 0.78, ...]
~~~

and many vectors stored in a database.

The goal is to find the vectors that are closest to the query according to a similarity or distance measure.

~~~text
Query Vector
      ↓
Compare with stored vectors
      ↓
Calculate similarity / distance
      ↓
Find closest vectors
      ↓
Top-k results
~~~

These closest vectors are called **nearest neighbors**.

---

### 2. Exact vs Approximate Search

#### Exact Nearest-Neighbor Search

In exact search, the system compares the query with **every stored vector**.

~~~text
Query
  ↓
Vector 1
Vector 2
Vector 3
Vector 4
...
Vector N
  ↓
Find exact nearest neighbors
~~~

This can become slow when the database contains millions of vectors.

#### Approximate Nearest-Neighbor Search

ANN methods reduce the amount of searching.

~~~text
Query
  ↓
ANN Index
  ↓
Likely Similar Candidates
  ↓
Similarity Search
  ↓
Top-k Results
~~~

The system does not necessarily examine every vector.

This makes retrieval much faster.

---

### 3. Why Is ANN Important in RAG?

A production RAG system may contain a very large number of document chunks.

For example:

~~~text
10 million document chunks
        ↓
10 million embeddings
        ↓
Vector Database
~~~

If every query required comparison with all 10 million vectors, retrieval could become expensive.

ANN methods allow the system to efficiently find relevant vectors:

~~~text
User Query
     ↓
Query Embedding
     ↓
ANN Search
     ↓
Relevant Vectors
     ↓
Relevant Document Chunks
     ↓
LLM
     ↓
Answer
~~~

Therefore, ANN is an important technique for **scalable vector retrieval**.

---

### 4. Common ANN Methods

Some important approaches include:

- **HNSW (Hierarchical Navigable Small World)**
- **IVF (Inverted File Index)**

These are specifically relevant to vector databases and are commonly used to speed up nearest-neighbor search.

---

### 5. HNSW

**HNSW** organizes vectors into a graph structure.

Nearby vectors are connected, allowing the search to navigate through the graph toward vectors similar to the query.

~~~text
             Query
               ↓
             Node A
            /      \
         Node B    Node C
          /          \
       Node D       Node E
          \          /
           Similar Vectors
~~~

Instead of comparing against every vector, the search follows promising paths through the graph.

**Main idea:**

> Use a graph structure to quickly navigate toward nearby vectors.

---

### 6. IVF

**IVF (Inverted File Index)** divides vectors into different groups or clusters.

For example:

~~~text
All Vectors
     ↓
 ┌────────┬────────┬────────┐
 │Cluster1│Cluster2│Cluster3│
 └────────┴────────┴────────┘
              ↓
       Query identifies
       relevant cluster(s)
              ↓
       Search those vectors
              ↓
          Top-k results
~~~

Instead of searching the entire database, the system first identifies the most relevant clusters and searches within them.

**Main idea:**

> Divide vectors into groups and search only the most relevant groups.

---

### 7. ANN Trade-off

ANN search introduces a trade-off between **speed and accuracy**.

~~~text
Exact Search
     ↓
Higher accuracy
     ↓
More computation
     ↓
Slower for very large datasets
~~~

Compared with:

~~~text
ANN Search
     ↓
Much faster
     ↓
Less computation
     ↓
May miss the exact nearest neighbor
~~~

In practice, ANN methods are useful because a very fast and highly relevant result is often more practical than an extremely expensive exact search.

---

### 8. ANN in a RAG Pipeline

A complete retrieval flow can look like:

~~~text
Documents
    ↓
Chunking
    ↓
Embedding Model
    ↓
Vector Database
    ↓
ANN Index
```

For a user query:

~~~text
User Query
    ↓
Query Embedding
    ↓
ANN Search
    ↓
Candidate Vectors
    ↓
Top-k Relevant Chunks
    ↓
LLM
    ↓
Generated Answer
~~~

The ANN method therefore works inside the **retrieval stage** to make vector search efficient.

---

### Key Point

> **Approximate Nearest-Neighbor (ANN) search methods are techniques that efficiently find vectors similar to a query without comparing the query against every stored vector. They improve retrieval speed and scalability while allowing a small trade-off in exactness. HNSW and IVF are important examples of ANN approaches.**

### Interview Answer

> **Approximate Nearest-Neighbor search methods are used to efficiently find vectors that are similar to a query vector without performing an exhaustive comparison with every vector in the database. This is important for large-scale RAG systems because exact search becomes expensive as the number of embeddings grows. Methods such as HNSW and IVF organize vectors in efficient structures so that only promising candidates need to be searched, providing faster retrieval with a small trade-off in exactness.**


## 5. What are HNSW and IVF at a high level?

### Answer

**HNSW** and **IVF** are two approaches used by vector databases to perform **efficient approximate nearest-neighbor (ANN) search**.

Both are designed to avoid comparing a query vector with every vector in a large database.

The main difference is:

- **HNSW** → organizes vectors using a **graph structure**.
- **IVF** → organizes vectors into **clusters/groups**.

---

### 1. HNSW

**HNSW** stands for **Hierarchical Navigable Small World**.

At a high level, HNSW represents vectors as nodes in a **graph**.

Vectors that are close or similar are connected to each other.

~~~text
              Query
                ↓
              Node A
             /      \
          Node B    Node C
          /  \        \
       Node D Node E   Node F
            \          /
             Node G
~~~

When searching for a vector, the algorithm navigates through the graph toward nodes that are increasingly similar to the query.

#### Simple idea

~~~text
Query
  ↓
Start at a node
  ↓
Move toward closer nodes
  ↓
Explore promising neighbors
  ↓
Find similar vectors
~~~

The **hierarchical** part means the graph contains multiple levels, allowing the search to move quickly through higher-level connections before exploring more detailed lower-level connections.

---

### 2. IVF

**IVF** stands for **Inverted File Index**.

At a high level, IVF divides the vector space into **clusters**.

For example:

~~~text
All Vectors
      ↓
 ┌────────┬────────┬────────┐
 │Cluster1│Cluster2│Cluster3│
 └────────┴────────┴────────┘
```

Each vector belongs to one of these groups.

When a query arrives:

~~~text
Query Vector
      ↓
Find closest cluster(s)
      ↓
Search only those clusters
      ↓
Find nearest vectors
      ↓
Top-k Results
~~~

Instead of searching the entire database, IVF searches only the most relevant clusters.

---

### 3. HNSW vs IVF

| Feature | HNSW | IVF |
|---|---|---|
| Full form | Hierarchical Navigable Small World | Inverted File Index |
| Main structure | Graph | Clusters |
| Basic idea | Navigate through connected vectors | Search relevant clusters |
| Search process | Follow promising graph paths | Select clusters, then search inside them |
| Main purpose | Fast similarity search | Reduce search space |
| ANN method | Yes | Yes |

---

### 4. Simple Analogy

Imagine a huge library.

#### HNSW

Books are connected based on similarity.

~~~text
AI Books
  ↕
ML Books
  ↕
Deep Learning Books
  ↕
RAG Books
~~~

If you are looking for a RAG book, you follow the connections toward increasingly relevant books.

#### IVF

The library is divided into sections:

~~~text
Library
├── AI
├── Mathematics
├── History
├── Programming
└── Biology
~~~

If your query is about RAG, you first go to the **AI** section and search there instead of checking every book.

---

### 5. HNSW and IVF in RAG

In a RAG system:

~~~text
Documents
    ↓
Chunking
    ↓
Embedding Model
    ↓
Vector Database
    ↓
HNSW / IVF Index
    ↓
Similarity Search
    ↓
Relevant Chunks
    ↓
LLM
    ↓
Answer
~~~

Both HNSW and IVF help make the **retrieval stage faster and more scalable**.

---

### Key Point

> **HNSW and IVF are approximate nearest-neighbor search approaches used in vector databases. HNSW organizes vectors as a navigable graph and searches by following promising connections, while IVF groups vectors into clusters and searches only the most relevant clusters.**

### Interview Answer

> **HNSW and IVF are two common approaches for efficient vector similarity search. HNSW, or Hierarchical Navigable Small World, uses a graph structure where similar vectors are connected and the search navigates through the graph to find nearby vectors. IVF, or Inverted File Index, divides vectors into clusters and searches only the clusters relevant to the query. Both reduce the search space and make large-scale vector retrieval faster.**


## 6. What is top-k retrieval?

### Answer

**Top-k retrieval** is the process of retrieving the **k most relevant results** from a vector database for a given user query.

Here, **k** represents the number of results we want to retrieve.

For example, if `k = 5`, the system retrieves the **5 most similar document chunks** to the user's query.

---

### 1. How Does Top-k Retrieval Work?

Suppose a user asks:

~~~text
"What is Retrieval-Augmented Generation?"
~~~

The query is converted into an embedding:

~~~text
User Query
    ↓
Embedding Model
    ↓
Query Vector
~~~

The vector database compares the query vector with stored document vectors.

Suppose the similarity scores are:

~~~text
Chunk A → 0.92
Chunk B → 0.87
Chunk C → 0.84
Chunk D → 0.81
Chunk E → 0.76
Chunk F → 0.63
Chunk G → 0.51
~~~

If:

~~~text
k = 3
~~~

the system retrieves:

~~~text
Chunk A → 0.92
Chunk B → 0.87
Chunk C → 0.84
~~~

These are the **top 3 most similar results**.

---

### 2. Why Is Top-k Retrieval Used in RAG?

The LLM usually does not need every document in the knowledge base.

Instead, RAG retrieves a small number of relevant chunks and provides them as context.

~~~text
Large Document Collection
          ↓
      Retrieval
          ↓
     Top-k Chunks
          ↓
   Context Construction
          ↓
          LLM
          ↓
        Answer
~~~

This helps reduce:

- Unnecessary context
- Processing cost
- Latency
- Irrelevant information

---

### 3. What Does k Mean?

`k` simply represents the **number of results retrieved**.

For example:

~~~text
k = 1  → Retrieve 1 result
k = 3  → Retrieve 3 results
k = 5  → Retrieve 5 results
k = 10 → Retrieve 10 results
~~~

The value of `k` depends on the application and the retrieval requirements.

---

### 4. Choosing the Value of k

Choosing `k` involves a trade-off.

#### Very Small k

~~~text
k = 1 or 2
```

Advantages:

- Less irrelevant context
- Lower processing cost
- Lower latency

Disadvantage:

- Important information may be missed

#### Very Large k

~~~text
k = 20 or 50
~~~

Advantages:

- More information is retrieved
- Higher chance of including the required information

Disadvantages:

- More irrelevant chunks may be included
- More context is sent to the LLM
- Higher cost and latency
- Too much context can make the answer less focused

Therefore, `k` should be chosen based on the dataset, query type, context limits, and retrieval quality.

---

### 5. Top-k Retrieval in a RAG Pipeline

A typical flow is:

~~~text
Documents
    ↓
Chunking
    ↓
Embedding Model
    ↓
Vector Database
    ↓
Vector Index
    ↓
User Query
    ↓
Query Embedding
    ↓
Similarity Search
    ↓
Top-k Relevant Chunks
    ↓
LLM
    ↓
Answer
~~~

For example:

~~~text
Query:
"What are the benefits of RAG?"

          ↓

Similarity Search

          ↓

Top-k = 3

┌────────────────────────────┐
│ Chunk 1 → High similarity  │
│ Chunk 2 → High similarity  │
│ Chunk 3 → High similarity  │
└────────────────────────────┘

          ↓

        LLM

          ↓

       Answer
~~~

---

### 6. Top-k vs Similarity Score

The **similarity score** tells us how similar a result is to the query.

**Top-k** tells us how many of the highest-ranked results we want.

For example:

~~~text
Similarity Scores:

Chunk A → 0.95
Chunk B → 0.91
Chunk C → 0.88
Chunk D → 0.72
Chunk E → 0.61
~~~

If `k = 3`:

~~~text
Top 3:
A → 0.95
B → 0.91
C → 0.88
~~~

So, **similarity determines the ranking, while k determines how many results are returned**.

---

### Key Point

> **Top-k retrieval means retrieving the k most relevant document chunks for a query based on their similarity to the query embedding. The value of k controls how much information is passed from the retrieval stage to the LLM.**

### Interview Answer

> **Top-k retrieval is the process of retrieving the k most similar or relevant results for a query. In RAG, the user query is converted into an embedding and compared with document embeddings in the vector database. The results are ranked by similarity, and the top k document chunks are returned as context for the LLM. Choosing k involves a trade-off between retrieving enough information and avoiding unnecessary context, latency, and cost.**


## 7. What is metadata filtering?

### Answer

**Metadata filtering** is the process of filtering documents based on their **metadata before or during retrieval**.

Metadata is additional information stored along with a document or chunk, such as:

- Document name
- Author
- Date
- Category
- Department
- Language
- Product
- Access permissions

For example, suppose a document chunk is stored as:

~~~text
Text:
"RAG combines retrieval with generation..."

Metadata:
{
  "source": "rag_notes.pdf",
  "category": "AI",
  "year": 2026,
  "language": "English"
}
~~~

The metadata does not represent the actual document content. It provides **information about the document**.

---

### 1. Why Is Metadata Filtering Used?

In a large knowledge base, searching through every document may return results that are semantically similar but not relevant to the user's requirements.

Metadata filtering allows the system to restrict the search to a specific subset of documents.

For example:

~~~text
User Query:
"What are the latest RAG techniques?"

Filter:
year >= 2025
category = "AI"
~~~

The vector database first considers documents satisfying these conditions and then performs similarity search.

~~~text
All Documents
      ↓
Metadata Filtering
      ↓
Relevant Subset
      ↓
Vector Similarity Search
      ↓
Top-k Results
      ↓
LLM
~~~

---

### 2. Example of Metadata Filtering

Suppose a database contains:

| Document | Category | Year | Language |
|---|---|---:|---|
| Doc A | AI | 2026 | English |
| Doc B | Finance | 2026 | English |
| Doc C | AI | 2024 | English |
| Doc D | AI | 2026 | Hindi |
| Doc E | Healthcare | 2025 | English |

Suppose the user asks:

~~~text
"Explain recent AI developments"
~~~

And we apply:

~~~text
category = "AI"
year >= 2025
language = "English"
~~~

Only:

~~~text
Doc A
~~~

matches all the metadata conditions.

The similarity search can then operate on the filtered documents.

---

### 3. Metadata Filtering vs Semantic Search

These two techniques solve different problems.

| Metadata Filtering | Semantic Search |
|---|---|
| Uses structured metadata | Uses vector embeddings |
| Applies exact conditions | Finds semantically similar content |
| Example: `year = 2026` | Example: "recent AI techniques" |
| Narrows the search space | Ranks results by semantic similarity |

They are often used **together** in a RAG system.

~~~text
User Query
     ↓
Metadata Filter
     ↓
Filtered Documents
     ↓
Semantic / Vector Search
     ↓
Top-k Results
     ↓
LLM
~~~

---

### 4. Common Metadata Filters

Examples include:

~~~text
category = "AI"

year >= 2025

author = "John"

language = "English"

department = "Engineering"

document_type = "PDF"
~~~

Multiple conditions can also be combined:

~~~text
category = "AI"
AND
year >= 2025
AND
language = "English"
~~~

---

### 5. Why Is Metadata Filtering Useful in RAG?

Metadata filtering can help with:

- Improving retrieval relevance
- Reducing the search space
- Avoiding irrelevant documents
- Supporting time-based queries
- Implementing access control
- Separating different document categories
- Improving retrieval efficiency

For example, in an enterprise RAG system, a user may only be allowed to retrieve documents belonging to their department.

~~~text
All Company Documents
          ↓
User Permission Filter
          ↓
Allowed Documents
          ↓
Semantic Search
          ↓
Relevant Chunks
          ↓
LLM
~~~

This helps prevent the system from retrieving documents the user should not have access to.

---

### Key Point

> **Metadata filtering means restricting the documents considered for retrieval using structured information such as date, category, author, language, or access permissions. It is often combined with semantic search to improve the relevance and efficiency of RAG retrieval.**

### Interview Answer

> **Metadata filtering is a technique used in RAG to restrict retrieval based on structured information associated with documents. For example, we can filter documents by year, category, language, author, or user permissions before performing vector similarity search. This reduces the search space and helps retrieve more relevant documents. Metadata filtering and semantic search can be combined, where metadata determines which documents are eligible and vector similarity determines which of those documents are most relevant to the query.**


## 8. What is hybrid search?

### Answer

**Hybrid search** is a retrieval technique that combines **keyword-based search** with **semantic/vector search** to find relevant documents.

The main idea is to use the strengths of both approaches:

- **Keyword search** → finds exact words or phrases
- **Semantic search** → finds meaning and concepts even when the exact words are different

~~~text
                 User Query
                     ↓
              ┌──────┴──────┐
              ↓             ↓
       Keyword Search   Vector Search
              ↓             ↓
        Keyword Results  Semantic Results
              └──────┬──────┘
                     ↓
             Result Combination
                     ↓
                Top Results
                     ↓
                    LLM
~~~

---

### 1. Keyword Search

Keyword search looks for **exact or closely matching words** in the documents.

For example:

~~~text
Query:
"RAG evaluation metrics"
~~~

Keyword search looks for terms such as:

~~~text
RAG
evaluation
metrics
~~~

It is useful when the exact words matter, such as:

- Product names
- Technical terms
- IDs
- Error codes
- Names
- Exact phrases

---

### 2. Semantic Search

Semantic search uses **embeddings** to understand the meaning of the query and documents.

For example:

~~~text
Query:
"How can we measure the quality of a RAG system?"
~~~

A semantic search system may retrieve a document containing:

~~~text
"RAG evaluation can be performed using retrieval and
generation quality metrics."
~~~

Even though the exact words are different, the meanings are related.

---

### 3. Why Combine Both?

Each search method has limitations.

**Keyword search** can miss documents when the wording is different.

**Semantic search** can sometimes miss exact terms that are important.

Hybrid search combines both.

~~~text
Keyword Search
     +
Semantic Search
     ↓
Combined Results
     ↓
More Comprehensive Retrieval
~~~

---

### 4. Example

Suppose a user searches:

~~~text
"How to fix HTTP 401 authentication error?"
~~~

Keyword search is useful because it can find documents containing:

~~~text
HTTP 401
authentication
error
~~~

Semantic search may also find documents discussing:

~~~text
"Unauthorized API requests caused by invalid credentials."
~~~

A hybrid search system can use results from both searches.

---

### 5. How Does Hybrid Search Work in RAG?

A typical hybrid RAG pipeline is:

~~~text
Documents
    ↓
 ┌───────────────────────┐
 │ Keyword Index         │
 │ Vector Index          │
 └───────────────────────┘
            ↓
        User Query
            ↓
     ┌──────┴──────┐
     ↓             ↓
Keyword Search  Vector Search
     ↓             ↓
Keyword Results  Semantic Results
     └──────┬──────┘
            ↓
       Result Fusion
            ↓
        Top-k Results
            ↓
            LLM
            ↓
          Answer
~~~

The results from both retrieval methods can be **combined or reranked** to produce the final set of documents.

---

### 6. Hybrid Search vs Semantic Search

| Feature | Semantic Search | Hybrid Search |
|---|---|---|
| Keyword matching | Limited | Yes |
| Semantic similarity | Yes | Yes |
| Exact terms | Can be weaker | Strong |
| Meaning-based matching | Strong | Strong |
| Uses embeddings | Yes | Usually |
| Uses keyword search | No | Yes |
| Suitable for RAG | Yes | Yes |

---

### 7. When Should Hybrid Search Be Used?

Hybrid search is particularly useful when the data contains both:

- Natural language content
- Important exact terms

Examples include:

~~~text
Technical documentation
Product catalogs
Legal documents
Enterprise knowledge bases
Customer support data
Code documentation
~~~

For example, a technical support system may need to understand the meaning of a question while also matching an exact **error code**.

---

### Key Point

> **Hybrid search combines keyword-based retrieval and semantic/vector retrieval. Keyword search is useful for exact terms, while semantic search is useful for understanding meaning. Combining them can provide more comprehensive retrieval for RAG systems.**

### Interview Answer

> **Hybrid search is a retrieval strategy that combines keyword search with semantic vector search. Keyword search is good at finding exact terms, phrases, IDs, and technical keywords, while semantic search finds results based on meaning using embeddings. In a RAG system, results from both methods can be combined or reranked before selecting the final top-k documents for the LLM.**


## 9. Keyword Search vs Semantic Search?

### Answer

**Keyword search** and **semantic search** are two different approaches used to retrieve relevant information.

- **Keyword search** looks for exact words or phrases.
- **Semantic search** looks for the **meaning and context** of the query using embeddings.

---

### 1. Keyword Search

Keyword search retrieves documents based on the presence of **specific words or phrases**.

For example:

~~~text
Query:
"RAG evaluation metrics"
~~~

A keyword search looks for documents containing terms such as:

~~~text
RAG
evaluation
metrics
~~~

It mainly focuses on **word matching** rather than understanding the complete meaning of the query.

#### Example

If the document contains:

~~~text
"RAG systems can be evaluated using faithfulness and
answer relevance."
~~~

A keyword search can retrieve it because it contains relevant terms such as `RAG` and `evaluated`.

---

### 2. Semantic Search

Semantic search retrieves documents based on the **meaning of the query** rather than requiring the exact words to appear.

It generally works by converting the query and documents into **embeddings** and comparing their similarity.

~~~text
User Query
    ↓
Embedding Model
    ↓
Query Vector
    ↓
Similarity Search
    ↓
Semantically Similar Documents
~~~

For example:

~~~text
Query:
"How can we measure the quality of a RAG system?"
~~~

A semantic search system may retrieve:

~~~text
"RAG systems can be evaluated using retrieval and
generation quality metrics."
~~~

Even though the exact wording is different, the meanings are related.

---

### 3. Main Difference

| Feature | Keyword Search | Semantic Search |
|---|---|---|
| Matching | Exact words/phrases | Meaning and context |
| Uses embeddings | No | Yes |
| Understands meaning | Limited | Yes |
| Exact terms | Very useful | May be weaker |
| Different wording | May miss results | Can find related results |
| Technical terms / IDs | Very useful | Can be less reliable |
| Typical technology | Inverted index | Vector index |
| RAG usage | Useful | Very common |

---

### 4. Example

Suppose the database contains:

~~~text
Document A:
"RAG combines retrieval with generation."

Document B:
"Retrieval-Augmented Generation uses external
knowledge to improve LLM responses."
~~~

Query:

~~~text
"How does RAG use external knowledge?"
~~~

#### Keyword Search

It looks for exact terms such as:

~~~text
RAG
external
knowledge
~~~

#### Semantic Search

It converts the query into an embedding and looks for documents with similar meaning.

Therefore, a document using different wording can still be retrieved if its meaning is relevant.

---

### 5. Advantages and Limitations

#### Keyword Search

**Advantages:**

- Good for exact terms
- Fast and well-established
- Useful for names, IDs, error codes, and technical terms
- Easy to understand and debug

**Limitations:**

- Can miss relevant documents with different wording
- Does not fully capture semantic meaning
- Synonyms may not always be matched

---

#### Semantic Search

**Advantages:**

- Understands semantic similarity
- Handles different wording
- Useful for natural-language queries
- Can retrieve conceptually related documents

**Limitations:**

- Requires an embedding model
- Requires vector search infrastructure
- May sometimes miss exact terms or identifiers
- Can retrieve results that are semantically related but not exactly what the user needs

---

### 6. Keyword Search vs Semantic Search in RAG

A RAG system can use either approach:

~~~text
                 User Query
                     ↓
              ┌──────┴──────┐
              ↓             ↓
       Keyword Search   Semantic Search
              ↓             ↓
         Text Results    Vector Results
              └──────┬──────┘
                     ↓
              Combined Results
                     ↓
                    LLM
~~~

Using both approaches together is called **hybrid search**.

Hybrid search is useful when a system needs both:

~~~text
Exact Matching
      +
Meaning-Based Matching
~~~

---

### Key Point

> **Keyword search retrieves documents based mainly on matching words or phrases, while semantic search retrieves documents based on their meaning using embeddings. Keyword search is particularly useful for exact terms, whereas semantic search is useful when the same idea can be expressed using different words.**

### Interview Answer

 **Keyword search matches the words or phrases in a query with words present in documents, while semantic search uses embeddings to find documents that are similar in meaning. Keyword search is useful for exact terms such as names, IDs, and error codes, whereas semantic search is useful for natural-language queries and different wording. In RAG, both can be combined as hybrid search to improve retrieval.**


 ## 10. How would you choose a retrieval strategy for a RAG application?

### Answer

The retrieval strategy should be chosen based on the **type of data, query patterns, required accuracy, latency, and application requirements**.

There is no single retrieval strategy that is best for every RAG application.

A good approach is to start with a simple strategy and evaluate it using representative queries, then add techniques such as metadata filtering, hybrid search, or reranking when needed.

---

### 1. Start with Semantic Search

For many RAG applications, a good starting point is **semantic/vector search**.

~~~text
User Query
    ↓
Query Embedding
    ↓
Vector Database
    ↓
Similarity Search
    ↓
Top-k Chunks
    ↓
LLM
~~~

Semantic search is useful when users ask questions in natural language and the relevant documents may use different wording.

---

### 2. Consider the Type of Data

The nature of the data affects the retrieval strategy.

#### Mostly Natural-Language Documents

Examples:

~~~text
Articles
FAQs
Documentation
Knowledge bases
Research documents
~~~

Semantic search is often useful because the meaning of the query is important.

#### Data With Important Exact Terms

Examples:

~~~text
Product IDs
Error codes
Policy numbers
Technical terms
Names
Part numbers
~~~

Keyword search can be important because exact matches matter.

---

### 3. Use Hybrid Search When Both Matter

If the application needs both **semantic understanding and exact keyword matching**, use hybrid search.

~~~text
                 Query
                   ↓
          ┌────────┴────────┐
          ↓                 ↓
   Keyword Search     Semantic Search
          ↓                 ↓
     Results               Results
          └────────┬────────┘
                   ↓
             Result Fusion
                   ↓
              Top-k Results
                   ↓
                  LLM
~~~

This is especially useful for technical or enterprise knowledge bases where both natural-language meaning and exact terms are important.

---

### 4. Use Metadata Filtering When Appropriate

If documents contain useful metadata, filtering can restrict retrieval to the relevant subset.

For example:

~~~text
Query:
"Latest AI research"

Metadata Filter:
category = "AI"
year >= 2025
language = "English"
~~~

The system can first filter the documents and then perform similarity search.

~~~text
All Documents
      ↓
Metadata Filtering
      ↓
Filtered Documents
      ↓
Semantic Search
      ↓
Top-k Results
~~~

This can improve relevance and reduce the search space.

---

### 5. Choose an Appropriate Top-k

The value of `k` also affects the retrieval strategy.

~~~text
Small k
  ↓
Less context
Lower latency/cost
But may miss information

Large k
  ↓
More information
But may add irrelevant context
and increase latency/cost
~~~

The appropriate value should be determined through testing rather than choosing an arbitrary number.

---

### 6. Add Reranking if Initial Retrieval Is Not Enough

Sometimes the first-stage retriever returns documents that are broadly relevant but are not the best matches.

In that case, a **reranker** can be added.

~~~text
User Query
     ↓
Initial Retrieval
     ↓
Top-k Candidate Documents
     ↓
Reranker
     ↓
Best Relevant Documents
     ↓
LLM
~~~

This creates a two-stage retrieval system:

1. **Retriever** → quickly finds candidate documents.
2. **Reranker** → more carefully orders the candidates by relevance.

---

### 7. Consider the Application Requirements

When choosing a strategy, consider:

| Requirement | Possible Consideration |
|---|---|
| Natural-language questions | Semantic search |
| Exact keywords / IDs | Keyword search |
| Both exact terms and meaning | Hybrid search |
| Large document collection | Vector indexing / ANN |
| Structured document attributes | Metadata filtering |
| High retrieval precision | Reranking |
| Low latency | Efficient indexing and smaller candidate sets |
| High recall | Larger candidate set / suitable retrieval strategy |

---

### 8. Evaluate the Strategy

The final choice should be based on **retrieval quality and application requirements**, not just the retrieval method itself.

Create representative queries and evaluate whether the correct documents are being retrieved.

For example:

~~~text
Test Queries
     ↓
Retrieval Strategy
     ↓
Retrieved Documents
     ↓
Evaluate Relevance
     ↓
Compare Results
     ↓
Improve Strategy
~~~

Useful retrieval metrics include:

- Precision@k
- Recall@k
- Retrieval relevance
- Latency
- Cost

The goal is to find a suitable balance between **retrieval quality, latency, and cost**.

---

### 9. Example Decision Process

Suppose we are building a RAG system for technical documentation.

A reasonable approach could be:

~~~text
Technical Documents
        ↓
   User Query
        ↓
Metadata Filtering
        ↓
Hybrid Search
   ┌────┴────┐
   ↓         ↓
Keyword   Semantic
 Search    Search
   └────┬────┘
        ↓
   Candidate Results
        ↓
     Reranking
        ↓
     Top Results
        ↓
        LLM
~~~

This approach can handle both:

- Natural-language questions
- Exact technical terms and error codes

However, the exact architecture should be validated using the application's actual queries and evaluation data.

---

### Key Point

> **To choose a retrieval strategy, first understand the data and query patterns, then select the simplest approach that provides sufficient retrieval quality. Semantic search works well for meaning-based queries, keyword search for exact terms, hybrid search for both, metadata filtering for structured constraints, and reranking when higher precision is required. The final strategy should be validated using retrieval quality, latency, and cost.**

### Interview Answer

> **I would choose a retrieval strategy based on the data, query patterns, accuracy requirements, latency, and cost. I would usually start with semantic vector search for natural-language queries. If exact terms such as IDs or error codes are important, I would use keyword search or hybrid search. I would add metadata filtering when documents have useful structured attributes and reranking when the initial retrieval is not precise enough. Finally, I would evaluate the strategy using representative queries and metrics such as precision@k, recall@k, latency, and cost, and then tune the system based on the results.**
