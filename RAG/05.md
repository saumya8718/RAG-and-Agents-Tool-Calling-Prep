# 05. Retrieval Quality & Reranking 

## 1. What makes a retrieved document relevant?

### Answer

A **retrieved document is relevant** when it contains information that is **useful for answering the user's query**.

In RAG, relevance is not simply about whether the document contains the same words as the query. A document can be relevant because it contains the **same concept, information, or evidence** needed to answer the question.

---

### 1. Example of a Relevant Document

Suppose the user asks:

~~~text
"What are the benefits of using RAG?"
~~~

Consider these retrieved documents:

**Document A:**

~~~text
"RAG allows an LLM to retrieve external information,
which can improve factual grounding and provide access
to domain-specific knowledge."
~~~

This is relevant because it directly discusses benefits and capabilities of RAG.

**Document B:**

~~~text
"Vector databases store embeddings and allow similarity search."
~~~

This is related to RAG, but it may not directly answer the question about its benefits.

Therefore:

~~~text
Query
 ↓
Document A → Highly Relevant
Document B → Related but Less Relevant
~~~

---

### 2. What Factors Make a Document Relevant?

A retrieved document is generally considered relevant when it has one or more of these properties:

#### 1. Semantic Similarity

The document discusses the same concept or meaning as the query.

~~~text
Query:
"How does RAG reduce hallucination?"

Document:
"Retrieved external knowledge can provide evidence
that the LLM can use when generating an answer."
~~~

The wording is not identical, but the concepts are related.

---

#### 2. Directly Answers the Query

The document should contain information that can actually help answer the user's question.

~~~text
Query:
"What is HNSW?"

Relevant:
"HNSW is a graph-based approximate nearest-neighbor
search algorithm."
~~~

A document that only discusses vector databases in general would be less directly relevant.

---

#### 3. Contains Supporting Evidence

A document can also be relevant when it provides evidence or context required to construct the final answer.

For example:

~~~text
Query:
"What is the company's refund policy?"

Relevant Document:
"The refund policy allows customers to request a
refund within 30 days of purchase."
~~~

The document provides the information needed to answer the question.

---

#### 4. Matches the Required Context

Sometimes relevance depends on additional constraints.

For example:

~~~text
Query:
"What was the sales policy in 2026?"
~~~

A document about the same policy from 2020 may be semantically similar but not relevant to the required time period.

Metadata such as:

~~~text
year = 2026
department = "Sales"
document_type = "Policy"
~~~

can therefore help determine relevance.

---

### 3. Relevance Is More Than Keyword Matching

Consider the query:

~~~text
"How can I reduce the response time of my RAG system?"
~~~

A document containing:

~~~text
"Latency can be reduced by optimizing retrieval,
using efficient indexes, and reducing unnecessary
context."
~~~

may be highly relevant even if it does not contain the exact phrase:

~~~text
"reduce response time"
~~~

This is why **semantic retrieval** is useful in RAG.

---

### 4. Relevance vs Similarity Score

A high similarity score does not always guarantee that a document is truly useful.

For example:

~~~text
Query:
"How do I evaluate RAG retrieval quality?"

Retrieved Document:
"RAG systems use vector databases for semantic search."
~~~

This document is related to RAG and may have a reasonably high similarity score, but it does not directly explain retrieval evaluation.

Therefore:

~~~text
Similarity
    ↓
Candidate Relevance
    ↓
Actual Usefulness for the Query
~~~

This is one reason RAG systems may use **reranking** after initial retrieval.

---

### 5. How Relevance Is Used in a RAG Pipeline

A typical retrieval process is:

~~~text
User Query
    ↓
Query Embedding
    ↓
Initial Retrieval
    ↓
Candidate Documents
    ↓
Relevance Evaluation / Reranking
    ↓
Most Relevant Documents
    ↓
Context Construction
    ↓
LLM
    ↓
Answer
~~~

The goal is to provide the LLM with documents that contain the information needed to produce a correct and useful answer.

---

### Key Point

> **A retrieved document is relevant when its content provides useful information for answering the user's query. Relevance depends on semantic meaning, direct answerability, supporting evidence, and contextual requirements—not just keyword or similarity matching.**

### Interview Answer

> **A retrieved document is relevant if it contains information that can directly or indirectly help answer the user's query. I would consider semantic similarity, whether the document actually answers the question, whether it provides supporting evidence, and whether it satisfies constraints such as date or category. A high vector similarity score is useful for finding candidates, but it does not always guarantee true relevance, which is why reranking and retrieval evaluation may be needed.**


## 2. What is reranking?

### Answer

**Reranking** is the process of taking the initial results returned by a retrieval system and **reordering them based on their relevance to the user's query**.

In a RAG system, the first retrieval step is usually optimized for **speed** and may return some results that are only partially relevant.

A reranker performs a second, more detailed relevance check and places the most useful documents at the top.

---

### 1. Why Is Reranking Needed?

Suppose a user asks:

~~~text
"How can I evaluate the retrieval quality of a RAG system?"
~~~

The vector search may return:

~~~text
Document A → RAG architecture
Document B → RAG retrieval evaluation
Document C → Vector databases
Document D → RAG hallucinations
Document E → Embeddings
~~~

Although all documents are related to RAG, **Document B** is the most directly relevant.

A reranker can reorder them:

~~~text
Before Reranking:

A → RAG architecture
B → Retrieval evaluation
C → Vector databases
D → Hallucinations
E → Embeddings

        ↓ Reranker

After Reranking:

B → Retrieval evaluation
A → RAG architecture
C → Vector databases
D → Hallucinations
E → Embeddings
~~~

The most relevant documents are then passed to the LLM.

---

### 2. Two-Stage Retrieval

Reranking is commonly used in a **two-stage retrieval pipeline**.

~~~text
                 User Query
                     ↓
              Initial Retrieval
                     ↓
              Candidate Documents
                     ↓
                  Reranker
                     ↓
             Re-ranked Documents
                     ↓
                Top Results
                     ↓
                    LLM
~~~

#### Stage 1: Initial Retrieval

The first retriever quickly finds a larger set of candidate documents.

For example:

~~~text
Top 20 candidates
```

This stage may use:

- Vector search
- Keyword search
- Hybrid search

#### Stage 2: Reranking

The reranker examines the query and candidate documents more carefully and assigns a new relevance score.

For example:

~~~text
Query + Document
       ↓
   Reranker
       ↓
Relevance Score
~~~

The candidates are then sorted according to these scores.

---

### 3. Retrieval vs Reranking

The main difference is their role in the pipeline.

| Initial Retrieval | Reranking |
|---|---|
| Finds candidate documents | Reorders candidate documents |
| Optimized for speed | Focuses more on relevance |
| Searches a large collection | Works on a smaller candidate set |
| Often uses vector/keyword search | Uses a more detailed relevance model |
| First stage | Second stage |

For example:

~~~text
1,000,000 Documents
        ↓
Initial Retrieval
        ↓
100 Candidates
        ↓
Reranking
        ↓
10 Best Documents
        ↓
LLM
~~~

This is more efficient than applying an expensive reranking model to all 1,000,000 documents.

---

### 4. Why Can Reranking Improve RAG?

Vector similarity does not always perfectly represent whether a document answers a specific question.

For example:

~~~text
Query:
"What are the limitations of RAG?"
~~~

A document discussing:

~~~text
"RAG uses vector databases for semantic retrieval."
~~~

may be semantically related to the query but does not directly discuss limitations.

A reranker can consider the **relationship between the query and the document more precisely** and move more relevant documents higher in the ranking.

---

### 5. Reranking in a RAG Pipeline

A typical pipeline can look like:

~~~text
Documents
    ↓
Chunking
    ↓
Embeddings
    ↓
Vector Database
    ↓
Initial Retrieval
    ↓
Top 20-50 Candidates
    ↓
Reranking
    ↓
Top 3-5 Relevant Chunks
    ↓
Context Construction
    ↓
LLM
    ↓
Answer
~~~

The exact number of candidates and final documents depends on the application.

---

### 6. Reranking Trade-off

Reranking can improve retrieval quality, but it also adds computational work.

~~~text
Without Reranking
      ↓
Lower latency
Lower computational cost
But potentially weaker ranking

With Reranking
      ↓
Better candidate ordering
Potentially better retrieval quality
But additional latency and cost
~~~

Therefore, reranking should be used when the improvement in retrieval quality justifies the additional cost and latency.

---

### Key Point

> **Reranking is a second-stage retrieval process that takes initially retrieved candidate documents and reorders them according to their relevance to the query. It helps ensure that the most useful documents are passed to the LLM.**

### Interview Answer

> **Reranking is a second-stage retrieval technique used to improve the ordering of initially retrieved documents. First, a fast retriever such as vector, keyword, or hybrid search retrieves a set of candidate documents. A reranker then evaluates the query-document relevance more carefully and reorders the candidates. The highest-ranked documents are passed to the LLM. Reranking can improve retrieval quality, but it adds some computational cost and latency.**


## 3. Why might the most similar chunks still be poor context?

### Answer

The **most similar chunks are not always the best context** for an LLM because similarity search usually measures how closely the **meaning or embeddings** of the query and chunk are related.

A chunk can be semantically similar to the query but still fail to provide the **specific information needed to answer it**.

---

### 1. Semantic Similarity Does Not Guarantee Relevance

Suppose the user asks:

~~~text
"What are the limitations of RAG?"
~~~

The retriever might return:

~~~text
Chunk A:
"RAG combines retrieval with generation and uses
external knowledge to improve LLM responses."

Chunk B:
"RAG can suffer from retrieval errors, irrelevant
context, and increased system complexity."
~~~

Both chunks are related to RAG.

However:

~~~text
Chunk A → Related to RAG
Chunk B → Directly discusses limitations
~~~

Therefore, Chunk A may have a high similarity score but still be poor context for answering the specific question.

---

### 2. The Chunk May Lack Enough Context

A chunk may contain the right information but be too small to understand properly.

For example:

~~~text
Previous chunk:
"The system uses a reranker to improve retrieval."

Retrieved chunk:
"This significantly improves accuracy."
~~~

The second chunk may be semantically similar to the query, but without the previous chunk, it is unclear:

~~~text
What does "this" refer to?
~~~

This can happen when chunking separates related information.

---

### 3. The Chunk May Be Too Broad

A chunk can contain many topics and only a small part may be relevant.

For example:

~~~text
Chunk:
"RAG uses embeddings, vector databases, chunking,
reranking, prompt templates, evaluation metrics,
and monitoring..."
~~~

If the question is:

~~~text
"What is reranking?"
~~~

the chunk is related to RAG, but it contains a lot of unnecessary information.

This can introduce **noise into the LLM's context**.

---

### 4. Similarity May Focus on the Wrong Part

A document can contain a highly similar phrase but still not answer the user's actual question.

For example:

~~~text
Query:
"How can I reduce RAG latency?"
~~~

A chunk discussing:

~~~text
"RAG retrieval improves the relevance of responses."
~~~

may be retrieved because it contains similar RAG-related concepts.

However, it does not provide information about:

~~~text
Latency optimization
```

So semantic similarity alone is not enough.

---

### 5. Duplicate or Redundant Chunks

The retrieval system may return several chunks containing almost the same information.

For example:

~~~text
Top 5 Results:

Chunk 1 → Same explanation of RAG
Chunk 2 → Same explanation of RAG
Chunk 3 → Same explanation of RAG
Chunk 4 → Same explanation of RAG
Chunk 5 → Actual answer
~~~

Even though the first four chunks may have high similarity scores, they consume the context window without adding much new information.

This can prevent the LLM from receiving other useful information.

---

### 6. Missing Information

Sometimes the retrieved chunks are individually relevant but do not contain **all the information required** to answer the question.

For example:

~~~text
Query:
"What is HNSW and what are its advantages?"

Retrieved:

Chunk A → Definition of HNSW
Chunk B → General vector database concepts
~~~

The definition may be relevant, but if information about the advantages is missing, the retrieved context is incomplete.

---

### 7. Why Reranking Helps

Because similarity search is not perfect, RAG systems can use **reranking**.

~~~text
User Query
     ↓
Vector / Keyword Retrieval
     ↓
Candidate Chunks
     ↓
Reranking
     ↓
Most Relevant Chunks
     ↓
Context Construction
     ↓
LLM
~~~

The initial retriever finds candidate chunks quickly.

The reranker then evaluates the relationship between the **query and each candidate chunk** more carefully.

This can move directly useful chunks above merely related chunks.

---

### 8. Retrieval Quality Is More Than Similarity

A good context should ideally be:

- Relevant to the exact question
- Informative
- Sufficient to answer the question
- Not unnecessarily repetitive
- Coherent with surrounding information
- Within the required context limits

Therefore:

~~~text
High Similarity
      ≠
Always Good Context
~~~

Instead:

~~~text
Good Context
=
Relevance
+
Sufficient Information
+
Low Redundancy
+
Useful Context
~~~

---

### Key Point

> **The most similar chunks can still be poor context because embedding similarity measures semantic relatedness, not necessarily whether the chunk directly answers the question. Chunks may be incomplete, too broad, redundant, or related to the topic without containing the required information.**

### Interview Answer

> **The most similar chunks are not always the best context because similarity search measures semantic relatedness rather than exact usefulness for the question. A chunk may be related to the topic but not directly answer the query, may lack surrounding context, contain too much irrelevant information, or be redundant with other retrieved chunks. This is why RAG systems may use techniques such as better chunking, metadata filtering, hybrid search, and reranking to improve the quality of the final context.**


## 4. What is query expansion?

### Answer

**Query expansion** is a retrieval technique in which the original user query is expanded with **additional related words, terms, or concepts** before performing retrieval.

The goal is to give the retrieval system more information about what the user is looking for and increase the chance of finding relevant documents.

---

### 1. Why Is Query Expansion Needed?

Users may ask a question using words that are different from the words used in the documents.

For example:

~~~text
Original Query:
"How can I make RAG faster?"
~~~

A knowledge base might use terms such as:

~~~text
"RAG latency optimization"
"retrieval optimization"
"performance improvement"
"response time reduction"
~~~

A query expansion technique can add related terms:

~~~text
Original Query
      ↓
Query Expansion
      ↓
"RAG faster"
"RAG latency"
"RAG performance"
"retrieval optimization"
      ↓
Retrieval
~~~

This can improve the chances of retrieving relevant documents.

---

### 2. How Does Query Expansion Work?

A simple flow is:

~~~text
User Query
     ↓
Query Expansion
     ↓
Expanded Query
     ↓
Retriever
     ↓
Relevant Documents
     ↓
LLM
~~~

The expansion can be performed using:

- Synonyms
- Related terms
- Domain-specific terminology
- Alternative expressions
- Additional keywords

---

### 3. Example

Suppose the user asks:

~~~text
"What is the best way to reduce hallucinations in RAG?"
~~~

The system may expand the query with related concepts:

~~~text
Original:
reduce hallucinations in RAG

Expanded:
RAG hallucination reduction
RAG grounding
factual accuracy
retrieval quality
context grounding
~~~

The expanded terms can then be used during retrieval.

This can help when the documents use terms such as **grounding** instead of **hallucination reduction**.

---

### 4. Query Expansion in a RAG Pipeline

A RAG system can use query expansion before searching the vector database or search index.

~~~text
User Query
     ↓
Query Expansion
     ↓
Expanded Query
     ↓
Embedding / Search
     ↓
Candidate Documents
     ↓
Reranking
     ↓
Top-k Results
     ↓
LLM
~~~

The exact implementation depends on the retrieval system.

---

### 5. Benefits of Query Expansion

Query expansion can help:

- Improve recall
- Handle different terminology
- Find documents using synonyms
- Handle domain-specific vocabulary
- Reduce problems caused by wording differences

For example:

~~~text
User:
"How do I make my RAG system faster?"

Document:
"Techniques for reducing RAG inference latency"
~~~

The original query and document use different wording, but query expansion can help connect the two.

---

### 6. Limitations of Query Expansion

Query expansion is not always beneficial.

If too many unrelated terms are added, the retrieval system may retrieve irrelevant documents.

For example:

~~~text
Original Query:
"RAG latency"

Poor Expansion:
RAG
AI
LLM
machine learning
databases
embeddings
cloud
software
~~~

The expanded query has become too broad.

This can reduce precision and introduce irrelevant results.

Therefore, query expansion should add **useful and relevant terms**, not simply more terms.

---

### 7. Query Expansion vs Query Rewriting

These techniques are related but different.

| Query Expansion | Query Rewriting |
|---|---|
| Adds related terms or concepts | Changes the query into a better form |
| Usually preserves the original query | May replace or restructure the original query |
| Can produce additional terms | Produces a reformulated query |
| Goal is to broaden retrieval | Goal is to make the query clearer or more effective |

Example:

**Original query:**

~~~text
"RAG faster?"
~~~

**Query expansion:**

~~~text
RAG latency optimization
RAG performance improvement
retrieval optimization
~~~

**Query rewriting:**

~~~text
"What techniques can reduce the latency of a
Retrieval-Augmented Generation system?"
~~~

---

### Key Point

> **Query expansion improves retrieval by adding relevant synonyms, related terms, or concepts to the original query. It helps the retrieval system find documents that use different terminology, but excessive or unrelated expansion can reduce retrieval precision.**

### Interview Answer

> **Query expansion is a retrieval technique where the original user query is supplemented with related terms, synonyms, or domain-specific concepts before retrieval. For example, a query like "How can I make RAG faster?" can be expanded with terms such as "RAG latency optimization" and "retrieval performance." This can improve recall when documents use different terminology, but the expansion should be controlled because adding unrelated terms can introduce irrelevant results.**


## 5. What is query rewriting?

### Answer

**Query rewriting** is the process of transforming the user's original query into a **clearer, more precise, or retrieval-friendly query** before sending it to the retrieval system.

The goal is to make the query better suited for retrieving the information needed to answer the user's question.

---

### 1. Why Is Query Rewriting Needed?

Users do not always write queries in a way that is ideal for retrieval.

For example:

~~~text
Original Query:
"RAG faster?"
~~~

This query is short and ambiguous.

A query rewriting step can transform it into:

~~~text
"What techniques can be used to reduce the latency
of a Retrieval-Augmented Generation system?"
~~~

The rewritten query gives the retrieval system more context about what information is required.

---

### 2. How Does Query Rewriting Work?

A typical flow is:

~~~text
User Query
     ↓
Query Rewriter
     ↓
Rewritten Query
     ↓
Retriever
     ↓
Relevant Documents
     ↓
LLM
     ↓
Answer
~~~

The query rewriter can use an LLM or another language-processing method to reformulate the original query.

---

### 3. Example

Suppose a user asks:

~~~text
"How does it help with hallucinations?"
~~~

The word **"it"** is ambiguous.

If the previous conversation was about RAG, a query rewriter can transform it into:

~~~text
"How does Retrieval-Augmented Generation help reduce
LLM hallucinations?"
~~~

The rewritten query is more explicit and easier for the retriever to process.

---

### 4. Query Rewriting for Conversational RAG

Query rewriting is particularly useful when the user asks follow-up questions.

For example:

~~~text
User:
"What is RAG?"

Assistant:
"RAG combines retrieval with generation..."

User:
"How does it reduce hallucinations?"
~~~

The second query depends on the previous conversation.

The system can rewrite it as:

~~~text
"How does Retrieval-Augmented Generation reduce
LLM hallucinations?"
~~~

Then the rewritten query is sent to the retriever.

~~~text
Conversation History
        ↓
   Query Rewriter
        ↓
Standalone Query
        ↓
     Retriever
        ↓
 Relevant Documents
        ↓
        LLM
~~~

---

### 5. Query Rewriting vs Query Expansion

These concepts are related but different.

| Query Rewriting | Query Expansion |
|---|---|
| Reformulates the query | Adds related terms |
| Produces a clearer query | Broadens the query |
| Can change the wording or structure | Usually preserves the original query |
| Useful for ambiguous or conversational queries | Useful for synonyms and terminology variations |

#### Example

Original:

~~~text
"RAG faster?"
~~~

**Query rewriting:**

~~~text
"How can the latency of a RAG system be reduced?"
~~~

**Query expansion:**

~~~text
RAG latency
RAG performance
retrieval optimization
response time
~~~

So:

~~~text
Rewriting → Make the query clearer
Expansion → Add related retrieval terms
~~~

---

### 6. Benefits of Query Rewriting

Query rewriting can help:

- Resolve ambiguous queries
- Handle conversational follow-up questions
- Make short queries more descriptive
- Improve retrieval relevance
- Convert natural user language into retrieval-friendly queries
- Incorporate relevant conversation context

---

### 7. Limitation of Query Rewriting

A rewritten query can sometimes introduce **incorrect assumptions** or remove important information from the original query.

For example:

~~~text
Original:
"Compare RAG and fine-tuning for customer support."
~~~

If the rewriting system incorrectly produces:

~~~text
"How is RAG used for customer support?"
~~~

the comparison requirement has been lost.

Therefore, the rewritten query should preserve the **original intent** of the user.

---

### Key Point

> **Query rewriting transforms the user's original query into a clearer and more retrieval-friendly query while preserving its intent. It is especially useful for ambiguous queries and conversational follow-up questions.**

### Interview Answer

> **Query rewriting is the process of reformulating a user's query into a clearer and more retrieval-friendly form before retrieval. It is particularly useful for short, ambiguous, or conversational queries. For example, after discussing RAG, a user may ask "How does it reduce hallucinations?" The system can rewrite this as "How does Retrieval-Augmented Generation reduce LLM hallucinations?" The rewritten query is then sent to the retriever. The important requirement is that the rewritten query should preserve the user's original intent.**


## 6. What is Multi-Query Retrieval?

### Answer

**Multi-query retrieval** is a retrieval technique where a single user query is transformed into **multiple different queries** that represent the same information need from different perspectives.

Instead of searching the knowledge base using only the original query, the system generates several related queries and retrieves documents for each of them.

This increases the chance of finding all the relevant information.

---

### Why Do We Need Multi-Query Retrieval?

A single query may not match all relevant documents because different documents may use different:

- Words
- Phrases
- Terminology
- Perspectives
- Ways of describing the same concept

For example, suppose the user asks:

> **"How can I reduce RAG latency?"**

Different documents might discuss the same topic using terms such as:

- RAG performance optimization
- Retrieval latency
- Vector search optimization
- Faster document retrieval
- Reducing LLM response time

A single query may not retrieve all of these documents effectively.

Multi-query retrieval addresses this by generating multiple versions of the query.

---

### Basic Flow

~~~text
                User Query
                    ↓
        "How can I reduce RAG latency?"
                    ↓
             Query Generator
                    ↓
       ┌────────────┼────────────┐
       ↓            ↓            ↓
 Query 1         Query 2       Query 3
       ↓            ↓            ↓
   Retriever     Retriever    Retriever
       ↓            ↓            ↓
   Documents     Documents    Documents
       └────────────┼────────────┘
                    ↓
              Combine Results
                    ↓
              Remove Duplicates
                    ↓
              Reranking (Optional)
                    ↓
              Top Relevant Docs
                    ↓
                   LLM
                    ↓
                 Answer
~~~

---

### Example

Original query:

> **"How can I reduce RAG latency?"**

The system may generate:

**Query 1:**
> How can Retrieval-Augmented Generation latency be reduced?

**Query 2:**
> What techniques improve RAG retrieval performance?

**Query 3:**
> How can vector search and document retrieval be optimized?

Each query is sent to the retriever.

The results are then combined to create a larger and more diverse set of candidate documents.

---

### Multi-Query Retrieval vs Query Expansion

| Multi-Query Retrieval | Query Expansion |
|---|---|
| Generates multiple separate queries | Adds related terms to a query |
| Each query can be independently retrieved | Usually produces an expanded version of the original query |
| Focuses on different perspectives or formulations | Focuses on adding related terminology |
| Results from multiple searches are combined | Retrieval is generally performed using the expanded query |

---

### Advantages

#### 1. Improves Recall

Different query formulations can retrieve documents that the original query might miss.

#### 2. Handles Different Terminology

It can retrieve documents that use different words for the same concept.

#### 3. Handles Ambiguous Queries

Multiple interpretations of a query can be explored.

#### 4. Provides More Diverse Results

Different queries can retrieve information from different parts of the knowledge base.

---

### Limitation

The main drawback is **additional retrieval cost and latency**.

If one query requires one retrieval operation, generating five queries may require several retrieval operations.

Therefore, multi-query retrieval should be used when the improvement in retrieval quality justifies the additional cost.

---

### Multi-Query RAG Architecture

~~~text
User
 ↓
Original Query
 ↓
Generate Multiple Queries
 ↓
┌───────────────────────────────┐
│ Query 1 → Retrieval           │
│ Query 2 → Retrieval           │
│ Query 3 → Retrieval           │
└───────────────────────────────┘
 ↓
Combine Retrieved Documents
 ↓
Remove Duplicates
 ↓
Rerank
 ↓
Top-k Documents
 ↓
LLM
 ↓
Final Answer
~~~

### Key Point

**Multi-query retrieval generates multiple variations of a user's query, retrieves documents for each variation, and combines the results to improve retrieval coverage and recall.**

### Interview Answer

> **Multi-query retrieval is a RAG technique where one user query is converted into multiple related queries. Each query is independently sent to the retriever, and the retrieved results are combined, usually followed by deduplication and optionally reranking. This helps improve recall because different query formulations can retrieve relevant documents that a single query might miss. The trade-off is increased retrieval cost and latency.**


## 7. How would you improve a RAG system that retrieves irrelevant documents?

### Answer

If a RAG system is retrieving irrelevant documents, the first step is to identify **where the retrieval problem is coming from**.

Common causes include:

- Poor document chunking
- Poor embedding model
- Incorrect query formulation
- Too many or too few retrieved documents
- Lack of metadata filtering
- Similar but irrelevant chunks
- Missing reranking
- Poor search strategy

A systematic approach can be used to improve retrieval quality.

---

### 1. Improve Chunking

Poorly designed chunks can contain incomplete or unrelated information.

For example, if a chunk is too large, it may contain several unrelated topics. If it is too small, important context may be lost.

Try:

- Appropriate chunk sizes
- Chunk overlap
- Recursive chunking
- Semantic chunking
- Document-structure-based chunking

The chunking strategy should match the type of documents being indexed.

---

### 2. Use a Better Embedding Model

The embedding model determines how text is represented as vectors.

If semantically related documents are not being retrieved, evaluate whether the current embedding model understands the domain and language of the data.

For example, technical documentation may benefit from an embedding model that performs well on technical text.

---

### 3. Improve the User Query

The original query may be too short, ambiguous, or conversational.

Use **query rewriting** to make the query clearer and more suitable for retrieval.

Example:

```text
Original:
"RAG faster?"

Rewritten:
"What techniques can reduce the latency of a RAG system?"
```

A clearer query can improve the relevance of retrieved documents.

---

### 4. Use Query Expansion or Multi-Query Retrieval

If one query does not retrieve enough relevant information, generate related queries.

For example:

```text
Original:
"How can I reduce RAG latency?"

Query 1:
"How can RAG retrieval latency be reduced?"

Query 2:
"How can vector search performance be improved?"

Query 3:
"What techniques optimize RAG performance?"
```

The results from these queries can then be combined.

This can improve **recall** and help retrieve documents that use different terminology.

---

### 5. Use Hybrid Search

If semantic search alone is not working well, combine:

- Keyword search
- Semantic/vector search

Keyword search is useful for exact terms such as:

```text
HTTP 401
APIError
Product ID
SQL JOIN
```

Semantic search is useful when the query and document use different wording but have similar meaning.

Hybrid search can therefore improve retrieval quality.

---

### 6. Apply Metadata Filtering

Use metadata to restrict the search space.

For example:

```text
Query:
"What is the refund policy?"

Filters:
category = "billing"
language = "English"
year >= 2025
```

This prevents the retriever from searching irrelevant categories or documents.

---

### 7. Use Reranking

The initial retriever may return documents that are semantically similar but not actually useful for answering the question.

A **reranker** can evaluate the retrieved candidates again and reorder them based on their relevance to the query.

```text
User Query
    ↓
Initial Retrieval
    ↓
Candidate Documents
    ↓
Reranker
    ↓
Most Relevant Documents
    ↓
LLM
```

This is especially useful when the initial retrieval has good recall but poor precision.

---

### 8. Tune Top-k

The value of **k** determines how many documents are retrieved.

If `k` is too small:

```text
Relevant information may be missed
```

If `k` is too large:

```text
Irrelevant information may be included
```

Therefore, test different values of `k` using representative queries and choose a value that provides a good balance between relevance and coverage.

---

### 9. Remove Duplicate and Low-Quality Documents

The knowledge base itself can affect retrieval quality.

Check for:

- Duplicate documents
- Outdated documents
- Empty or corrupted text
- Poorly extracted content
- Irrelevant documents
- Incorrect metadata

Cleaning the indexed data can significantly improve retrieval.

---

### 10. Evaluate Retrieval Separately

Do not immediately assume that the LLM is the problem.

First determine whether the retriever is actually returning relevant documents.

For example:

```text
User Query
    ↓
Retrieved Documents
    ↓
Are documents relevant?
   ↙       ↘
 Yes       No
 ↓          ↓
Check LLM   Improve Retrieval
            ↓
       Chunking / Embeddings
       Query / Search / Reranking
```

Useful retrieval metrics include:

- Precision@k
- Recall@k
- Retrieval relevance

This helps identify whether the problem is in **retrieval** or **generation**.

---

### Recommended Improvement Pipeline

A practical approach could be:

```text
Poor Retrieval
      ↓
Check Documents & Chunking
      ↓
Check Embedding Model
      ↓
Improve Query
      ↓
Use Metadata Filtering
      ↓
Use Hybrid / Multi-Query Retrieval
      ↓
Rerank Results
      ↓
Tune Top-k
      ↓
Evaluate Precision@k / Recall@k
      ↓
Monitor and Iterate
```

### Key Point

**To improve irrelevant retrieval, first diagnose the retrieval stage and then improve chunking, embeddings, query formulation, search strategy, metadata filtering, reranking, and top-k selection. Retrieval should be evaluated separately from generation.**

### Interview Answer

> **If a RAG system retrieves irrelevant documents, I would first diagnose the retrieval stage rather than immediately changing the LLM. I would check the document quality and chunking strategy, evaluate the embedding model, improve the query using query rewriting or multi-query retrieval, and consider hybrid search and metadata filtering. I would also add a reranking stage to improve the ordering of retrieved candidates and tune the top-k value. Finally, I would evaluate retrieval using metrics such as Precision@k and Recall@k to determine whether the changes actually improve retrieval quality.**
