# 06. Agent Frameworks & Architecture

This section focuses on understanding **LangChain, LangGraph, workflows, agents, and the underlying architecture** behind tool-calling systems.

The goal is not just to learn framework syntax, but to understand what the framework is actually doing internally.

---

## 1. What is LangChain and where does it fit in an agent architecture?

### Answer

**LangChain** is a framework for building applications powered by LLMs.

It provides reusable components for:

- Calling LLMs
- Prompt management
- Tool calling
- Agents
- Retrieval/RAG
- Memory/state
- Output parsing
- Connecting external APIs and services

Instead of manually writing all the code for an LLM application, LangChain provides abstractions that make these components easier to connect.

### Where does LangChain fit?

LangChain generally sits in the **application/orchestration layer** between the LLM and external tools/data sources.

```text
                User
                  |
                  v
          Application / LangChain
                  |
          +-------+-------+
          |               |
          v               v
         LLM            Tools
          |               |
          |          +----+----+
          |          |    |    |
          |         API  DB  Search
          |
          v
      Final Response
```

For an agent, LangChain can help manage:

```text
User Request
     |
     v
   Agent
     |
     v
    LLM
     |
     +----> Tool 1
     |
     +----> Tool 2
     |
     +----> Tool 3
     |
     v
 Final Answer
```

### Example

Suppose the user asks:

> "What is the weather in Delhi and convert the temperature to Fahrenheit?"

An agent could use:

1. Weather tool
2. Calculator tool

LangChain can provide abstractions for defining these tools and connecting them to the agent.

### Important distinction

LangChain is **not the LLM itself**.

It is a framework used to build and orchestrate LLM applications.

```text
LLM              → Generates/decides
Tools            → Perform external actions
LangChain        → Helps connect and orchestrate them
Application      → Controls execution and safety
```

### Key Point

> **LangChain is an application framework that provides building blocks for LLM applications, including agents, tools, retrieval, prompts, and model interactions.**

### Interview Answer

> **LangChain is a framework used to build LLM-powered applications. In an agent architecture, it can provide abstractions for the LLM, tools, prompts, tool calling, and agent execution. It sits in the application/orchestration layer and helps connect the model with external tools and data sources.**

## 2. What is LangGraph and why is it useful for agentic applications?

### Answer

**LangGraph** is a framework for building **stateful, multi-step, and agentic workflows** using a graph-based architecture.

Instead of thinking about an application as just a sequence of functions, LangGraph represents the application as:

- **Nodes** → actions or processing steps
- **Edges** → transitions between steps
- **State** → information shared between steps

### Basic idea

```text
                 +----------------+
                 |      Start     |
                 +-------+--------+
                         |
                         v
                 +----------------+
                 |      Agent     |
                 +-------+--------+
                         |
                    Decide action
                    /           \
                   /             \
                  v               v
             Tool Call        Final Answer
                  |
                  v
            Update State
                  |
                  +-------> Agent
```

This is useful because agents often need to:

- Perform multiple steps
- Call multiple tools
- Maintain state
- Make decisions based on previous results
- Repeat certain steps
- Handle errors
- Branch into different paths
- Stop when a condition is satisfied

### Why a graph?

A graph makes the execution flow explicit.

For example:

```text
START
  |
  v
Research
  |
  v
Need More Information?
   /        \
 Yes         No
 |            |
 v            v
Search      Generate
 |            |
 +----->-----+
        |
        v
      END
```

The agent can move through different paths depending on the state.

### LangChain vs LangGraph

A simple way to remember:

```text
LangChain
    ↓
Components and abstractions for LLM applications

LangGraph
    ↓
Stateful graph-based orchestration for complex workflows/agents
```

LangGraph is particularly useful when an application requires explicit control over **state, loops, branching, and multi-step execution**.

### Key Point

> **LangGraph models agentic applications as graphs containing nodes, edges, and shared state, making complex multi-step and stateful execution easier to manage.**

### Interview Answer

> **LangGraph is a framework for building stateful agentic applications using a graph of nodes and transitions. It is useful when an agent needs loops, branching, multiple tool calls, persistent state, or controlled multi-step execution.**

## 3. What is the difference between a chain, workflow, and agent?

### Answer

These three concepts differ mainly in **how the next step is determined**.

### 1. Chain

A **chain** follows a predefined sequence of operations.

```text
Input
  |
  v
Step 1
  |
  v
Step 2
  |
  v
Step 3
  |
  v
Output
```

Example:

```text
Question
   ↓
Prompt
   ↓
LLM
   ↓
Formatter
   ↓
Answer
```

The sequence is mostly fixed.

---

### 2. Workflow

A **workflow** is a predefined process that may contain:

- Multiple steps
- Conditions
- Branches
- Parallel operations
- Loops

Example:

```text
          Start
            |
            v
       Validate Input
            |
        +---+---+
        |       |
      Valid   Invalid
        |       |
        v       v
     Process   Error
        |
        v
       End
```

The flow is designed by the developer.

---

### 3. Agent

An **agent** dynamically decides what action to take next.

```text
             User Goal
                 |
                 v
               Agent
                 |
          Decide next action
          /       |       \
         v        v        v
       Search    API      Calculator
         |        |        |
         +--------+--------+
                  |
                  v
              Observe Result
                  |
                  v
               Agent
                  |
             Decide Again
```

The exact sequence is not completely predefined.

### Comparison

| Feature | Chain | Workflow | Agent |
|---|---|---|---|
| Flow | Fixed | Predefined | Dynamic |
| Decision making | Low | Developer-defined | Model-driven |
| Branching | Limited | Yes | Dynamic |
| Tool selection | Usually fixed | Usually predefined | Can be dynamic |
| Predictability | High | High | Lower |
| Flexibility | Low | Medium | High |
| Control | High | High | Lower |
| Best for | Simple pipelines | Known processes | Dynamic tasks |

### Example

Suppose we want to process a customer complaint.

**Chain:**

```text
Complaint → LLM → Classify → Response
```

**Workflow:**

```text
Complaint
    ↓
Classify
    ↓
Billing? ──Yes──> Billing Process
    |
    No
    ↓
Technical? ──Yes──> Technical Process
```

**Agent:**

```text
Complaint
    ↓
Agent decides:
"Should I search customer history?"
"Should I query billing?"
"Should I call support API?"
"Should I ask the user?"
```

### Key Point

> **A chain follows a fixed sequence, a workflow follows a developer-defined process with possible branches, while an agent dynamically chooses its next actions based on the current goal and state.**

### Interview Answer

> **A chain is a fixed sequence of operations. A workflow is a predefined process that can contain branching and conditions. An agent is more dynamic because the model decides which action or tool to use next based on the task and current state.**

## 4. What is a state graph in an agent framework?

### Answer

A **state graph** represents an agentic application as a collection of:

- **State**
- **Nodes**
- **Edges**
- **Transitions**

The **state** contains the information required to know what has happened and what should happen next.

### Components

#### 1. State

State contains information such as:

```text
state = {
    user_query,
    conversation_history,
    tool_results,
    current_step,
    retrieved_documents,
    final_answer
}
```

#### 2. Nodes

Nodes perform operations.

Examples:

```text
Agent Node
Search Node
Database Node
Calculator Node
Validation Node
Final Response Node
```

#### 3. Edges

Edges determine where execution goes next.

```text
Agent → Search
Agent → Calculator
Agent → Final Answer
```

#### 4. Conditional transitions

The next node can depend on the current state.

```text
                 Agent
                   |
            What should happen?
             /       |       \
            /        |        \
           v         v         v
        Search    Database   Answer
           |         |
           +----+----+
                |
                v
              Agent
```

### Why state is important

Consider an agent that performs:

```text
Search → Tool → Search → Final Answer
```

The agent needs to remember:

- What the original question was
- What search was performed
- What the tool returned
- What information is still missing
- Which step it is currently on

That information is stored in the state.

### Simple example

```text
State:
{
    question: "Find the price of X",
    search_result: "...",
    price: 500,
    currency: "INR"
}
```

After the search node:

```text
State
  ↓
Search Node
  ↓
Updated State
  ↓
Agent Node
  ↓
Final Answer
```

### Key Point

> A state graph represents an agent as nodes and transitions operating on shared state. It makes multi-step, branching, and looping agent execution easier to control.

### Interview Answer

> **A state graph is a graph-based representation of an agent where nodes perform actions, edges define transitions, and a shared state stores information about the current task and previous results. It is useful for managing multi-step, branching, and looping agent workflows.**

## 5. When should you avoid using an agent framework?

### Answer

An agent framework should not automatically be used for every LLM application.

If the problem is simple and predictable, using a framework may add unnecessary complexity.

### Avoid an agent framework when:

#### 1. The workflow is very simple

Example:

```text
Input
  ↓
Prompt
  ↓
LLM
  ↓
Output
```

There may be no need for an agent framework.

---

#### 2. The execution path is completely deterministic

For example:

```text
Get User
   ↓
Validate User
   ↓
Fetch Orders
   ↓
Generate Report
```

If the steps are always the same, ordinary application code may be easier.

---

#### 3. You need maximum control

In some applications you may want every step to be explicitly controlled.

```text
if user_is_valid:
    fetch_data()
else:
    return_error()
```

A custom workflow can be easier to reason about.

---

#### 4. Latency is extremely important

Framework abstractions can introduce additional processing or complexity.

For a very latency-sensitive application, a minimal custom implementation may be preferable.

---

#### 5. The framework abstraction hides important behavior

If developers do not understand:

- Tool execution
- State
- Retries
- Agent loops
- Error handling
- Prompt construction

then debugging can become difficult.

---

#### 6. The project is small

For a small prototype:

```text
LLM API
   +
One or two functions
```

may be enough.

You do not necessarily need a full agent framework.

### Framework vs custom implementation

| Situation | Suitable approach |
|---|---|
| Simple LLM call | Direct LLM API |
| Fixed pipeline | Custom code/workflow |
| Simple tool calling | Direct tool-calling API |
| Complex stateful agent | Agent framework |
| Multiple tools + loops | Agent framework can help |
| Complex branching | Graph/workflow framework can help |
| Highly specialized execution | Custom architecture may be better |

### Important principle

> Use a framework because it solves a problem, not simply because the application uses an LLM.

### Key Point

> If the workflow is simple, deterministic, small, or requires very tight control, a custom implementation can be simpler than introducing an agent framework.

### Interview Answer

> **I would avoid an agent framework when the task is simple, deterministic, or requires very tight control over execution. In such cases, direct LLM APIs and normal application code may be easier to understand, debug, and maintain. Frameworks become more useful as state, tools, branching, loops, and orchestration complexity increase.**

## 6. How would you implement a simple tool-calling agent without LangChain/LangGraph?

### Answer

This is an important interview question because it tests whether you understand the **underlying architecture** instead of only knowing framework syntax.

A simple tool-calling agent can be implemented using:

- An LLM API
- Tool definitions
- Normal application code
- A loop
- Tool execution functions
- Structured tool results
- State/history

You do **not** fundamentally need LangChain or LangGraph.

---

### Step 1: Define the tools

Suppose we have a calculator tool.

```text
Tool:
calculate(expression)
```

Its schema could look like:

~~~json
{
  "name": "calculate",
  "description": "Evaluate a mathematical expression",
  "parameters": {
    "type": "object",
    "properties": {
      "expression": {
        "type": "string"
      }
    },
    "required": ["expression"]
  }
}
~~~

The LLM receives the tool description.

---

### Step 2: Send the user request and tools to the LLM

```text
User
 |
 | "What is 25 * 16?"
 v
Application
 |
 | User request + tool definitions
 v
LLM
```

The LLM may decide:

```json
{
  "tool": "calculate",
  "arguments": {
    "expression": "25 * 16"
  }
}
```

The LLM is **requesting** the tool call.

It is not directly executing the function.

---

### Step 3: Application validates the tool call

The application receives the structured request.

```text
LLM
 |
 | tool = calculate
 | expression = "25 * 16"
 v
Application
 |
 +--> Is tool allowed?
 +--> Are arguments valid?
 +--> Does schema match?
```

Only after validation should the application execute the function.

---

### Step 4: Execute the tool

Normal application code performs the actual operation.

```text
calculate("25 * 16")
        |
        v
       400
```

---

### Step 5: Send the tool result back to the LLM

```text
Tool Result:
400
```

The application sends this result back as part of the conversation/state.

```text
User Request
      +
Tool Call
      +
Tool Result
      |
      v
     LLM
```

The LLM can now generate the final answer.

```text
"What is 25 * 16?"

        ↓

LLM requests calculator

        ↓

Application executes calculator

        ↓

Result = 400

        ↓

LLM

        ↓

"25 × 16 = 400"
```

---

### Complete architecture

~~~text
                    User
                      |
                      v
              +---------------+
              |  Application  |
              +-------+-------+
                      |
              Request + Tools
                      |
                      v
                 +---------+
                 |   LLM   |
                 +----+----+
                      |
                Tool Decision
                      |
                      v
              Structured Call
                      |
                      v
              +---------------+
              |  Application  |
              |   Validator   |
              +-------+-------+
                      |
                  Execute Tool
                      |
                      v
              +---------------+
              | External Tool |
              +-------+-------+
                      |
                  Tool Result
                      |
                      v
              +---------------+
              |  Application  |
              +-------+-------+
                      |
                Result + State
                      |
                      v
                 +---------+
                 |   LLM   |
                 +----+----+
                      |
                      v
                Final Answer
~~~

---

### The agent loop

For a more general agent, put the process inside a loop.

~~~text
User Request
     |
     v
    LLM
     |
     v
Tool call needed?
   /       \
 No         Yes
 |           |
 v           v
Answer    Validate
             |
             v
          Execute
             |
             v
         Tool Result
             |
             v
         Update State
             |
             +-------> LLM
~~~

Pseudo-code:

~~~python
messages = [user_message]

while True:

    response = llm(
        messages=messages,
        tools=available_tools
    )

    if response.has_tool_call():

        tool_call = response.tool_call

        # 1. Validate tool
        # 2. Validate arguments
        # 3. Check permissions

        result = execute_tool(
            tool_call.name,
            tool_call.arguments
        )

        messages.append(response)
        messages.append({
            "role": "tool",
            "content": result
        })

    else:
        return response.text
~~~

This is the core idea behind a simple tool-calling agent.

---

### Production considerations

A real implementation should also include:

```text
Input validation
      ↓
Tool allowlist
      ↓
Argument validation
      ↓
Authentication / authorization
      ↓
Timeouts
      ↓
Retry limits
      ↓
Maximum agent steps
      ↓
Logging / tracing
      ↓
Error handling
```

For example:

```python
MAX_STEPS = 5

for step in range(MAX_STEPS):

    response = llm(...)

    if response.has_tool_call():
        validate_tool_call(response)
        result = execute_tool(...)
        update_state(result)
    else:
        return response.text

return "Maximum agent steps reached."
```

This prevents the agent from running indefinitely.

---

### What frameworks are actually helping with

Once you understand the manual implementation, frameworks become easier to understand.

A framework may provide abstractions for:

```text
Tool definitions
      ↓
LLM interaction
      ↓
Tool selection
      ↓
Tool execution
      ↓
State management
      ↓
Agent loop
      ↓
Retries / errors
      ↓
Tracing / observability
```

So the framework is **not magic**.

It is mainly providing reusable abstractions around the architecture you could implement yourself.

### Key Point

> **A simple tool-calling agent can be implemented without LangChain or LangGraph using an LLM API, tool schemas, application-side tool execution, state/history, and an agent loop.**

### Interview Answer

> **I would first define the available tools with structured schemas. I would send the user request and tool definitions to the LLM. If the LLM returns a tool call, my application would validate the tool name and arguments, check permissions, execute the corresponding function, and send the tool result back to the LLM. I would repeat this loop until the LLM produces a final answer or a safety limit such as maximum steps or timeout is reached. This is essentially the underlying architecture that agent frameworks help orchestrate.**
