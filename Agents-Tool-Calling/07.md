# 07. Agent + RAG + Tools

This section connects the two major concepts:

```text
RAG
 ↓
Retrieval of relevant information
 ↓
Agents
 ↓
Dynamic decision-making + tool usage
```

The key idea is that **RAG can itself be exposed as a tool**, allowing an agent to decide when retrieval is necessary and combine retrieval with other tools.

---

## 1. How can an agent use RAG as a tool?

### Answer

An agent can treat the **retrieval part of a RAG system as a tool**.

Instead of always performing retrieval for every user question, the agent can decide:

> "I need information from the knowledge base, so I should call the retrieval tool."

### Basic architecture

```text
                  User
                    |
                    v
                 Agent
                    |
             Decide next action
                    |
             +------+------+
             |             |
             v             v
          RAG Tool      Other Tool
             |          (Calculator/API)
             v
       Retrieve Documents
             |
             v
       Relevant Chunks
             |
             +------> Agent
                         |
                         v
                    Final Answer
```

### RAG as a tool

A retrieval tool could conceptually look like:

```text
search_knowledge_base(query)
```

For example:

```json
{
  "name": "search_knowledge_base",
  "description": "Search the company's internal documents",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string"
      }
    },
    "required": ["query"]
  }
}
```

The agent sees this as one of its available tools.

---

### Example

User asks:

> "What is our company's leave policy?"

The agent decides:

```text
User Question
      |
      v
    Agent
      |
      | Need internal information
      v
RAG Retrieval Tool
      |
      v
Company Documents
      |
      v
Relevant Chunks
      |
      v
    Agent
      |
      v
Final Answer
```

The agent can then use the retrieved information to generate the answer.

---

### RAG tool can contain the whole retrieval pipeline

The tool does not necessarily have to expose only vector search.

Internally it could perform:

```text
Query
  ↓
Query Processing
  ↓
Embedding
  ↓
Vector / Hybrid Search
  ↓
Metadata Filtering
  ↓
Reranking
  ↓
Relevant Chunks
```

From the agent's perspective, this can simply be:

```text
search_knowledge_base(query)
```

### Key Point

> **RAG can be exposed as a tool that an agent calls whenever it needs information from a specific knowledge base.**

### Interview Answer

> **I can expose the retrieval part of a RAG pipeline as a tool, for example `search_knowledge_base(query)`. The agent decides when retrieval is needed, calls the tool, receives relevant documents or chunks, and then uses those results to generate the final answer.**

---

## 2. What is the difference between a RAG pipeline and an agent that can perform retrieval?

### Answer

The main difference is **who controls the retrieval process and how flexible the execution is**.

### RAG Pipeline

A traditional RAG pipeline usually follows a predefined flow:

```text
User Query
    |
    v
Query Processing
    |
    v
Retrieve Documents
    |
    v
Rerank
    |
    v
Construct Context
    |
    v
LLM
    |
    v
Answer
```

Retrieval is normally part of the fixed pipeline.

---

### Agent with Retrieval

An agent can decide whether retrieval is necessary and potentially perform retrieval multiple times.

```text
User Query
    |
    v
  Agent
    |
    +----> Answer directly
    |
    +----> Search knowledge base
    |
    +----> Web search
    |
    +----> Database
    |
    v
Observe results
    |
    v
Decide next action
    |
    v
Final Answer
```

### Example

User asks:

> "What is 2 + 2?"

A traditional RAG pipeline might still perform retrieval if retrieval is always part of the pipeline.

An agent could decide:

```text
Question
   ↓
Agent
   ↓
Simple calculation
   ↓
Answer directly
```

Now consider:

> "According to our internal HR policy, how many paid leaves are available?"

The agent can decide:

```text
Question
   ↓
Agent
   ↓
Internal knowledge required
   ↓
RAG Tool
   ↓
Retrieve policy
   ↓
Answer
```

### Comparison

| Feature | RAG Pipeline | Agent + Retrieval |
|---|---|---|
| Retrieval | Usually predefined | Dynamically selected |
| Flow | Mostly fixed | Dynamic |
| Multiple tools | Not necessarily | Yes |
| Multiple retrieval calls | Usually controlled by pipeline | Can be dynamic |
| Decision making | Application-defined | Agent/model can decide |
| Complexity | Lower | Higher |
| Predictability | Higher | Lower |
| Flexibility | Lower | Higher |

### Important distinction

An agent using RAG **does not replace RAG**.

Instead:

```text
RAG = Retrieval capability

Agent = Decision-making/orchestration layer
```

So:

```text
              Agent
                |
       +--------+--------+
       |        |        |
       v        v        v
      RAG      API     Calculator
```

### Key Point

> **A traditional RAG pipeline usually retrieves as part of a predefined flow, while an agent with retrieval can decide when, whether, and potentially how many times to retrieve.**

### Interview Answer

> **In a normal RAG pipeline, retrieval is a predefined part of the execution flow. In an agentic system, retrieval can be exposed as a tool, and the agent decides whether retrieval is necessary based on the task and current state. The agent can also combine retrieval with other tools.**

---

## 3. How would an agent decide whether to retrieve information or answer directly?

### Answer

The agent can make this decision based on:

- User query
- Available tools
- Tool descriptions
- Instructions
- Current state
- Conversation context
- Whether the required information is already known
- Whether external or private information is required

Conceptually:

```text
                  User Query
                       |
                       v
                     Agent
                       |
               Understand the task
                       |
             +---------+---------+
             |                   |
      Information needed?      No
             |                   |
            Yes                  v
             |              Answer Directly
             v
        Retrieve Information
```

### Example 1 — Direct Answer

User:

> "What is the capital of France?"

If the model already knows the answer and there is no requirement to use an external source:

```text
Question
   ↓
Agent
   ↓
No retrieval needed
   ↓
Answer
```

---

### Example 2 — Retrieval Required

User:

> "What is our company's reimbursement policy?"

The information is likely inside company documents.

```text
Question
   ↓
Agent
   ↓
Internal information required
   ↓
RAG Tool
   ↓
Retrieve policy
   ↓
Answer
```

---

### Example 3 — Current Information Required

User:

> "What is the current price of this product?"

If the agent has a product/API/search tool:

```text
Question
   ↓
Agent
   ↓
Current information required
   ↓
API / Search Tool
   ↓
Current Result
   ↓
Answer
```

---

### Example 4 — Multiple sources

User:

> "Compare our internal sales report with the latest market data."

The agent may need:

```text
                 Agent
                   |
          +--------+--------+
          |                 |
          v                 v
      Internal RAG      External Search/API
          |                 |
          v                 v
     Company Data       Market Data
          |                 |
          +--------+--------+
                   |
                   v
                Agent
                   |
                   v
               Comparison
```

### Important point

The decision should not simply be:

> "Always retrieve."

Instead, retrieval should be selected when it provides information that is:

- Required
- More reliable than the model's existing knowledge
- Private/internal
- Current or changing
- Specific to the organization's data

### Key Point

> **The agent decides whether to retrieve based on the task requirements, available context, and whether external, private, or up-to-date information is needed.**

### Interview Answer

> **I would provide retrieval as a tool and instruct the agent about when it is useful. The agent can answer directly when the required information is already available and reliable, but it should retrieve when the question depends on private, current, domain-specific, or externally stored information.**

## 4. How can an agent combine multiple tools such as search, database queries, APIs, and calculators?

### Answer

An agent can treat every capability as a separate tool and dynamically decide which tools to use.

For example:

```text
Tools:

1. Web Search
2. Database Query
3. Product API
4. Calculator
5. RAG Retrieval
```

The agent acts as the orchestrator.

### Basic architecture

```text
                    User
                      |
                      v
                   Agent
                      |
             Decide next action
                      |
        +------+------+------+------+------+
        |      |      |      |      |      
        v      v      v      v      v
      Search  DB     API  Calculator  RAG
        |      |      |      |         |
        +------+------+------+------+--+
                      |
                      v
                  Tool Results
                      |
                      v
                    Agent
                      |
              Decide next action
                      |
                      v
                 Final Answer
```

### Example

User asks:

> "Find the sales of Product A from our database, get its current market price, calculate the percentage difference, and explain the result."

The agent might perform:

```text
1. Database Tool
       ↓
   Sales = ₹80,000

2. Product API
       ↓
   Market Price = ₹75,000

3. Calculator
       ↓
   Percentage Difference

4. Agent
       ↓
   Generate explanation
```

The important part is that the agent can use the **result of one tool as input to another tool**.

### Sequential tool use

```text
User
 ↓
Agent
 ↓
Database
 ↓
Database Result
 ↓
Agent
 ↓
API
 ↓
API Result
 ↓
Agent
 ↓
Calculator
 ↓
Result
 ↓
Agent
 ↓
Final Answer
```

### Parallel tool use

If two tools are independent, they may be executed in parallel.

For example:

```text
                 Agent
                   |
             Need two sources
              /           \
             v             v
      Internal RAG      Web Search
             |             |
             v             v
          Result         Result
              \           /
               \         /
                 Agent
                   |
                   v
               Final Answer
```

Parallel execution can reduce latency when the tools do not depend on each other's results.

### Tool selection

The agent can choose tools based on:

```text
User Goal
   +
Tool Descriptions
   +
Tool Schemas
   +
Current State
   +
Previous Tool Results
```

### Important design principle

The application should still control:

```text
Tool permissions
Argument validation
Authentication
Timeouts
Retries
Maximum steps
Error handling
```

The agent should **request** tool usage, while the application controls actual execution.

### Key Point

> **Multiple tools can be combined by allowing the agent to select and sequence them based on the task, with each tool result being added to the agent's state for subsequent decisions.**

### Interview Answer

> **I would expose search, database queries, APIs, calculators, and RAG retrieval as separate tools with clear schemas. The agent can select the appropriate tool, inspect its result, and then decide whether another tool is required. Independent tools can potentially run in parallel, while dependent operations are executed sequentially.**

## 5. How would you design an agent that researches a question using multiple sources and produces a final answer?

### Answer

A research agent can combine:

- Web search
- Internal RAG
- Databases
- APIs
- Multiple retrieval operations
- A synthesis/final-answer step

The agent should not simply collect information. It should **plan, retrieve, evaluate, combine, and synthesize** the results.

---

### High-level architecture

```text
                         User Question
                              |
                              v
                        Research Agent
                              |
                       Understand Goal
                              |
                              v
                      Create Research Plan
                              |
              +---------------+---------------+
              |               |               |
              v               v               v
         Web Search       Internal RAG     Database/API
              |               |               |
              v               v               v
         Source A/B        Source C        Source D
              |               |               |
              +---------------+---------------+
                              |
                              v
                       Gather Results
                              |
                              v
                    Filter / Validate Results
                              |
                              v
                         Synthesize
                              |
                              v
                        Final Answer
```

---

### Step 1: Understand the question

Suppose the user asks:

> "Compare our product's performance with the current market and explain the major differences."

The agent first determines what information is required.

```text
Required:

1. Internal product performance
2. Current market information
3. Relevant metrics
4. Comparison
5. Explanation
```

---

### Step 2: Create a research plan

The agent can decide:

```text
Task 1 → Query internal company documents
Task 2 → Search current market information
Task 3 → Retrieve database metrics
Task 4 → Compare results
Task 5 → Generate final report
```

---

### Step 3: Use multiple sources

```text
                  Agent
                    |
       +------------+------------+
       |            |            |
       v            v            v
   RAG Search    Web Search    Database
       |            |            |
       v            v            v
 Internal Docs   Market Data   Company Data
       |            |            |
       +------------+------------+
                    |
                    v
               Agent State
```

The agent keeps the results in its state.

---

### Step 4: Validate and organize information

The system should distinguish between:

```text
Source
Claim
Value
Date
Confidence / relevance
```

For example:

```text
Source: Internal sales report
Metric: Q3 revenue
Value: ₹10 crore
Date: Q3 2026
```

This makes the final synthesis easier and reduces confusion between sources.

---

### Step 5: Decide whether more research is needed

After receiving the first results, the agent can decide:

```text
Is the information sufficient?
        |
    +---+---+
    |       |
   Yes      No
    |        |
    v        v
Synthesize  Search Again
              |
              v
           Update State
              |
              +----> Agent
```

This is where an agent differs from a simple fixed RAG pipeline.

---

### Step 6: Synthesize the final answer

Once enough information has been gathered:

```text
Sources
   |
   v
Collected Evidence
   |
   v
Agent / LLM
   |
   v
Structured Analysis
   |
   v
Final Answer
```

The final answer should ideally distinguish:

```text
Fact
Source
Analysis
Uncertainty
```

For example:

```text
Internal data shows X.

External market data reports Y.

Therefore, the observed difference is Z.
```

---

### Example research workflow

```text
User:
"Research why Product A's sales decreased."

             |
             v
       Research Agent
             |
       +-----+------+
       |            |
       v            v
   Internal RAG   Web Search
       |            |
       v            v
Sales Reports    Market News
       |            |
       +-----+------+
             |
             v
       Database Query
             |
             v
       Customer Data
             |
             v
       Agent analyzes
             |
       Need more data?
          /      \
        Yes       No
         |         |
         v         v
    More Search  Synthesis
                   |
                   v
              Final Report
```

---

### Tool architecture

The agent might have tools such as:

```text
search_web(query)
search_internal_docs(query)
query_database(sql_or_parameters)
call_market_api(parameters)
calculate(expression)
```

The application controls which tools are available and what permissions they have.

---

### Important production considerations

A research agent should have:

#### 1. Source tracking

Keep track of where each piece of information came from.

```text
Claim → Source → Retrieved Result
```

#### 2. Tool limits

Prevent unlimited research:

```text
MAX_STEPS = 10
MAX_SEARCHES = 5
TIMEOUT = 60 seconds
```

#### 3. Validation

Validate:

- Tool arguments
- Retrieved data
- API responses
- Database results

#### 4. Deduplication

Multiple sources may provide the same information.

```text
Source A ──┐
Source B ──┼──> Deduplicate
Source C ──┘
```

#### 5. Error handling

A source may fail:

```text
Web Search → Timeout
                 |
                 v
          Retry / Alternate Source
```

#### 6. Grounded generation

The final answer should be based on the retrieved evidence rather than unsupported claims.

---

### RAG → Agent progression

This is the key concept behind this section.

### Traditional RAG

```text
Question
   ↓
Retrieve
   ↓
Context
   ↓
LLM
   ↓
Answer
```

### Agent + RAG

```text
Question
   ↓
Agent
   |
   +----> RAG
   |
   +----> Search
   |
   +----> Database
   |
   +----> API
   |
   +----> Calculator
   |
   v
Results
   |
   v
Agent
   |
   v
Final Answer
```

So the progression is:

```text
RAG
↓
Retrieval capability

Agent
↓
Decision-making + orchestration

Agent + RAG
↓
Agent can decide when and how to retrieve
```

### Key Point

> **A research agent can plan a question, use multiple retrieval and external tools, maintain the collected evidence in state, decide whether additional research is required, and finally synthesize a grounded answer.**

### Interview Answer

> **I would design the system with a research agent and several tools such as web search, internal RAG, database queries, and APIs. The agent would first understand the question and create a research plan, then call the appropriate tools and store their results in state. After evaluating whether enough information has been collected, it can perform additional searches if needed and finally synthesize the evidence into a final answer. I would also add source tracking, validation, timeouts, retries, and maximum-step limits.**

## Most Important Interview Concept

```text
RAG answers:
"How do I retrieve relevant information?"

Agents answer:
"What should I do next?"

Agent + RAG answers:
"When should I retrieve information,
what should I retrieve,
and what should I do with the result?"
```

The important progression to remember is:

```text
RAG
  ↓
Retrieval capability
  ↓
Agent
  ↓
```
