# 09. Production & Debugging

Once an agent works in a prototype, the next challenge is making it **reliable, fast, cost-efficient, observable, and safe in production**.

A production agent should not be treated as:

```text
User → LLM → Answer
```

Instead, it should be treated as a system:

```text
User
 ↓
Agent / Orchestrator
 ↓
LLM
 ↓
Tools
 ↓
External Systems
 ↓
Results
 ↓
LLM
 ↓
Final Answer
```

with monitoring, limits, validation, security, and error handling around it.

---

## 1. How would you debug an agent that chooses the wrong tool?

### Answer

If an agent repeatedly selects the wrong tool, I would not immediately change the model.

First, I would trace the complete decision process.

```text
User Request
     ↓
Prompt / Instructions
     ↓
Available Tool Definitions
     ↓
LLM Tool Selection
     ↓
Selected Tool
     ↓
Arguments
```

### Step 1: Inspect the user request

Check whether the request itself is ambiguous.

Example:

```text
"Get the price of the product."
```

Could mean:

```text
Internal database price?
Current market price?
Historical price?
```

If the task is ambiguous, the agent may legitimately choose the wrong tool.

---

### Step 2: Check tool descriptions

Tool descriptions are extremely important.

Bad:

```text
get_data()
```

Better:

```text
get_current_market_price(product_id)

Returns the current market price of a product.
Use this when the user asks for the current external
market price.
```

The LLM uses tool descriptions to understand when a tool is appropriate.

---

### Step 3: Check tool schemas

Make sure the schema clearly describes:

```text
Tool name
Description
Parameters
Parameter types
Required fields
Allowed values
```

Poor schemas can lead to incorrect tool selection or arguments.

---

### Step 4: Check system instructions

Verify that the agent has clear instructions.

For example:

```text
Use the internal database tool for company sales data.

Use web search only when current external information
is required.
```

---

### Step 5: Inspect the complete trace

Log:

```text
User input
 ↓
System instructions
 ↓
Available tools
 ↓
LLM response
 ↓
Selected tool
 ↓
Arguments
 ↓
Tool result
```

This tells us whether the problem came from:

- Ambiguous user request
- Poor tool description
- Poor system instructions
- Incorrect tool schema
- Model decision
- Incorrect state/context

---

### Step 6: Test tool selection independently

Create test cases:

```text
Question A → Expected Tool A
Question B → Expected Tool B
Question C → Expected Tool C
```

For example:

```text
"What's the weather?"
→ weather_tool

"Calculate 25 * 10"
→ calculator

"What is our leave policy?"
→ internal_rag
```

This creates a tool-selection evaluation set.

---

### Step 7: Consider simplifying the tool set

If multiple tools have very similar descriptions:

```text
search_database()
search_documents()
search_internal_data()
search_information()
```

the model may struggle to distinguish them.

Make tools:

- Clearly named
- Clearly described
- Non-overlapping where possible

### Key Point

> **To debug wrong tool selection, inspect the request, instructions, tool descriptions, schemas, model decision, and execution trace rather than changing the model blindly.**

### Interview Answer

> **I would first trace the complete request from the user input to the selected tool. I would check whether the request is ambiguous, whether tool descriptions and schemas clearly distinguish the tools, and whether the system instructions correctly define when each tool should be used. I would then create test cases mapping representative queries to expected tools and measure tool-selection accuracy.**

---

## 2. How would you debug an agent that repeatedly calls the same tool?

### Answer

Repeated tool calls usually indicate a problem with:

- Stop conditions
- State updates
- Tool results
- Agent instructions
- Error handling
- Retry logic

### Example

```text
Agent
 ↓
Search Tool
 ↓
Result
 ↓
Agent
 ↓
Search Tool
 ↓
Same Result
 ↓
Agent
 ↓
Search Tool
 ↓
...
```

This can become an infinite loop.

---

### Step 1: Inspect the execution trace

Log every step:

```text
Step 1 → search("Python")
Step 2 → search("Python")
Step 3 → search("Python")
Step 4 → search("Python")
```

Look for repeated:

- Tool name
- Arguments
- Tool results
- Agent state

---

### Step 2: Check whether state is being updated

The agent needs to know what happened previously.

```text
Before:
state = {
    question: "...",
    search_done: false
}
```

After execution:

```text
state = {
    question: "...",
    search_done: true,
    search_result: "..."
}
```

If the state is not updated, the agent may believe that the tool still needs to be called.

---

### Step 3: Check tool results

A tool may be returning:

```text
Empty result
```

or:

```text
Error
```

The agent may interpret this as:

> "I need to search again."

If that happens repeatedly, the system loops.

---

### Step 4: Check stopping conditions

The system should define conditions such as:

```text
Task completed
OR
Maximum steps reached
OR
Timeout
OR
No useful progress
```

Example:

```python
MAX_STEPS = 8
```

---

### Step 5: Limit repeated calls

You can track calls:

```python
tool_calls = {}

tool_calls[tool_name] = tool_calls.get(tool_name, 0) + 1

if tool_calls[tool_name] > 3:
    stop_agent()
```

For more robust systems, the limit can also consider identical arguments.

```text
search("Python")
search("Python")
search("Python")
```

This is stronger evidence of a loop than simply calling the same tool with different queries.

---

### Step 6: Check retry logic

Sometimes the problem is not the agent itself.

For example:

```text
Tool fails
 ↓
Retry
 ↓
Tool fails
 ↓
Agent retries
 ↓
Retry
 ↓
Agent retries
```

There may be multiple retry layers.

```text
Agent retry
+
Tool retry
+
API retry
```

These should be bounded.

### Key Point

> **Repeated tool calls should be debugged by examining state updates, tool results, stopping conditions, retry logic, and repeated tool arguments.**

### Interview Answer

> **I would inspect the execution trace and check whether the state is updated after every tool call. I would also verify the tool result, stopping conditions, and retry logic. I would add maximum-step and repeated-tool-call limits so that an agent cannot enter an infinite loop.**

# 3. How would you reduce agent latency?

### Answer

Agent latency can increase because an agent may perform:

```text
LLM Call
 ↓
Tool
 ↓
LLM Call
 ↓
Tool
 ↓
LLM Call
 ↓
Final Answer
```

The first step is to measure where the time is actually being spent.

### Measure the complete pipeline

```text
Total Latency
    =
LLM latency
+
Tool latency
+
Network latency
+
Database latency
+
Reranking/search latency
+
Other processing
```

---

### 1. Reduce unnecessary LLM calls

Instead of:

```text
LLM
 ↓
LLM
 ↓
LLM
 ↓
LLM
```

design the workflow so that one model call can accomplish multiple decisions when appropriate.

---

### 2. Reduce unnecessary tool calls

If the required information is already available:

```text
Do not call another tool.
```

---

### 3. Parallelize independent tools

Instead of:

```text
Search A
 ↓
Search B
 ↓
Search C
```

when the operations are independent:

```text
          Agent
            |
       +----+----+
       |    |    |
       v    v    v
     A      B    C
       |    |    |
       +----+----+
            |
            v
          Agent
```

This can reduce total waiting time.

---

### 4. Use faster models where appropriate

Not every step needs the same model.

For example:

```text
Simple classification → smaller/faster model
Complex reasoning → stronger model
```

---

### 5. Optimize tools

For slow tools:

```text
Database
→ indexes
→ optimized queries

Search
→ efficient retrieval

API
→ connection reuse / caching
```

---

### 6. Cache repeated results

If the same request occurs repeatedly:

```text
Query
 ↓
Cache
 ↓
Cached Result
```

This avoids unnecessary calls.

---

### 7. Stream responses

Streaming can improve perceived latency by allowing the user to see partial output while the system continues processing.

---

### 8. Reduce context size

Large prompts can increase processing time.

Use:

```text
Relevant context
instead of
Entire conversation/history
```

### Key Point

> **Reduce agent latency by minimizing unnecessary LLM/tool calls, parallelizing independent operations, optimizing slow tools, caching repeated work, using appropriate models, and controlling context size.**

### Interview Answer

> **I would first trace latency across the entire agent loop to identify the bottleneck. Then I would reduce unnecessary model and tool calls, parallelize independent tools, cache repeated results, optimize database/API operations, use faster models where appropriate, reduce unnecessary context, and stream the final response when useful.**

---

# 4. How would you control the cost of an agent making multiple LLM/tool calls?

### Answer

Agent cost mainly comes from:

```text
LLM tokens
+
Number of LLM calls
+
Tool/API usage
+
Database/search usage
```

A production system should have explicit cost controls.

---

### 1. Limit maximum agent steps

```python
MAX_STEPS = 8
```

This prevents:

```text
LLM → Tool → LLM → Tool → ...
```

from continuing indefinitely.

---

### 2. Limit tool calls

For example:

```text
Maximum searches = 5
Maximum database queries = 10
```

---

### 3. Control token usage

Avoid sending unnecessary:

- Conversation history
- Tool outputs
- Retrieved documents
- Repeated context

Use:

```text
Summarization
Context filtering
Relevant retrieval
Structured state
```

---

### 4. Use appropriate models

For simple tasks:

```text
Smaller model
```

For complex reasoning:

```text
More capable model
```

There is no need to use the most expensive model for every step.

---

### 5. Cache results

Cache:

```text
Embeddings
Search results
Repeated API responses
Repeated calculations
```

where appropriate.

---

### 6. Avoid unnecessary retries

Retries consume resources.

```text
MAX_RETRIES = 2
```

Only retry failures that are likely to be temporary.

---

### 7. Set a cost/time budget

Conceptually:

```text
Agent Budget

Max Steps      = 8
Max Tool Calls = 10
Max Tokens     = X
Max Time       = 60 sec
```

If the budget is exceeded:

```text
Stop safely
```

---

### 8. Monitor cost per task

Track:

```text
Cost per request
Tokens per request
LLM calls/request
Tool calls/request
Average cost
Maximum cost
```

This helps identify expensive agent behaviors.

### Key Point

> **Agent cost should be controlled using step limits, tool-call limits, token budgets, appropriate models, caching, bounded retries, and monitoring of cost per task.**

### Interview Answer

> **I would control cost by limiting the number of agent steps and tool calls, controlling prompt and tool-result size, using smaller models for simple operations, caching repeated work, limiting retries, and setting token, time, or cost budgets. I would also monitor cost per task to identify inefficient agent behavior.**

---

# 5. How would you monitor an agent in production?

### Answer

Monitoring should cover both **system performance** and **agent behavior**.

A useful production trace is:

```text
User Request
    ↓
Agent
    ↓
LLM Call
    ↓
Tool Selection
    ↓
Tool Execution
    ↓
Tool Result
    ↓
LLM
    ↓
Final Answer
```

Each step should be observable.

---

### 1. System metrics

Monitor:

```text
Latency
Throughput
Error rate
Timeout rate
Availability
Token usage
Cost
```

---

### 2. Agent metrics

Track:

```text
Average steps/request
Average tool calls/request
Tool-selection errors
Repeated tool calls
Agent completion rate
Agent failure rate
```

---

### 3. Tool metrics

For every tool:

```text
Tool name
Call count
Success rate
Failure rate
Latency
Timeouts
Retry count
```

Example:

```text
search_tool
Calls: 10,000
Success: 98%
Timeout: 1%
Error: 1%
Average latency: 350 ms
```

---

### 4. LLM metrics

Track:

```text
Input tokens
Output tokens
Latency
Model used
Cost
Number of calls
```

---

### 5. Quality metrics

Monitoring should not only ask:

> "Did the system respond?"

It should also ask:

> "Did the system perform the task correctly?"

Possible metrics include:

```text
Task success rate
Tool-selection accuracy
Answer correctness
Groundedness
User feedback
Human evaluation
```

---

### 6. Distributed tracing

A request should have a trace ID.

```text
Trace ID: ABC123

User Request
   ↓
LLM Call #1
   ↓
Search Tool
   ↓
LLM Call #2
   ↓
Database Tool
   ↓
LLM Call #3
   ↓
Final Answer
```

This makes debugging much easier.

---

### 7. Alerts

Create alerts for:

```text
High error rate
High latency
Unexpected cost increase
Tool failure spike
Repeated tool loops
High token usage
Service downtime
```

### Key Point

> **Production monitoring should cover infrastructure, LLM usage, tool execution, agent behavior, cost, latency, errors, and task quality.**

### Interview Answer

> **I would instrument every agent step and maintain end-to-end traces. I would monitor latency, errors, token usage, cost, number of steps, tool calls, tool failures, retries, and task success. I would also monitor quality metrics such as answer correctness and tool-selection accuracy and create alerts for abnormal behavior.**

# 6. How would you evaluate whether an agent is actually performing its task correctly?

### Answer

Agent evaluation should measure more than whether the LLM generated a response.

The important question is:

> **Did the agent successfully complete the intended task?**

### Example

Suppose the task is:

> "Find the customer's order and calculate the total refund."

A response can sound convincing while still being wrong.

So evaluation should examine the complete execution.

```text
User Task
   ↓
Tool Selection
   ↓
Tool Arguments
   ↓
Tool Execution
   ↓
Intermediate Results
   ↓
Final Answer
```

---

### 1. Task success

Did the agent actually complete the task?

```text
Task:
Book appointment

Success:
Appointment actually booked
```

Not:

```text
Agent:
"I have booked your appointment."

```

if no booking occurred.

---

### 2. Tool-selection accuracy

Check:

```text
Expected Tool
vs
Selected Tool
```

Example:

```text
Question → Weather Tool
Agent → Calculator

❌ Incorrect
```

---

### 3. Tool argument correctness

Even if the correct tool is selected, arguments can be wrong.

```text
Expected:
customer_id = 123

Agent:
customer_id = 321
```

---

### 4. Final answer correctness

Compare the final response with the expected result.

For deterministic tasks:

```text
Expected: 400
Agent: 400
→ Correct
```

---

### 5. Groundedness

For RAG-based agents, check whether the answer is supported by retrieved information.

```text
Retrieved Evidence
       ↓
Final Answer
```

The answer should not introduce unsupported facts.

---

### 6. Efficiency

An agent can complete the task correctly but use too many steps.

Compare:

```text
Agent A → 3 steps
Agent B → 15 steps
```

Both may succeed, but their efficiency differs.

Useful metrics:

```text
Average steps
Average tool calls
Latency
Cost
```

---

### 7. Robustness

Test difficult situations:

```text
Missing information
Invalid input
Tool failure
Timeout
Ambiguous question
Malformed tool result
Prompt injection
```

A reliable agent should fail safely.

---

### 8. Human evaluation

For subjective tasks such as research or writing, human reviewers can evaluate:

```text
Correctness
Relevance
Completeness
Clarity
Groundedness
```

### Evaluation dataset

Create representative test cases:

```text
Input
Expected Tool
Expected Result
Expected Behavior
```

Example:

| Test | Expected Behavior |
|---|---|
| Weather question | Call weather tool |
| Simple arithmetic | Use calculator |
| Internal policy | Use RAG |
| Unauthorized request | Reject |
| Tool timeout | Retry/fail gracefully |

### Key Point

> **Agent evaluation should measure task success, tool selection, tool arguments, final-answer correctness, groundedness, efficiency, and safe behavior under failures.**

### Interview Answer

> **I would evaluate an agent at multiple levels: whether it selected the correct tools, generated correct arguments, obtained the correct results, produced a correct final answer, and completed the actual task. I would also measure latency, cost, number of steps, robustness to tool failures, and safety behavior.**

# 7. How would you design a production-grade agent architecture?

### Answer

A production-grade agent should separate:

```text
User Interface
      ↓
Agent / Orchestration
      ↓
LLM
      ↓
Tools
      ↓
External Systems
```

while adding dedicated layers for:

- Validation
- Authorization
- State
- Observability
- Error handling
- Cost control
- Security
- Evaluation

---

## High-Level Architecture

```text
                         USER
                          |
                          v
                 +----------------+
                 |   API / UI     |
                 +-------+--------+
                         |
                         v
                 +----------------+
                 | Auth / Rate    |
                 |    Limiting    |
                 +-------+--------+
                         |
                         v
                 +----------------+
                 |     Agent      |
                 |  Orchestrator  |
                 +-------+--------+
                         |
                  +------+------+
                  |             |
                  v             v
               State          LLM
                  |             |
                  |       Tool Decision
                  |             |
                  |             v
                  |      +-------------+
                  |      |   Tool     |
                  |      | Validation |
                  |      +------+------+
                  |             |
                  |      Authorization
                  |             |
                  |             v
                  |      +-------------+
                  |      |    Tools    |
                  |      +------+------+
                  |             |
          +-------+------+------+-------+
          |              |              |
          v              v              v
       Database        APIs          RAG/Search
          |              |              |
          +--------------+--------------+
                         |
                         v
                    Tool Results
                         |
                         v
                      Agent
                         |
                         v
                   Final Response
                         |
                         v
                        USER
```

---

## 1. API / Authentication Layer

The system should first establish:

```text
Who is the user?
What are they allowed to do?
How frequently can they call the system?
```

Use:

```text
Authentication
Authorization
Rate limiting
Request validation
```

---

## 2. Agent Orchestration Layer

This layer manages:

```text
Agent loop
State
Tool selection
Step limits
Stopping conditions
Error handling
```

Conceptually:

```text
while not finished:

    decide_next_action()

    if tool_required:
        validate()
        authorize()
        execute()
        update_state()

    else:
        return_answer()
```

---

## 3. LLM Layer

The LLM handles:

```text
Understanding the request
Planning/decision making
Tool selection
Generating responses
```

But it should **not** be treated as the security boundary.

---

## 4. Tool Gateway / Validation Layer

Every tool request should pass through a controlled layer.

```text
LLM
 ↓
Tool Request
 ↓
Schema Validation
 ↓
Authorization
 ↓
Rate Limit
 ↓
Execution Constraints
 ↓
Tool
```

This is one of the most important production design principles.

---

## 5. Tools Layer

Tools can include:

```text
RAG
Search
Database
Calculator
Internal APIs
External APIs
Business systems
```

Each tool should have:

```text
Clear schema
Clear description
Defined permissions
Timeout
Error handling
Logging
```

---

## 6. State / Memory Layer

Store the state needed for the current task.

```text
State
├── User request
├── Current step
├── Tool calls
├── Tool results
├── Intermediate data
└── Final result
```

Persistent memory should be used only when required.

Do not blindly send the entire conversation history to every LLM call.

---

## 7. Observability Layer

Record:

```text
Request ID
Trace ID
LLM calls
Tool calls
Arguments
Results
Latency
Errors
Token usage
Cost
```

Sensitive information should be protected or redacted in logs.

---

## 8. Reliability Layer

Handle:

```text
Timeouts
Retries
Rate limits
Malformed responses
Tool failures
LLM failures
Network failures
```

with bounded execution.

---

## 9. Security Layer

Apply:

```text
Least privilege
Authentication
Authorization
Tool allowlists
Input validation
Output handling
Secret management
Prompt-injection defenses
Audit logging
```

---

## 10. Evaluation Layer

Continuously evaluate:

```text
Task success
Tool selection
Tool arguments
Answer correctness
Groundedness
Latency
Cost
Failure rate
```

Production systems should not rely only on occasional manual testing.

---

# Example Production Request

Suppose the user asks:

> "Check my order status and tell me whether it has been delivered."

The execution could look like:

```text
User
 ↓
API
 ↓
Authentication
 ↓
Agent
 ↓
LLM
 ↓
Decides: get_order_status
 ↓
Tool Validation
 ↓
Authorization
 ↓
Order API
 ↓
Order Result
 ↓
Agent
 ↓
Final Answer
 ↓
User
```

If the API fails:

```text
Order API
   ↓
Timeout
   ↓
Retry
   ↓
Success
   ↓
Agent
   ↓
Answer
```

If authorization fails:

```text
Authorization
   ↓
Denied
   ↓
Tool NOT executed
   ↓
Safe response
```

Every tool call would pass through validation and authorization before execution. I would add timeouts, bounded retries, step and cost limits, secure credential management, tracing, monitoring, and continuous evaluation of task success and agent behavior.**
