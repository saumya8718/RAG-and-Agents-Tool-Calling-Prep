# 02. Tools & Tool Calling

## 1. What is a tool in an AI agent?

### Answer

A **tool** is an external function, API, service, or capability that an AI agent can use to perform an action or obtain information that the LLM cannot reliably do by itself.

The LLM decides **when and which tool to use**, while the application actually executes the tool.

### Examples of Tools

An agent can have tools such as:

- Web search
- Calculator
- Weather API
- Database query
- File search
- RAG retrieval
- Email API
- Payment API
- External business APIs

### Example

Suppose an agent has:

```text
Tools:
1. calculator()
2. get_weather()
3. search_web()
```

User asks:

> "What is the weather in Delhi?"

The agent can select:

```text
get_weather()
```

The application executes the function and returns the result to the LLM.

### Basic Flow

```text
User
 ↓
LLM
 ↓
Select Tool
 ↓
Application executes Tool
 ↓
Tool Result
 ↓
LLM
 ↓
Final Answer
```

### Important Point

A tool is not necessarily an AI model.

For example:

```text
calculator() → normal program/function
weather_api() → external API
search() → search service
```

The LLM acts as the decision-making layer that determines when these capabilities are needed.

### Key Point

> **A tool is an external capability that an AI agent can invoke to retrieve information or perform an action.**

### Interview Answer

> **A tool in an AI agent is an external function, API, database, search service, or other capability that the agent can use to perform actions or obtain information. The LLM decides which tool is needed, while the application executes the tool and sends its result back to the LLM.**

## 2. What is tool calling/function calling?

### Answer

**Tool calling**, also called **function calling**, is a mechanism that allows an LLM to request the execution of a specific function or tool using **structured arguments**.

The LLM does not directly execute the function.

Instead, it generates a structured tool-call request:

```text
LLM
 ↓
Tool name + arguments
 ↓
Application
 ↓
Execute function
 ↓
Tool result
 ↓
LLM
```

### Example

Suppose we define:

```text
get_weather(city)
```

The user asks:

> "What is the weather in Delhi?"

The LLM may generate a tool call conceptually like:

~~~json
{
  "tool": "get_weather",
  "arguments": {
    "city": "Delhi"
  }
}
~~~

The application then executes:

```text
get_weather("Delhi")
```

The result might be:

~~~json
{
  "temperature": 31,
  "condition": "Sunny"
}
~~~

The result is sent back to the LLM, which generates the final response:

> "The weather in Delhi is 31°C and sunny."

### Why Is It Called Function Calling?

Because the tool is often represented to the LLM as a function with:

- Function name
- Description
- Parameters
- Parameter types
- Required fields

### Key Point

> **Tool calling allows an LLM to request a specific tool/function with structured arguments, while the application is responsible for actually executing it.**

### Interview Answer

> **Tool calling or function calling is a mechanism where an LLM selects a tool and generates structured arguments for it. The application receives this tool call, validates and executes the function, sends the result back to the LLM, and the LLM then produces the final response.**

## 3. Why can't an LLM directly execute a function?

### Answer

An LLM is primarily a model that **generates outputs**. It does not automatically have direct access to the application's runtime, operating system, databases, APIs, or other external resources.

For example, an LLM may generate:

```text
get_weather("Delhi")
```

But generating that text does not actually execute the function.

There needs to be an application layer between the LLM and the external system.

### Correct Architecture

```text
                 ┌──────────────┐
                 │     LLM      │
                 └──────┬───────┘
                        ↓
                Tool Call Request
                        ↓
                 ┌──────────────┐
                 │ Application  │
                 └──────┬───────┘
                        ↓
                Execute Function
                        ↓
                 External System
                        ↓
                   Tool Result
                        ↓
                       LLM
```

### Why Is This Separation Important?

The application needs to control:

- Which tools are available
- Whether the arguments are valid
- Whether the user is authorized
- Whether the action is safe
- How the function is executed
- How errors are handled
- What result is returned to the LLM

For example, an LLM should not automatically be allowed to execute:

```text
delete_database()
```

without application-level validation and authorization.

### Key Point

> **The LLM can generate a request to call a function, but the application/runtime must execute that function.**

### Interview Answer

> **An LLM cannot directly execute a function because it does not inherently have access to the application's runtime or external systems. It can generate a structured tool-call request, but the application must validate the request, execute the function, handle errors and permissions, and return the result to the LLM.**

## 4. How does an LLM decide which tool to call?

### Answer

The LLM decides which tool to call based on the **user's request, available tool definitions, instructions, and current context/state**.

The application provides the LLM with descriptions of the available tools.

For example:

```text
Tools:

1. calculator
   Description: Performs mathematical calculations.

2. weather
   Description: Returns current weather information.

3. search
   Description: Searches for information on the web.
```

The user asks:

> "What is 25 × 40?"

The LLM identifies that the calculator tool matches the task.

```text
User Request
     ↓
    LLM
     ↓
Understand Intent
     ↓
Match available tool
     ↓
calculator
```

For:

> "What is the weather in Delhi?"

it may select:

```text
weather
```

### The LLM Also Determines Arguments

After selecting the tool, it determines the required arguments.

For:

```text
get_weather(city)
```

the user request:

> "What's the weather in Delhi?"

can produce:

~~~json
{
  "city": "Delhi"
}
~~~

### Important

The LLM does **not randomly choose a function**.

The available tool definitions provide information such as:

- Tool name
- Description
- Parameters
- Parameter types
- Required fields

The model uses this information to select an appropriate tool.

### Multiple Tools

An agent may have:

```text
search()
calculator()
database_query()
weather()
```

The LLM can choose one or more tools depending on the task.

For example:

> "Find the price of a product and calculate the cost for 5 units."

Possible sequence:

```text
Product Search
      ↓
Get Price
      ↓
Calculator
      ↓
Final Answer
```

### Key Point

> **The LLM selects a tool by matching the user's goal with the descriptions and schemas of the available tools.**

### Interview Answer

> **The LLM decides which tool to call by considering the user's request, system instructions, available tool descriptions, schemas, and current context. It selects the tool that best matches the required action and generates the required structured arguments for that tool.**

## 5. What information should a tool definition/schema contain?

### Answer

A **tool definition/schema** tells the LLM what a tool does and what input it expects.

A good tool definition generally contains:

1. **Tool/Function name**
2. **Description**
3. **Parameters**
4. **Parameter types**
5. **Required parameters**
6. **Allowed values/constraints**, when applicable

### Example

Suppose we have a weather tool:

~~~json
{
  "name": "get_weather",
  "description": "Get the current weather for a city.",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {
        "type": "string",
        "description": "Name of the city"
      },
      "unit": {
        "type": "string",
        "enum": ["C", "F"],
        "description": "Temperature unit"
      }
    },
    "required": ["city"]
  }
}
~~~

### Explanation

#### Name

```text
get_weather
```

Uniquely identifies the tool.

#### Description

```text
Get the current weather for a city.
```

Helps the LLM understand when the tool should be used.

#### Parameters

Defines what information the tool needs.

```text
city
unit
```

#### Parameter Types

For example:

```text
city → string
unit → string
```

#### Required Parameters

For example:

```text
city → required
unit → optional
```

#### Constraints

Possible constraints include:

```text
enum: ["C", "F"]
```

This limits the allowed values.

### Why Is the Schema Important?

A clear schema helps the LLM:

- Select the correct tool
- Understand what the tool does
- Generate correct arguments
- Follow expected data types
- Avoid unnecessary tool calls

### Key Point

> **A tool schema describes what the tool does and exactly what structured input it expects.**

### Interview Answer

> **A tool definition should contain the tool name, a clear description, its parameters, parameter types, required fields, and relevant constraints such as allowed values. This information helps the LLM select the correct tool and generate valid structured arguments.**

## 6. What is structured tool input/output?

### Answer

**Structured tool input/output** means that data exchanged between the LLM, application, and tool follows a predefined format or schema rather than being arbitrary natural-language text.

Usually, structured data is represented using formats such as **JSON**.

### Structured Input

Suppose the tool is:

```text
get_weather(city, unit)
```

Instead of:

```text
"Please get the weather for Delhi in Celsius."
```

the application can use structured arguments:

~~~json
{
  "city": "Delhi",
  "unit": "C"
}
~~~

The structure clearly defines:

```text
city → string
unit → string
```

### Structured Output

The tool can return:

~~~json
{
  "city": "Delhi",
  "temperature": 31,
  "unit": "C",
  "condition": "Sunny"
}
~~~

The LLM can then interpret this result and generate a natural-language response.

### Why Structured Data Is Useful

It provides:

- Predictable format
- Easier validation
- Type checking
- Easier parsing
- Better reliability
- Easier debugging
- Better integration with applications

### Complete Example

```text
User
 ↓
LLM
 ↓
Structured Tool Call
 ↓
{
  "city": "Delhi",
  "unit": "C"
}
 ↓
Application
 ↓
Weather Tool
 ↓
Structured Result
 ↓
{
  "temperature": 31,
  "condition": "Sunny"
}
 ↓
LLM
 ↓
Natural Language Answer
```

### Natural Language vs Structured Input

```text
Natural Language:
"Get the weather for Delhi in Celsius."

Structured:
{
  "city": "Delhi",
  "unit": "C"
}
```

The structured form is easier for the application to validate and execute.

### Key Point

> **Structured tool input/output uses a predefined schema, usually JSON, so that tool arguments and results have a predictable and machine-readable format.**

### Interview Answer

> **Structured tool input and output means that the data exchanged with a tool follows a defined schema rather than arbitrary text. For example, a weather tool may accept `{ "city": "Delhi", "unit": "C" }` and return structured fields such as temperature and condition. This makes validation, parsing, and execution more reliable.**

## 7. Explain the complete flow of an LLM tool call from user request to tool result.

### Answer

The complete tool-calling flow can be divided into several steps.

### Step 1: User Sends a Request

Example:

> "What is the weather in Delhi?"

```text
User
 ↓
"What is the weather in Delhi?"
```

### Step 2: Application Sends Request + Tool Definitions to LLM

The application provides the LLM with:

- User request
- System instructions
- Available tools
- Tool descriptions
- Tool schemas

```text
User Request
     +
Tool Definitions
     ↓
    LLM
```

### Step 3: LLM Decides What to Do

The LLM determines that it needs weather information.

```text
LLM
 ↓
Select get_weather
```

### Step 4: LLM Generates Structured Tool Arguments

For example:

~~~json
{
  "city": "Delhi"
}
~~~

The LLM returns a tool-call request rather than the final answer.

### Step 5: Application Receives the Tool Call

The application reads:

```text
Tool:
get_weather

Arguments:
city = "Delhi"
```

### Step 6: Application Validates the Arguments

The application can check:

```text
Is city present?
Is city a string?
Is the request authorized?
Is the tool allowed?
```

### Step 7: Application Executes the Tool

```text
get_weather("Delhi")
```

The actual execution happens in the application/runtime.

### Step 8: Tool Returns a Result

For example:

~~~json
{
  "city": "Delhi",
  "temperature": 31,
  "condition": "Sunny"
}
~~~

### Step 9: Tool Result Is Sent Back to the LLM

```text
Tool Result
    ↓
   LLM
```

The LLM now has the actual information.

### Step 10: LLM Generates the Final Response

```text
LLM
 ↓
"The current temperature in Delhi is 31°C and it is sunny."
```

### Complete Flow

```text
┌───────────────┐
│     User      │
└───────┬───────┘
        │
        ↓
┌───────────────┐
│      LLM      │
│ Understand    │
│ Request       │
└───────┬───────┘
        │
        ↓
┌───────────────┐
│ Tool Selection│
└───────┬───────┘
        │
        ↓
┌────────────────────┐
│ Structured Arguments│
└─────────┬──────────┘
          │
          ↓
┌────────────────────┐
│    Application     │
│ Validate + Execute │
└─────────┬──────────┘
          │
          ↓
┌────────────────────┐
│       Tool         │
└─────────┬──────────┘
          │
          ↓
┌────────────────────┐
│    Tool Result     │
└─────────┬──────────┘
          │
          ↓
┌────────────────────┐
│        LLM         │
│ Generate Response  │
└────────────────────┘
```

### Short Version

```text
User
 ↓
LLM
 ↓
Tool Selection
 ↓
Structured Arguments
 ↓
Application Executes Tool
 ↓
Tool Result
 ↓
LLM
 ↓
Final Response
```

### Key Point

> **The LLM requests the tool call, but the application executes the tool and returns the result to the LLM.**

### Interview Answer

> **The flow starts with the user request. The application sends the request along with available tool definitions to the LLM. The LLM selects a tool and generates structured arguments. The application validates and executes the tool, receives the result, and sends that result back to the LLM. Finally, the LLM uses the tool result to generate the response to the user.**

## 8. What happens if the LLM generates invalid tool arguments?

### Answer

An LLM can sometimes generate arguments that do not match the tool's expected schema.

For example, suppose the tool expects:

~~~json
{
  "city": "Delhi"
}
~~~

But the LLM generates:

~~~json
{
  "city": 123
}
~~~

or:

~~~json
{
  "location": "Delhi"
}
~~~

where `city` is required.

The application should **not blindly execute the tool**.

### Correct Flow

```text
LLM generates arguments
        ↓
Validate arguments
        ↓
   Valid?
    /   \
  Yes    No
   ↓      ↓
Execute   Reject / Repair
Tool      / Retry
```

### Step 1: Validate

The application checks:

- Required fields
- Data types
- Allowed values
- Range constraints
- Format
- Authorization

For example:

```text
city must be a string
```

### Step 2: Handle the Error

If arguments are invalid, possible approaches include:

#### Option 1: Ask the LLM to Correct Them

```text
Invalid arguments
      ↓
Return error information to LLM
      ↓
LLM generates corrected arguments
      ↓
Validate again
```

#### Option 2: Reject the Request

If the problem cannot be safely corrected:

```text
Invalid arguments
      ↓
Reject tool call
      ↓
Return appropriate error
```

#### Option 3: Ask the User

If required information is missing:

```text
User:
"Book a flight to Delhi."

Missing:
Date

        ↓

Agent:
"What date would you like to travel?"
```

### Example

Tool schema:

```text
transfer_money(
    account_id: string,
    amount: number
)
```

LLM generates:

~~~json
{
  "account_id": "123",
  "amount": "ten thousand"
}
~~~

The application detects:

```text
Expected: number
Received: string
```

It should not directly execute the transfer.

### Why Validation Is Important

Without validation, invalid or unsafe arguments could:

- Cause application errors
- Produce incorrect results
- Trigger unintended actions
- Create security problems
- Cause data corruption

### Key Point

> **Never blindly trust LLM-generated tool arguments. Validate them before execution and handle invalid arguments through correction, retry, rejection, or user clarification.**

### Interview Answer

> **If an LLM generates invalid tool arguments, the application should validate them against the tool schema before execution. If validation fails, the system can return an error to the LLM for correction, retry with limits, ask the user for missing information, or reject the tool call. This prevents incorrect or unsafe tool execution.**

## 9. What is the difference between function calling and traditional API calling?

### Answer

**Function calling** and **traditional API calling** both involve executing functions or APIs, but the main difference is **who decides what should be called**.

### Traditional API Calling

In traditional API calling, the application developer explicitly writes the logic that determines when an API should be called.

Example:

```text
User Request
     ↓
Application Code
     ↓
Condition
     ↓
API Call
     ↓
API Result
```

For example:

```text
if user asks for weather:
    call weather API
```

The application controls the decision.

---

### Function Calling

With function calling, the **LLM can decide which available function/tool should be called** based on the user's request.

```text
User Request
     ↓
LLM
     ↓
Select Function
     ↓
Generate Arguments
     ↓
Application Executes Function
     ↓
Result
     ↓
LLM
```

### Example

Suppose we have:

```text
weather()
calculator()
search()
```

The application exposes these tools to the LLM.

User asks:

> "What is 25 × 20?"

The LLM may choose:

```text
calculator()
```

The application then executes it.

### Comparison

| Traditional API Calling | Function / Tool Calling |
|---|---|
| Application decides when to call API | LLM can decide which tool to call |
| Logic is usually explicitly coded | Tool selection can be model-driven |
| Developer controls the sequence | Agent can dynamically choose actions |
| API may be called directly by code | LLM produces structured tool-call request |
| More predictable | More flexible but potentially less predictable |

### Important Clarification

Function calling does **not** mean the LLM itself executes the function.

Instead:

```text
LLM
 ↓
Requests function call
 ↓
Application
 ↓
Actually executes function/API
```

So function calling is better understood as a **structured interface between the LLM and the application's tools**.

### Example

Traditional:

```text
if request_type == "weather":
    result = weather_api("Delhi")
```

Function calling:

```text
LLM
 ↓
{
  "tool": "weather_api",
  "arguments": {
    "city": "Delhi"
  }
}
 ↓
Application
 ↓
weather_api("Delhi")
```

### Key Point

> **Traditional API calling is usually controlled directly by application code, while function calling allows the LLM to select a predefined function and generate its structured arguments; the application still performs the actual execution.**

### Interview Answer

> **In traditional API calling, the application code determines when and how an API is called. In function calling, the LLM can select from predefined tools and generate structured arguments based on the user's request. The application then validates and executes the selected function. Therefore, function calling adds an LLM-driven decision layer on top of normal function or API execution.**
